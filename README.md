# TripDNA — 방향과 개발 순서

> **이 문서의 역할:** 이 프로젝트의 목표·범위·개발 순서를 담은 **단일 진입 문서**.
> **기준일:** 2026-09-30 (도시·LLM 추천 방향 갱신)
> **문서 우선순위:** 다른 문서와 충돌하면 **이 문서가 우선**한다.
> `docs/` 하위 문서는 새 추천의 데이터·동작·화면·평가 계약을 구체화한다.
> 중복된 3.0 문서는 정리했다. 세부 문서 목록은 [문서 목차](docs/README.md)를 따른다.

> **새 추천 방향:** 사용자 직접 선호와 도시 자료를 분리하고, 검수한 DB를 근거로 LLM이 후보·경험을 선택하는 구조를 검증한다. 상세 정책은 [취향·도시·LLM 추천 설계 v2](docs/recommendation/architecture.md)에 위임한다. 문서에는 새 구조의 요구사항을 두고, 기존 구현은 이관·비교에 필요한 현황만 구분해 적는다. 현행 버전 선출시 여부는 미정이다.

## 1. 목표 (2026-09-10 변경)

| 구분 | 이전 | 현재 |
|---|---|---|
| 목표 | 수익 사업 검증 | **출시하고 사용자를 만든다** |
| 수익 | 구독 중심 | **제휴 단독.** 구독 없음 |
| 성공 기준 | 사용자 1만 명 | **출시 + 공유 발생 + 제휴사 확정 예약 1건** |

### 목표를 한 문장으로

> 공유로 유입을 만들고, 취향 이해와 추천 품질로 다시 사용할 이유를 만든다.
> 앱스토어에 출시해서 사람들이 자기 취향 지문을 공유하게 만들고,
> **출시 후 6개월 안에 제휴사 대시보드에서 확정(confirmed) 예약 1건**을 확인한다.

기준이 "정산(입금) 1건"이 아니라 "확정 예약 1건"인 이유는 정산 주기 때문이다. Klook은 예약 다음 달에 검증하고 검증 후 약 90일 뒤에 지급하므로 예약에서 입금까지 3~4개월이 걸리고, 최소 지급액도 $50다. 커미션 5%면 10만 원 예약당 5천 원이라 입금 한 번을 보려면 예약 10건 안팎이 쌓여야 한다. 유입이 붙는 시간까지 더하면 6개월 안에 입금은 사실상 판정 불가다. **확정 예약 1건은 같은 것을 검증하면서 6개월 안에 측정이 된다.**

### 왜 이렇게 바꿨는가

"어디로 갈지 정하기 전" 구간은 업계에서 구조적으로 **무료 미끼 구간**이다. 실제 돈은 예약에서 나고, 예약 구간에서는 자본과 공급자 관계가 이긴다. 국가 추천 단계의 제휴 수익은 월 1만 명 규모에서도 수십만 원대에 그친다.

따라서 **이 제품으로 생계형 매출을 만드는 목표는 접는다.** 대신 되돌릴 수 없는 결정을 피하고, 출시·유입·제휴 파이프라인을 한 바퀴 완주하는 것을 목표로 둔다.

### 수익모델을 제휴 단독으로 두는 이유

구독은 유지율이 곧 매출이다. 안 쓰는 달이 생기면 해지된다. 제휴는 **쓰는 순간의 구매 의도**만 있으면 된다. 여행 결정은 원래 연 1~2회이므로, "계획할 때만 열리는 앱"은 이 카테고리의 정상 패턴이고 제휴에서는 손해가 아니다.

구독을 넣지 않으면 페이월이 사라져 사용자 수가 최대화되고, 인앱결제·환불·가격 실험·결제 심사가 전부 사라진다. 나중에 새 기능을 유료로 붙이는 길은 열려 있으므로 **되돌릴 수 있는 결정**이다.

## 2. 한 줄 정의와 판단 기준

**지난 여행에서 좋았던 점과 아쉬웠던 점을 기억해서, 다음 여행지를 고를 때 같은 실패를 줄여주는 앱.**

모든 기능은 다음 기준으로 판단한다.

1. 사용자 취향을 더 정확히 이해하거나 추천 품질을 검증하는가?
2. 출시를 위해 필요한 범위인가, 출시 후 평가하면서 교체할 수 있는가?
3. 사람들이 결과를 **공유**하고 다음 여행을 계획할 때 다시 사용할 이유를 만드는가?
4. 추천의 독립성을 지키면서 **제휴 상품으로 이어질 자리**를 만드는가?

> **검증할 가설:** 여행 기록이 적어도, 좋고 싫었던 이유를 구분해서 물으면 적은 입력으로 더 적합한 후보를 제시할 수 있다.
> 인기순·관심사만 사용한 추천 대비 개선 여부로 판단한다. 결정성·동점 감소·국가별 노출 균등만으로 추천 품질을 입증하지 않는다.

## 3. 구현 상태와 전환 경계

현행 앱에는 온보딩·여행 기록·평가·국가 추천·공유·SwiftData 저장이 있다. 추천은 여전히 국가 프로필과 5축을 사용한다. **도시 DB·직접 선호 기반 기억·LLM 추천은 아직 구현하지 않았다.**

- 문서 정리는 구현 이관 완료가 아니다. 현재 빌드의 국가 추천을 새 설계의 추천 품질로 평가하지 않는다.
- 앱이 읽는 국가·태그 번들 JSON은 이관 전 실행을 위해 유지한다. 새 도시 자료의 근거로 복사하지 않는다.
- 국가 축 CSV·중복 시드·생성 도구와 튜닝 지침은 문서에서 제거했다. 과거 모델 비교는 Git 커밋과 해당 번들 자료 해시를 고정해 재현한다.
- 테스트·빌드 통과 이력은 해당 커밋의 기록이다. 새 구조의 품질·이관·출시 검증을 대신하지 않는다.

## 4. 저장·전송 경계

여행·사진의 영속 저장은 현재 SwiftData·LocalPhotoStore를 사용하며 기기 간 동기화·서버 복구는 없다. 로그인 없이 이용할 수 있고, Apple 로그인만으로 기록이 복구되지는 않는다.

LLM 채택 시 키 보호·요청 검증·호출 제한을 위한 서버를 도입한다. 추천에 필요한 직접 증거·방문 도시·이번 조건만 전송하며, 원본 사진·EXIF·전체 위치 이력은 보내지 않는다. 외부 전송 안내, 제공자 보관 설정, 로그 최소화·삭제 정책을 구현과 함께 확정한다. 로컬 저장을 이유로 LLM 운영 비용이나 개인정보 검토가 없다고 간주하지 않는다.

LLM 호출과 사용자 전체의 행동 집계는 별개다. 집계는 출시 후 별도로 판단하며, 목적·항목·보관 기간·동의·철회·삭제·접근 통제를 정하기 전 과거 기록을 자동 업로드하지 않는다. 기기 식별자로 연결되는 기록을 익명이라고 단정하지 않는다.

Apple 로그인은 필수로 바꾸지 않는다. 현재 별도 로그아웃 대신 데이터 삭제 경로를 제공하며, 서버 보관을 도입하면 실제 삭제 범위를 함께 안내한다. 상세 계약은 [저장·전송 경계](docs/data/storage-and-privacy.md)를 따른다.

## 5. 수익화: 제휴 단독

### 원칙 (변경 불가)

1. **제휴 수수료 유무는 취향 적합도 산정에 절대 사용하지 않는다.** 추천은 제휴와 독립적으로 계산한다.
   영향의 방향은 한쪽으로만 흐른다. **제휴 → 랭킹은 금지. 랭킹 → 제휴 링크 선택은 허용.**
   즉 추천에서 선택한 경험과 검증된 도시 근거로 액티비티를 연결할 수 있다.
2. **제휴 관계를 화면에 표시한다.** 표시 방법은 아래 "표시 문구" 항에서 확정한다.
3. **클릭은 매출이 아니다.** 외부 링크 클릭과 예약 완료·정산을 구분해서 본다. 구현 방식은 아래 "측정" 항에서 확정한다.
4. 무료 단계에서 **"왜 추천했는지"와 "안 맞을 수 있는 점"은 반드시 보여준다.** 판단에 필요한 정보를 수익 목적으로 가리지 않는다.

### 붙일 위치: 여행 상세가 1순위, 추천 상세가 2순위

액티비티 예약은 **나라를 고르는 시점이 아니라 항공·숙소를 확정한 뒤**에 일어난다. 쿠키 윈도우는 GetYourGuide 31일, Klook 30일(호텔 7일)이라 "어느 나라 갈까" 단계의 클릭은 실제 예약까지 대부분 살아남지 못한다. §1에서 "국가 추천 단계는 구조적으로 수익 구간이 아님"이라고 적은 것과 같은 이유다.

| 순위 | 위치 | 역할 | 쓰는 도시 |
|---|---|---|---|
| **1** | 여행 등록 완료 / `TripDetailView` (출발 전 예정 여행) | **전환.** 확정 예약 1건은 여기서 나온다 | `TripLeg.cities` — 사용자가 직접 입력한 실제 도시. 시드 불필요 |
| 2 | `RecommendationDetailView` 액티비티 섹션 | 탐색·노출 | 새 구조에서는 추천 도시 ID와 검증된 제휴 목적지 연결 |

추천 상세의 섹션 구성:

```
왜 추천하나요
현실 적합
알아둘 점
이 도시에서는 뭐 할까   ← 새 구조. 추천 도시의 액티비티 제휴 링크
```

앞 3개 섹션은 전부 "당신의 취향" 이야기인데 네 번째만 일반 관광 정보면 톤이 끊겨 광고 블록으로 읽힌다. **선택된 도시·경험과 맞는 검증된 액티비티를 연결한다.** ("음식 탐방을 원해서 — 오사카 푸드 투어")

### 표시 문구

「추천·보증 등에 관한 표시·광고 심사지침」 2024-12-01 개정에서 **"수수료를 지급받을 수 있음" 같은 조건부·불확정 표현은 명확한 표시문구가 아닌 것으로 분류**됐고, 매출 실적에 따라 나중에 대가를 받는 경우(= 제휴 링크)도 공개 의무 대상임이 명시됐다.

- 문구는 **단정형.** "이 링크로 예약하면 TripDNA가 수수료를 **제공받습니다**."
- 위치는 추천 내용과 **근접하게, 링크 카드 위에.** 접기·더보기 뒤에 두지 않는다.
- 지침은 본문보다 크게 하거나 색을 달리해 쉽게 인식되게 하라고 한다. **`Color.dnaSlate` 캡션은 본문보다 흐리므로 그대로 쓰지 않는다.**

> 이 지침의 세부 조항은 블로그·카페 등 문자 매체 기준으로 쓰여 있고 앱 화면에 어느 조항이 그대로 준용되는지는 미확인이다. 위 세 가지(근접·단정형·충분한 대비)는 어느 해석에서도 안전한 선이므로 그 선을 지킨다.

### 측정: sub-id로 한다

`AnalyticsEvent`는 SwiftData 로컬에만 쌓인다. 서버가 없으므로 **다른 기기에서 일어난 클릭은 영원히 관측할 수 없다.** 로컬 이벤트의 용도는 본인 기기 검증뿐이다.

서버 없이 원칙 3을 실현하는 유일한 방법은 **링크의 sub-id에 맥락을 인코딩하고 제휴사 대시보드에서 역으로 읽는 것**이다.

```
subid = <진입지점>_<표시위치 또는 D-day>_<도시ID>
예시 형식: rec_1_jp_osaka / trip_d14_jp_osaka
```

제휴사가 지원하는 필드 길이·형식을 확인한 뒤 적용한다. 사용자 식별자·취향 원문은 넣지 않는다. 클릭 수와 확정 예약을 진입 지점·표시 위치·도시별로 확인하며, §6의 제휴 지표는 이 경로를 사용한다.

### 필요한 데이터: 추천 도시와 제휴 목적지 연결

새 구조는 추천한 도시 ID와 검증된 제휴 목적지 ID를 연결한다. 제휴 목적지가 없다는 이유로 추천 후보를 제외하지 않는다.

- 제휴 ID·링크는 도시의 경험 사실과 구분한다. 모델의 후보 선택에 수수료나 제휴 유무를 넣지 않는다.
- 기존 국가 CSV에 대표 도시를 끼워 넣어 새 도시 추천 DB를 대신하지 않는다.
- 여행 상세는 사용자가 실제 등록한 도시를, 추천 상세는 선택된 도시를 기준으로 연결한다.
- 도시 이름이 모호하거나 제휴 목적지를 확인하지 못한 경우 잘못된 도시 링크를 만들지 않는다.

여기서 따라 나오는 두 가지 제약:

1. **외부 링크 열기는 한 줄 작업이 아니다.** 유저 폰에 제휴사 앱이 깔려 있으면 유니버설 링크가 앱을 열고 그 순간 귀속이 사라진다. `SFSafariViewController`도 iOS 11부터 앱별로 분리된 쿠키 저장소를 쓰므로, 거기서 만든 쿠키는 사용자가 나중에 Safari로 예약할 때 따라가지 않는다. **제휴사 앱이 가로채지 않고 웹으로 열리는 방법을 제휴사별로 확인하고 실기기로 검증한다.**
2. **제휴 승인을 추천 개발의 직렬 블로커로 두지 않는다.** §9의 병행 작업으로 링크 자리·표시 문구·sub-id 구조를 준비하고, 승인된 제휴 ID와 목적지를 확인한 뒤 공개한다.

### 아직 미확인

- 심사지침 문자 매체 조항의 앱 화면 준용 범위
- 앱스토어 페이지가 Travelpayouts의 "공개 열람 가능한 프로젝트 링크"로 인정되는지
- 가이드라인 5.1.1(ix)(항공 여행 등 고규제 분야는 법인 명의 제출)의 적용 여부 — 액티비티 링크 연결은 서비스 제공이 아니라 해당하지 않을 가능성이 높으나, **항공권으로 확장하면 다시 본다**

## 7. 범위: 유지 / 동결 / 제외

### 유지 — 사용자 기능, 내부 추천 구조는 교체

- 온보딩: 사진첩·직접 입력·직접 선호 질문. 방문만으로 취향을 만들지 않으며 질문은 [온보딩](docs/screens/onboarding.md)과 [질문 설계](docs/screens/preference-questions.md)를 따른다.
- 여행 등록·상세·수정 가능한 평가·다국가 구간 기록.
- 직접 증거를 요약한 취향 지문·공유, 여행 간 평가·랭킹.
- 도시 추천·선택 조건·북마크·제외·기억 관리.
- 하루 한 장: 로컬 기록 기능. 자동 사진 선택은 별도 동의가 있을 때만 수행한다.
- 연간 Wrapped 6장·공유 카드. 공개 범위와 미리보기는 [공유 스펙](docs/screens/wrapped-and-sharing.md)을 따른다.

### 동결 — 유지하되 추가 투자 금지

- 사진 스캔의 예외 처리 고도화 (합치기·나누기 엣지 케이스)
- 장식 목적의 A/B 사진 세트 제작. 취향을 구분하는 질문·선택지 개선은 동결하지 않는다
- 장식 목적의 지문 그래프 개선. 새 증거 구조의 의미를 정확히 표시하기 위한 변경은 허용
- 랭킹 드래그 중 실시간 미리보기 (이미 있으면 그대로 둠)

### 제외 — 새 추천에서도 추가하지 않는 것

- 구독·크레딧·요금제
- 전 세계 모든 도시의 완전한 커버리지. 주요 도시 약 100곳의 검수·추천 실험은 §8에 따라 진행
- 출시 전 협업 필터링·집계 학습 서버. 출시 후 검증을 통과한 모델 갱신은 허용
- 도착 감지·위치 권한
- Firebase (Auth·Firestore·Storage)
- 실시간 항공 가격, 총예산 적합, 일정 생성기
- 후보 비교 화면, 유료 상세 비교 상품. 로컬 노출 집합 ID와 당시 입력 스냅샷은 평가를 위해 유지

> 도시·LLM 추천의 새 목표 범위는 §8을 따른다. 기존 국가 버전의 선출시 여부는 미정이며, 기존 5축·세션 제외·3슬롯을 새 구현의 요구사항으로 옮기지 않는다.

## 8. 추천·취향의 기준

### 새 추천의 목표 구조 (2026-09-30)

- 도시 중심으로 추천하고 나라는 위치·묶음으로 둔다. 주요 여행 도시 약 100곳이 초기 카탈로그 목표안이며, 정확한 목록·첫 공개 범위는 검수 후 정한다.
- 저장된 취향으로 즉시 추천한다. 날짜·예산 등 이번 조건은 선택 입력이며 미입력은 모름으로 남긴다.
- 검수한 도시 자료와 직접 선호로 LLM이 고른다. 앱은 제외·확인 가능한 필수 조건·출력 ID를 검증한다. 상세 답변은 DB 근거만 쓰고 최신 확인은 공식 링크로 안내한다.
- 방문 도시도 추천하되 “새로운 곳만 보기”를 제공한다. 이유 없는 도시 부정 반응은 계속 제외로 저장하고 안내·되돌리기를 제공한다.
- 명시적인 평소 취향은 자동 저장 후 안내·되돌리기를 제공한다. 방문·저장·질문만으로 성향을 만들지 않는다. 이번 조건과 평소 취향을 구분한다.
- 새 매칭 공식 설계는 중단한다. 같은 도시 자료로 단순 규칙과 LLM을 비교한 후 채택한다. 국가 기반 기존 앱과의 비교는 단위 차이를 명시한 별도 평가다.

정책·저장·실패 처리·이관·검증 시나리오는 [설계 v2](docs/recommendation/architecture.md)를 따른다. 이 구조는 아직 구현하지 않았다.

### 평가와 향후 학습

동일 사용자 사실·도시 자료로 단순 규칙과 LLM의 선택 품질을 비교하고, 설명 품질은 따로 평가한다. 입력 질문 수나 국가/도시 단위가 다른 비교를 LLM 자체의 우월성으로 해석하지 않는다. 지인 10~20명 파일럿은 오류 발견용이며 경쟁 우위의 증거가 아니다. 절차와 채택 기준은 [비교 실험](docs/evaluation/offline-evaluation.md)을 따른다.

실제 보인 후보만 노출로 기록한다. 당시 입력·후보·자료·프롬프트·모델 버전과 반응을 연결하고, 저장·클릭을 여행 만족도의 정답으로 간주하지 않는다. [계측](docs/evaluation/metrics.md)에서 구현 현황과 추가 요구를 구분한다.

향후 집계에서는 실제 경험 보고로 도시 자료를 검토하고, 직접 선호·이번 조건·만족도 관계로 추천을 개선한다. 저장자의 취향 평균을 여행지 특성으로 되먹이지 않는다. 이용자 수만으로 학습 모델을 전환하지 않으며, 버전별 평가와 되돌리기를 전제로 한다.

## 9. 개발 순서

실행 항목과 완료 기준·진행 상태는 [전환 체크리스트](docs/TODO.md)에서 관리한다. 아래는 단계 요약이다.

1. **도시 자료와 입력 형식 검수:** 15~20곳에서 출처·지역·경험·조건 형식을 확인한 뒤 목표 100곳으로 확장한다. 국가 축을 채우는 작업으로 대신하지 않는다.
2. **PC 비교 실험:** 동일 도시 자료와 사용자 사례로 단순 규칙·고품질 LLM·저가 LLM을 비교한다. 선택·설명·일관성·비용·지연·실패를 측정한다. 모델과 비용 상한은 아직 미정이다.
3. **채택 후 데이터 이관:** 원본 여행·답변·북마크·제외를 보존하고 직접 증거·이번 여행·도시 ID를 구분한다. 기존 국가 평균에서 파생한 지문은 새 선호로 옮기지 않는다.
4. **서버·화면 연결:** 요청 검증·비용 제한·전송/삭제 정책과 추천·상세·피드백·기억 관리·공유를 구현한다. 제외와 필수 조건을 앱에서 검증한다.
5. **출시 검증:** 품질 기준, 원본 보존, 제외·되돌리기, 실패 처리, 공유 공개 범위와 §10을 확인한다. 현재 버전 선출시 여부는 별도 결정한다.
6. **출시 후 관측:** 추천 품질·공유·다음 여행의 재사용·제휴 확정 예약을 본다. 사용자 집계는 동의·운영 범위와 효과를 검증한 뒤 별도 도입한다.

### 병행할 제휴·공유·출시 작업

- 제휴사 승인과 추천 개발을 분리한다. 도시 ID와 검증된 제휴 목적지를 연결하고 표시 문구·sub-id·실기기 링크 귀속을 확인한다. 제휴 설정이 없는 상태로 수익 경로가 완성됐다고 표시하지 않는다.
- 지문·여행·Wrapped 공유의 미리보기, 실제 저장·전송, 공개 범위를 실기기에서 확인한다. 정확한 여행 날짜·도시·동행인·사진은 기존 공유 이미지에 포함하지 않는다.
- 앱스토어 설치 주소(`TripDNAShareURL`), 앱 아이콘, 개인정보 처리방침, 사진첩 권한 문구, `PrivacyInfo.xcprivacy`, 메타데이터·스크린샷·심사 준비를 점검한다.
- 공유나 제휴 성과를 기다려 초기 도시 추천 검증을 미루지 않는다. 확정 예약 여부는 §1의 성공 기준을 따른다.

## 10. 출시 차단 요건

아래는 출시할 빌드에서 확인할 요건이며, 이번 문서 정리로 통과한 검사가 아니다.

- 빌드·회귀 검사와 재시작 후 데이터 유지, 이관 실패 시 원본 보존.
- 출시할 추천 방식의 품질 기준 충족. 같은 입력·다른 취향 테스트만으로 정확도를 판정하지 않는다.
- 제외 위반·허위 근거 방지, 기억 수정·되돌리기·삭제, 늦은 응답·오류·비용 제한 처리.
- LLM 사용 시 외부 전송 안내·키 보호·접근 통제·보관 및 삭제 정책.
- 여행·평가·전체 데이터 삭제와 공유 공개 범위 확인.
- 개인정보 처리방침·권한 문구·앱 아이콘·프라이버시 선언·앱스토어 제출 자료.
- 제휴 링크를 공개하는 경우 표시 문구·목적지·귀속 검증.

## 11. 하지 말아야 할 것

이 프로젝트에서 반복된 실패 패턴이다.

1. **중복 스펙을 계속 늘리는 것.** 변경은 기준 문서와 관련 화면에 반영하고 폐기한 규칙·끊어진 참조를 함께 정리한다.
2. **불공정한 비교로 모델을 선택하는 것.** 알려진 추론 오류, 입력 정보량, 후보·자료·추천 단위의 차이를 구분해서 평가한다.
3. **검증 없이 "사용자가 쌓이면 좋아진다"고 가정하는 것.** 어떤 관측으로 무엇을 학습할지 정하고, 적은 데이터에서도 작동하는 초기 모델과 평가 기준선을 유지한다.
4. **기능 수나 복잡한 수식을 차별점으로 간주하는 것.** 적은 입력으로 취향을 더 정확히 이해하는지 검증한다. 공유와 추천 품질을 함께 개선한다.
5. **효과를 확인하기 전에 운영 범위를 늘리는 것.** 주요 도시 검수·PC 실험부터 진행하고 LLM 채택 후 필요한 서버를 연결한다. 집계 학습 서버는 별도로 판단한다.
