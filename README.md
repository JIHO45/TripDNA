## 1. 목표 (2026-09-10 변경)

| 구분 | 이전 | 현재 |
|---|---|---|
| 목표 | 수익 사업 검증 | **출시하고 사용자를 만든다** |
| 수익 | 구독 중심 | **제휴 단독.** 구독 없음 |
| 성공 기준 | 사용자 1만 명 | **출시 + 공유 발생 + 제휴사 확정 예약 1건** |

### 목표를 한 문장으로

> 앱스토어에 출시해서 사람들이 자기 취향 지문을 공유하게 만들고,
> **출시 후 6개월 안에 제휴사 대시보드에서 확정(confirmed) 예약 1건**을 확인한다.

기준이 "정산(입금) 1건"이 아니라 "확정 예약 1건"인 이유는 정산 주기 때문이다. Klook은 예약 다음 달에 검증하고 검증 후 약 90일 뒤에 지급하므로 예약에서 입금까지 3~4개월이 걸리고, 최소 지급액도 $50다. 커미션 5%면 10만 원 예약당 5천 원이라 입금 한 번을 보려면 예약 10건 안팎이 쌓여야 한다. 유입이 붙는 시간까지 더하면 6개월 안에 입금은 사실상 판정 불가다. **확정 예약 1건은 같은 것을 검증하면서 6개월 안에 측정이 된다.**

### 왜 이렇게 바꿨는가

"어디로 갈지 정하기 전" 구간은 업계에서 구조적으로 **무료 미끼 구간**이다. 실제 돈은 예약에서 나고, 예약 구간에서는 자본과 공급자 관계가 이긴다. 국가 추천 단계의 제휴 수익은 월 1만 명 규모에서도 수십만 원대에 그친다.

따라서 **이 제품으로 생계형 매출을 만드는 목표는 접는다.** 대신 되돌릴 수 없는 결정을 피하고, 출시·유입·제휴 파이프라인을 한 바퀴 완주하는 것을 목표로 둔다.

### 수익모델을 제휴 단독으로 두는 이유

구독은 유지율이 곧 매출이다. 안 쓰는 달이 생기면 해지된다. 제휴는 **쓰는 순간의 구매 의도**만 있으면 된다. 여행 결정은 원래 연 1~2회이므로, "계획할 때만 열리는 앱"은 이 카테고리의 정상 패턴이고 제휴에서는 손해가 아니다.

구독을 넣지 않으면 페이월이 사라져 사용자 수가 최대화되고, 인앱결제·환불·가격 실험·결제 심사가 전부 사라진다. 나중에 새 기능을 유료로 붙이는 길은 열려 있으므로 **되돌릴 수 있는 결정**이다.

## 2. 한 줄 정의와 판단 기준

**지난 여행에서 좋았던 점과 아쉬웠던 점을 기억해서, 다음 여행지를 고를 때 같은 실패를 줄여주는 앱.**

모든 기능은 다음 순서로 판단한다.

1. 출시를 앞당기는가, 늦추는가?
2. 사람들이 결과를 **공유**하게 만드는가?
3. 추천에서 **제휴 상품으로 이어질 자리**를 만드는가?
4. 새로 만들 코드가 필요한가, 이미 있는 것으로 되는가?

> ⚠️ 이전 기준이던 "다음 여행지 예측의 정확도를 올리는가"는 **폐기.**
> 정확도를 올려도 출시하지 않으면 아무것도 확인할 수 없다.

## 3. 현재 구현 상태 (2026-09-10 실측)

Swift 54개 파일 / **13,536줄**. 빌드 성공. 단위 테스트 12개 + UI 테스트 전부 통과.

| 영역 | 코드 | 상태 |
|---|---|---|
| 온보딩 (스캔·직접입력·퀴즈·결과) | 2,536줄 | 구현됨 |
| 여행 (등록·상세·평가·하루한장) | 2,613줄 | 구현됨 |
| 공용 UI (사진·컴포넌트) | 2,296줄 | 구현됨 |
| 추천 (3슬롯·필터·저장·상세) | 1,319줄 | 구현됨. **단 아래 결함 있음** |
| Wrapped (스토리·공유카드) | 962줄 | 구현됨 |
| 지문 상세·랭킹 | 794줄 | 구현됨 |
| 도메인·서비스·저장소 | 2,106줄 | 구현됨 |
| **영속성** | SwiftData 저장소 | 구현됨 (2단계) |
| **외부 링크 / 제휴** | — | **없음** |

입력·기록(온보딩+여행+공용UI)이 **7,445줄로 전체의 55%**, 추천은 1,319줄로 10%다. 이 비중은 목표 변경 후에도 문제가 아니다. 기록 화면이 곧 공유 소재이기 때문이다. 단 **추가 투자는 하지 않는다.**

### ✅ 해결됨 — 추천 결함 2개 (2026-09-10, 1단계)

**1. 취향 매칭이 1개 축의 부호 비교로 붕괴하던 문제**

`matchingAxes`가 30개국 전부 `natureUrban` 하나뿐이라 코사인 유사도가 부호 일치 여부로 수렴했고, `tasteFit`이 1.0 아니면 0.0이었다. `interestTags`는 9개 중 `food`만 값이 있었고, `popularity`는 디코더에서 `nil`로 하드코딩돼 `underrated_fit`의 저인기 항이 동작하지 않았다.

- `matchingAxes`를 값이 채워진 4축(`natureUrban`·`energyLevel`·`planningStyle`·`socialMode`)으로 확장. `noveltyAppetite`는 국가별 값이 없어 제외한다.
- `interestTags` 9개와 `popularity`를 30개국 전부 채우고, 디코더가 `popularity`를 실제로 읽게 고침.
- 편집은 `country_profiles_draft.csv`에서만 한다. `generate_seed_data.py`가 스펙 시드와 앱 번들 리소스에 같은 JSON을 써서 두 사본이 어긋나지 않는다.

동점이 사라졌다. 도시·계획 성향은 일본 0.95 → 프랑스 0.899 → 한국 0.877, 유적·계획 성향은 이집트 0.954 → 아르헨티나 0.891로 갈린다. 이전에는 같은 자리에서 9~17개국이 0.90 동점이었다.

**2. 동점을 취향이 아니라 딕셔너리 순서가 깨던 문제**

`InMemoryAppStore`의 모든 조회를 안정적인 키로 정렬해서 반환하고, 추천 정렬에 "기준값 내림차순 → 국가 코드 오름차순" 타이브레이커를 명시했다. 설명 태그 정렬도 Set 순회 순서에 의존하던 것을 값·id 기준으로 고정했다.

슬롯 정책도 §8의 변경된 규칙에 맞췄다. `fresh_stretch`·`underrated_fit`은 1순위가 2순위보다 확실히 나을 때만 채우고, `best_match`는 거의 같은 점수인 나라가 3곳 이상이면 그 사실을 카드에 표시한다.

> 국가 프로필 값은 편집 데이터다. 출시 후 실제 반응을 보고 갱신한다.

## 4. 저장 방식: SwiftData 로컬 우선 (Firebase 보류)

기존 스펙은 Firebase(Auth·Firestore·Storage)를 전제했으나, **Firebase를 붙이지 않고 SwiftData로 출시한다.** 2단계에서 `SwiftDataAppStore`로 교체 완료.

| 항목 | 판단 |
|---|---|
| 서버 운영 | 없음. 1인 운영 부담 제거 |
| 비용 | 없음 |
| 개인정보 | 사진·여행 기록이 기기를 벗어나지 않음 → **Storage Rules·계정 삭제 운영·EXIF 처리 검증 요건이 대부분 소멸** |
| 사진 | 이미 있는 `LocalPhotoStore` 사용 |
| 한계 | 기기 간 동기화 없음. 기기 분실 시 데이터 소실 |
| 확장 | 필요해지면 SwiftData + CloudKit 미러링으로 승격 |

### Apple 로그인은 출시 시점에 필수로 두지 않는다

서버가 없으면 로그인이 사용자에게 주는 이득이 0이다. 계정 복구도, 기기 간 이어보기도 불가능하다. 그 상태에서 로그인을 강제하면 **마찰만 남고 유입이 줄어든다.**

- 이미 구현된 `AppleSignInClient` / `SessionStore`는 **유지**한다.
- 온보딩에서 로그인 없이 계속 진행할 수 있게 한다.
- CloudKit을 붙이는 시점에 로그인을 필수화한다.

> 기존 고정 결정이던 "Apple만, 게스트 없음"은 **변경됨.** 위 사유를 근거로 한다.

## 5. 수익화: 제휴 단독

### 원칙 (변경 불가)

1. **제휴 수수료 유무는 취향 적합도 산정에 절대 사용하지 않는다.** 추천은 제휴와 독립적으로 계산한다.
   영향의 방향은 한쪽으로만 흐른다. **제휴 → 랭킹은 금지. 랭킹 → 제휴 링크 선택은 허용.**
   즉 이미 계산이 끝난 `explanationTagIDs`로 어떤 액티비티를 보여줄지 고르는 것은 원칙 위반이 아니다.
2. **제휴 관계를 화면에 표시한다.** 표시 방법은 아래 "표시 문구" 항에서 확정한다.
3. **클릭은 매출이 아니다.** 외부 링크 클릭과 예약 완료·정산을 구분해서 본다. 구현 방식은 아래 "측정" 항에서 확정한다.
4. 무료 단계에서 **"왜 추천했는지"와 "안 맞을 수 있는 점"은 반드시 보여준다.** 판단에 필요한 정보를 수익 목적으로 가리지 않는다.

### 붙일 위치: 여행 상세가 1순위, 추천 상세가 2순위

액티비티 예약은 **나라를 고르는 시점이 아니라 항공·숙소를 확정한 뒤**에 일어난다. 쿠키 윈도우는 GetYourGuide 31일, Klook 30일(호텔 7일)이라 "어느 나라 갈까" 단계의 클릭은 실제 예약까지 대부분 살아남지 못한다. §1에서 "국가 추천 단계는 구조적으로 수익 구간이 아님"이라고 적은 것과 같은 이유다.

| 순위 | 위치 | 역할 | 쓰는 도시 |
|---|---|---|---|
| **1** | 여행 등록 완료 / `TripDetailView` (출발 전 예정 여행) | **전환.** 확정 예약 1건은 여기서 나온다 | `TripLeg.cities` — 사용자가 직접 입력한 실제 도시. 시드 불필요 |
| 2 | `RecommendationDetailView` 네 번째 섹션 | 탐색·노출 | 국가별 대표 도시 시드 |

추천 상세의 섹션 구성:

```
왜 추천하나요
현실 적합
알아둘 점
이 나라에서는 뭐 할까   ← 신규. 대표 도시별 액티비티 제휴 링크
```

앞 3개 섹션은 전부 "당신의 취향" 이야기인데 네 번째만 일반 관광 정보면 톤이 끊겨 광고 블록으로 읽힌다. **원칙 1의 허용 방향을 써서 `explanationTagIDs`로 액티비티 카테고리를 거른다.** ("미식 태그가 강해서 — 오사카 푸드 투어")

### 표시 문구

「추천·보증 등에 관한 표시·광고 심사지침」 2024-12-01 개정에서 **"수수료를 지급받을 수 있음" 같은 조건부·불확정 표현은 명확한 표시문구가 아닌 것으로 분류**됐고, 매출 실적에 따라 나중에 대가를 받는 경우(= 제휴 링크)도 공개 의무 대상임이 명시됐다.

- 문구는 **단정형.** "이 링크로 예약하면 TripDNA가 수수료를 **제공받습니다**."
- 위치는 추천 내용과 **근접하게, 링크 카드 위에.** 접기·더보기 뒤에 두지 않는다.
- 지침은 본문보다 크게 하거나 색을 달리해 쉽게 인식되게 하라고 한다. **`Color.dnaSlate` 캡션은 본문보다 흐리므로 그대로 쓰지 않는다.**

> 이 지침의 세부 조항은 블로그·카페 등 문자 매체 기준으로 쓰여 있고 앱 화면에 어느 조항이 그대로 준용되는지는 미확인이다. 위 세 가지(근접·단정형·충분한 대비)는 어느 해석에서도 안전한 선이므로 그 선을 지킨다.

### 측정: sub-id로 한다

`AnalyticsEvent`는 SwiftData 로컬에만 쌓인다. 서버가 없으므로 **다른 기기에서 일어난 클릭은 영원히 관측할 수 없다.** 로컬 이벤트의 용도는 본인 기기 검증뿐이다.

서버 없이 원칙 3을 실현하는 유일한 방법은 **링크의 sub-id에 맥락을 인코딩하고 제휴사 대시보드에서 역으로 읽는 것**이다.

```
subid = <진입지점>_<슬롯 또는 D-day>_<국가코드>_<도시>
예: rec_bestmatch_JP_osaka   /   trip_d14_JP_osaka
```

이러면 클릭 수와 확정 예약을 진입 지점·슬롯·국가·도시 축으로 분해할 수 있다. §6의 제휴 지표는 전부 이 경로로만 측정된다.

### 필요한 데이터: 국가별 대표 도시 (추천 상세용)

제휴사는 **도시 단위 액티비티**를 판다. "일본" 링크는 전환이 사실상 없다. 그렇다고 도시 추천 알고리즘을 만들 필요는 없다.

- 30개국 각각에 **대표 도시 2~3개**를 시드 데이터에 직접 넣는다. 편집은 `country_profiles_draft.csv` → `generate_seed_data.py` 경로를 그대로 쓴다.
- 도시 이름 문자열만 넣지 않는다. **제휴사의 destination id를 함께 넣는다** (GetYourGuide `locationId`, Klook city id). 검색 URL 조립은 전환이 낮고 URL 구조가 바뀌면 깨진다.
- 제휴사 한 곳에 묶이는 필드로 만들지 않는다. `cities: [{ name, nameKo, partnerIds: { ... } }]` 형태로 두면 제휴사를 갈아탈 때 시드를 다시 만들지 않아도 된다.
- 추천 점수 계산에는 **쓰지 않는다.** 제휴 링크를 붙일 자리를 만드는 용도다.
- `TripLeg.cities`는 사용자가 자기 여행에 입력하는 값이므로 이것과 별개다. 위 표의 1순위 위치는 시드가 아니라 이 값을 쓴다.

### 확인된 실무 조건 (2026-09-15 조사)

| 항목 | 확인된 내용 |
|---|---|
| 승인 | Klook 직접(`affiliate.klook.com`)은 최소 트래픽 요건이 공개돼 있지 않고 승인이 쉬운 편. Travelpayouts 경유는 **2개월 이상 된, 공개 열람 가능한 원본 여행 콘텐츠**를 요구 → 미출시 앱은 제출할 링크가 없다 |
| 커미션 | Klook 최대 5% / GetYourGuide 7~8% |
| 최소 지급액 | Klook $50 · GYG 직접은 PayPal 최소 없음·은행 €50 · Awin 경유 $20 |
| 정산 주기 | Klook은 예약 다음 달 검증 후 **약 90일 뒤** 지급 (예약→입금 3~4개월) |
| **앱 어트리뷰션** | **GYG 공식 문서: 자사 앱 내 파트너 쿠키 귀속 미지원.** Klook도 앱 내 트래킹은 앱이 이미 설치된 경우에만 동작 |
| 앱스토어 | 가이드라인 3.1.3(e) — 앱 밖에서 소비되는 실물 재화·서비스는 IAP 대상 아님. 투어·숙소 예약이 여기 해당하고 제휴 링크는 앱 내에서 결제를 받지 않으므로 리스크 낮음. EU 외부결제 규정은 디지털 재화 대상이라 무관 |

여기서 따라 나오는 두 가지 제약:

1. **외부 링크 열기는 한 줄 작업이 아니다.** 유저 폰에 제휴사 앱이 깔려 있으면 유니버설 링크가 앱을 열고 그 순간 귀속이 사라진다. `SFSafariViewController`도 iOS 11부터 앱별로 분리된 쿠키 저장소를 쓰므로, 거기서 만든 쿠키는 사용자가 나중에 Safari로 예약할 때 따라가지 않는다. **제휴사 앱이 가로채지 않고 웹으로 열리는 방법을 제휴사별로 확인하고 실기기로 검증한다.**
2. **제휴 승인을 출시 앞의 직렬 블로커로 두지 않는다.** §9 3단계를 둘로 쪼갠다 — 링크 자리·표시 문구·sub-id 구조까지는 제휴사 없이 먼저 만들고, 제휴 ID와 destination id는 출시 후 주입한다.

- 앱스토어 페이지가 Travelpayouts의 "공개 열람 가능한 프로젝트 링크"로 인정되는지
- 가이드라인 5.1.1(ix)(항공 여행 등 고규제 분야는 법인 명의 제출)의 적용 여부 — 액티비티 링크 연결은 서비스 제공이 아니라 해당하지 않을 가능성이 높으나, **항공권으로 확장하면 다시 본다**

- 평가 개수·매일 방문 같은 활동량 지표.

장기적으로 볼 것은 **"다음 여행을 계획할 때 돌아오는가"** 인데, 이건 출시 6~12개월 뒤에나 측정된다. 단기 판단에 쓰지 않는다.

## 7. 범위: 유지 / 동결 / 제외

### 유지 — 이미 구현됨. 출시에 포함

- 온보딩 3경로 (사진첩 스캔 / 직접 입력 / 사진 퀴즈)
- 여행 등록·상세·종료 평가·다국가 legs
- 지문 상세·랭킹 보드
- 추천 3슬롯·필터·저장 목록
- **하루 한 장** — 로컬 저장이므로 개인정보 부담이 없고 이미 완성됨
- **연간 Wrapped 6장 + 공유 카드** — 유입의 핵심 자산
- UTV 원장 재생 (`UTVReplayService`, 371줄)

> Wrapped·공유·하루 한 장은 **이전 검토에서 "보류" 판정을 받았으나 되살렸다.** 수익 검증이 목표일 때는 낭비지만, **유입이 목표일 때는 가장 강한 자산**이기 때문이다. 사람들이 캡처해서 올리는 형태이고, 이미 만들어져 있다.

### 동결 — 유지하되 추가 투자 금지

- 사진 스캔의 예외 처리 고도화 (합치기·나누기 엣지 케이스)
- 퀴즈 문항 확장·A/B 사진 세트 제작
- 지문 그래프 시각 개선
- 랭킹 드래그 중 실시간 미리보기 (이미 있으면 그대로 둠)

### 제외 — 만들지 않음

- 구독·크레딧·요금제
- 도시 추천 알고리즘, 전 세계 도시 커버리지
- 협업 필터링, 동적 추천, 세그먼트
- 도착 감지·위치 권한·하루 한 장 자동 후보
- Firebase (Auth·Firestore·Storage)
- 실시간 항공 가격, 총예산 적합, 일정 생성기
- 후보 비교 화면, `recommendationSession` 객체, 유료 상세 비교 상품

> 마지막 항목들은 **수익 사업을 목표로 할 때 필요한 것들**이다. 목표가 바뀌었으므로 만들지 않는다. 출시 후 공유·제휴 결과를 보고 다시 논의한다.

## 8. 데이터·산식 규칙 (유지)

기존 스펙에서 **가장 잘 만든 부분이고 그대로 유지한다.**

- **여행 원장이 진실의 원천이다.** UTV는 원장을 날짜순으로 결정적으로 재생한 파생 캐시다.
- 재생 트리거: 평가 확정, 랭킹 저장, 온보딩 완료.
- **Match Score와 현실 적합도를 합산하지 않는다.** 물가는 참고 배지로만 노출한다.
- **비행시간을 하드코딩하지 않는다.** 공항·노선 데이터가 없으면 UI를 숨긴다.
- 국가 프로필은 편집 데이터다. 출처·기준 시점·검수 상태를 붙인다.
- 하루 한 장은 UTV에 반영하지 않는다. 기록 전용이다.
- 추천 카드 반응 중 `save`/`dislike`만 보조 신호. `skip`은 UI 동작만.
- 사용자가 명시하지 않은 취향을 사실처럼 단정하지 않는다. 정보가 부족한 축은 "아직 흐린 축"으로 표시한다.

### 변경된 규칙

| 항목 | 기존 | 변경 |
|---|---|---|
| 평가 수정 | 제출 후 수정 없음 | **수정·삭제 가능.** 랭킹은 잘못 입력한 만족도·태그·날짜를 고치는 수단이 아니다 |
| 싫어요 | 180일 전역 제외 | **"이번엔 아니에요"(현재 세션 제외)와 "앞으로도 관심 없어요"(장기 제외)를 분리.** 장기 제외는 즉시 취소 가능 |
| 슬롯 | 3슬롯 고정 충족 | **근거 부족한 후보로 슬롯을 강제 충족하지 않는다.** 동점 그룹이 크면 그 사실을 드러낸다 |
| Profile_x | 편집 동결 | **오류는 새 버전으로 수정.** 동결 대상은 과거 실험의 기준 버전이지 잘못된 사실이 아니다 |

## 9. 개발 순서

각 단계는 **앞 단계가 끝나야 다음 단계가 의미를 갖는** 순서다.

### 0단계 — 커밋 정리 (즉시)

현재 커밋이 `Initial Commit` 하나뿐이고, **1.5개월치 작업 전체가 미커밋 상태**다. 사업성보다 현실적인 리스크다.

- 작업: 의미 단위로 나눠 커밋. 최소한 전체를 한 번 커밋.
- 완료 조건: `git status`가 깨끗하다.

### 1단계 — 추천이 실제로 작동하게 만든다 ✅ 2026-09-10 완료

§3의 결함 2개를 고친다. **코드보다 데이터 작업이 대부분이고, 추천 품질 개선 효과가 가장 크다.**

- `countries.json` 30개국 × `matchingAxes`에 나머지 3축(`energyLevel`·`planningStyle`·`socialMode`) 추가
- `interestTags` 9개 태그를 30개국에 채움 (현재 `food`만 채워져 있음)
- `popularity` 값 채움 또는 `underrated_fit` 슬롯의 저인기 항 제거
- 정렬 타이브레이커를 명시적으로 고정해 실행마다 결과가 바뀌지 않게 함
- 동점 그룹이 클 때 슬롯을 강제 충족하지 않도록 처리
- 완료 조건: 같은 입력으로 앱을 10번 재시작해도 `best_match`가 동일하고, 서로 다른 취향의 사용자 5명이 서로 다른 결과를 받는다. 이를 검증하는 테스트 추가.

### 2단계 — 영속성 ✅ 2026-09-10 완료

- `SwiftDataAppStore`(actor) 추가. 여행·랭킹·카드 반응·하루 한 장 메타데이터·지문·사용자 프로필·이벤트를 기기에 저장한다. 도메인 모델이 초기화 시점에 불변 조건을 검증하는 struct라, 조회 키만 컬럼으로 두고 값은 Codable JSON으로 보관한다.
- 저장소 전체를 `AppStore` 프로토콜로 묶어 교체 지점을 하나로 만들었다. `InMemoryAppStore`는 테스트·프리뷰용으로 남긴다.
- 국가·태그 시드는 번들 JSON 읽기 전용이라 DB에 넣지 않는다. 사진 파일은 기존 `LocalPhotoStore` 유지.
- 저장소를 열지 못하면 앱을 죽이지 않고 인메모리로 폴백한다.
- 로그인은 선택으로 바뀌었다. 온보딩 마지막에 "로그인 없이 시작하기"를 두고, 온보딩 완료 사실을 프로필에 남겨 재실행 시 홈으로 바로 들어간다.
- 완료 조건 검증: 여행 등록 → 종료 → 평가 후 저장 파일을 새 컨테이너로 다시 열어 여행·평가·지문·홈 국가가 그대로인지 확인하는 테스트 추가.

### 3단계 — 제휴 붙일 자리 만들기 (제휴사 없이 선행, 2~3일)

**제휴 승인을 출시 앞의 직렬 블로커로 두지 않는다.** 제휴사 ID가 없어도 만들 수 있는 것을 먼저 끝낸다.

- 여행 등록 완료 / `TripDetailView`(출발 전 예정 여행)에 액티비티 섹션 추가 — §5 표의 1순위. `TripLeg.cities`를 그대로 쓴다
- `RecommendationDetailView`에 "이 나라에서는 뭐 할까" 섹션 추가. `explanationTagIDs`로 카테고리를 거른다
- 제휴 표시 문구 노출 — 단정형·링크 카드 위·본문보다 진한 대비 (§5 "표시 문구")
- 외부 링크 열기 처리 (현재 앱 전체에 외부 링크 처리가 없음). **제휴사 앱이 유니버설 링크를 가로채지 않고 웹으로 열리는지 실기기로 검증한다**
- sub-id 조립 로직 (§5 "측정"). 제휴사 ID와 destination id는 주입 가능한 자리로만 비워둔다
- 클릭을 로컬 `AnalyticsEvent`로도 기록 — 용도는 본인 기기 검증에 한정
- 완료 조건: 제휴 ID 없이도 링크가 올바른 도시 페이지로, 웹 브라우저에서, sub-id를 달고 열린다.

### 3.5단계 — 제휴사 선정·승인·주입 (출시와 병행)

- 제휴사 1곳 선정 및 가입·승인 (§5 "아직 미확인" 항목 확인)
- 30개국 대표 도시 2~3개 + 제휴사 destination id 시드 추가 (`country_profiles_draft.csv` 경유)
- 완료 조건: 본인 기기에서 링크를 눌러 제휴사 대시보드에 클릭이 sub-id와 함께 잡히는 것을 확인한다.

### 4단계 — 공유 경로 점검 (1~2일)

**유입의 핵심.** 새로 만드는 게 아니라 이미 있는 것을 다듬는다.

- 지문 공유 카드 / 여행 공유 카드 / Wrapped 공유 카드가 실제로 저장·공유되는지 확인
- 공유 이미지에 앱 이름이 들어가는지 확인
- 개인 여행 이력이 의도치 않게 공개되지 않는지 공유 직전 확인 단계
- 완료 조건: 3종 공유 카드가 모두 실기기에서 정상 공유된다.

2026-09-23 구현·시뮬레이터 검증 완료, 실기기 최종 확인 대기:
- 지문·여행·Wrapped에 공통 이미지 미리보기와 공개 내용 확인을 연결했다. 국가 이름은 기본 숨김이며, 표시 설정을 바꾸면 확인을 다시 받는다.
- 1080×1920 공유 이미지에 TripDNA 이름을 표시한다. 정확한 여행 날짜·도시·동행인·사진은 내보내지 않는다.
- 사진첩 추가 권한을 요청해 이미지를 저장하며, 권한 거부·저장 실패 안내를 제공한다. 시스템 공유 시트에는 렌더링된 이미지만 전달한다.
- 현재 홈의 Wrapped 시즌 진입을 복원했다. 비시즌 미리보기는 개발 빌드에서만 제공한다.
- 단위·이미지 테스트 24개와 세 카드의 저장·시스템 공유 UI 테스트 3개 통과. Release 빌드 성공.
- 남은 확인: 실제 iPhone에서 3종 카드를 원하는 수신 앱으로 보내고, 저장된 이미지와 수신 이미지의 내용·해상도를 확인한다.

### 5단계 — 출시 준비 (2~3일)

- 개인정보 처리방침 (로컬 저장이라도 필요). 사진첩 접근 이유 명시
- 앱스토어 메타데이터·스크린샷·심사 대응
- 사진첩 권한 문구, 알림 권한 시점 점검
- 완료 조건: 심사 제출.

### 6단계 — 출시 후 측정 (상시)

- §6의 지표 확인. 특히 **공유율**
- 유입 경로별로 설치 → 첫 추천 도달 → 공유 → 제휴 클릭을 연결해서 봄
- 완료 조건: 6개월 내 **제휴사 확정 예약 1건** 여부 판정. 입금은 그 뒤 3~4개월 더 걸리므로 판정 기준으로 쓰지 않는다.

### 7단계 — 분기점

여기서 처음으로 다음을 논의한다. **그 전에 결정하지 않는다.**

- 공유가 되고 제휴 수익이 보인다 → 도시 확장, 후보 비교, 유료 상품 검토
- 공유는 되지만 제휴가 안 된다 → 유입 자산으로 두고 다른 수익 경로 검토
- 공유도 안 된다 → 이 방향의 유입 가설을 재검토

## 11. 하지 말아야 할 것

이 프로젝트에서 반복된 실패 패턴이다.

1. **스펙을 다시 쓰는 것.** 스펙 문서가 30개를 넘는데 커밋은 1개다. 문서를 늘리는 대신 1단계를 실행한다.
2. **출시 전에 경쟁 서비스와 비교 테스트하는 것.** §3의 결함이 남아 있으면 패배 원인을 오진한다. 1단계 이후에 한다.
3. **"사용자가 쌓이면 좋아진다"를 계획으로 삼는 것.** 여행 주기가 연 1~2회다. 데이터 축적 속도가 프로젝트 속도보다 느리다.
4. **기능을 더 만들어 차별점을 확보하려는 것.** 기술 차별점은 없다. 유통(공유)이 없어서 죽는다.
5. **되돌릴 수 없는 결정.** 구독·서버·전 세계 데이터는 모두 나중에 붙일 수 있다.
