# 계약 확인 — 실행 2 계획

2026-10-15 작성. 호출 전이다. 근거는 [실행 1 결과](../result.md)의 "다음 실험에 넣을 것" 1~3과 "실행 2를 평가하는 원칙"이다.

## 묻는 것

1. 지침 v2로 기존 사례의 조건 해석 오류(C03 유형)와 보이는 문장의 내부 표현이 줄었는가
2. 축제·경기·공연에 기대는 카드에서 정확한 날짜 확인 안내가 늘었는가
3. 새 입력(방문 포함 여부, 축제의 필수·선호 요청, C03과 같은 유형의 다른 문장)을 계약대로 다루는가

이 실험은 추천 품질을 재지 않는다. F11·F13의 유용성 부족(조건에 맞지 않을 가능성이 큰 도시가 일반 카드로 나옴)은 지침으로 풀리지 않으므로 남을 수 있다. 그 문제가 남아 있으면 위 질문에 모두 "그렇다"여도 "추천 품질이 개선됐다"고 적지 않는다.

## 실행 1에서 바꾼 것

| 항목 | 실행 1 | 실행 2 |
|---|---|---|
| 지침 | [v1](../prompt.md) | [v2](prompt.md): 바꾼 것 4가지는 그 파일 머리에 적었다 |
| 사례 | 회귀 13 + 새 계약 8 | 같은 21개 + [새 사례 6개](cases.json) |
| schema, 도시 자료, 모델·설정, 반복 | — | 바꾸지 않았다 |
| 기존 21개의 입력 | — | 바꾸지 않았다. 사용자 메시지의 해시를 고치기 전과 대조해 21개 모두 같음을 확인했다 |
| 검사기 | 내부 표현 검사 없음(실행 뒤 추가) | 내부 표현, 다녀온 곳 제외, 날짜 확인 안내(유의점의 "날짜·일정" 단어) |

검사기의 변경은 실행 1의 응답에도 그대로 적용해 기준선을 다시 셌다(아래). 지침이 같은 조건이 아니라는 점만 다르다.

## 사례

| 묶음 | 사례 | 실행 1과 비교 | 용도 |
|---|---|---|---|
| 기존 | F01~F13, C01~C08 | 한다 | 지침 v2의 효과 |
| 새 사례 | V1·V2·V3 | 하지 않는다 | 방문 포함 여부를 명시한 입력. V1·V3은 C04·C05에 포함(기본)을, V2는 C04에 제외를 넣었다. 원래 C04·C05는 비교용으로 그대로 둔다 |
| 새 사례 | E1·E2 | 하지 않는다 | 축제의 명확한 필수 요청과 선호 요청. F10의 기대는 바꾸지 않았다 |
| 새 사례 | X1 | 하지 않는다 | C03과 같은 유형("일본은 계속 빼 주세요")의 다른 문장. 지침이 C03 문장에만 맞춰졌는지 본다 |

확인용 사례(사용자 작성)는 아직 없다. 실행 1과 같다.

## 방식과 호출 수

실행 1과 같다. Flash(`gemini-3.8-flash`, 생각 수준 low) 사례당 1회, Haiku 5.5(`claude-haiku-5-5`, effort medium) 사례당 2회. 검색과 API 형식 강제 없음. 출력 상한 8,192토큰.

호출: 27사례 × (1 + 2) = 81회.

## 비용

- 실행 1 실제: 63회 US$0.16(Flash 호출당 0.0047, Haiku 0.0016). 같은 비율이면 81회에 약 US$0.21이다.
- dry-run 최대 추정(입력 문자당 2토큰, 출력 상한 전부): US$1.50. 엄밀한 상한은 아니다.
- 멈춤: 호출 직전마다 "실행 2의 기록된 지출 + 다음 호출의 최대 추정"이 US$1.50을 넘으면 멈춘다. API 오류도 기록하고 멈춘다.
- 누적: 이 기기 기록 기준 약 US$7.09. 실행 2를 더해도 첫 파일럿 상한 US$10 안이다.

## 기준선 (실행 1 응답을 지금 검사기로 다시 센 값)

문제가 있었던 응답 수다.

| 지표 | Flash | Haiku 5.5 |
|---|---|---|
| C03 조건 해석 오류(카드 표시 상태 불일치) | 1/1 | 1/2 |
| 보이는 문장의 내부 표현 | 0/21 | 22/42 |
| 날짜 확인 안내 없음(F05·F06·F10) | 3/3 | 5/6 |
| F10 표시 상태(필수·선호 해석, 판정 보류) | 1/1 | 2/2 |
| 형식 실패, 제외 위반, 조건 보고 누락, 말없이 빠짐, 검증되지 않은 탈락 | 0 | 0 |

## 판정 기준

**기존 21개 (실행 1과 비교).**

| 지표 | 개선으로 적는 조건 |
|---|---|
| C03 해석 오류 | 두 모델 모두 0 |
| 내부 표현 | Haiku가 22/42보다 줄고, Flash는 0을 유지 |
| 날짜 확인 안내 없음 | 두 모델 모두 줄어듦 |
| 위 표의 마지막 줄(0이던 오류) | 0을 유지. 하나라도 생기면 회귀 |
| F11·F13 유용성 | 판독으로 실행 1과 같은지 기록만 한다. 지침의 목표가 아니다 |

**새 사례 6개 (따로 집계).**

| 사례 | 기대 |
|---|---|
| V1·V3 | 다시 추천해도 위반이 아니다. 메모 반영(V1)과 별점만 있는 기록의 처리(V3)를 판독한다 |
| V2 | 방콕이 카드에 없다. 다녀온 곳 제외에 예외를 만들지 않는다 |
| E1 | 조건을 필수로 추출하고 카드가 "확인 필요"다. 카드마다 날짜 확인 안내가 있다 |
| E2 | 조건을 선호로 추출하고 카드가 "확인됨"이다. 카드마다 날짜 확인 안내가 있다 |
| X1 | 예외가 없고 일본 도시가 카드에 없다. "조용한 카페"만 선호 조건이고 카드는 "확인됨"이다 |

날짜 확인 안내는 유의점에 "날짜" 또는 "일정"이 있는지로만 센다. 안내가 맞는 내용인지는 판독한다.

## 실행

```
.venv/bin/python scripts/check_contract.py --exp 2 --dry-run
.venv/bin/python scripts/check_contract.py --exp 2 --run
.venv/bin/python scripts/check_contract.py --exp 2 --report
```

기록은 `run2/responses.jsonl`에 남고 저장소에 올리지 않는다. `--report`의 끝에 기존 21개의 실행 1 대 실행 2 비교와 새 사례의 집계가 따로 나온다.

## 한계

- 사례·기대·판정자가 모두 AI다. 도시 자료 20곳은 사람 검수 전이다.
- 지침 v2는 실행 1에서 본 사례를 보고 고쳤다. 기존 21개의 개선은 그 사례에 맞춘 결과일 수 있다. X1이 그 점을 일부만 확인한다.
- Flash는 사례당 1회라 흔들림을 모른다.
- 날짜 확인 안내의 자동 집계는 단어 기준이라 맞는 안내를 놓치거나 틀린 안내를 셀 수 있다.
