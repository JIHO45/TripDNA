# 계약 확인 — 실행 3 결과: 필수·선호 분류의 흔들림

2026-10-17 실행. [계획](plan.md). 지침 v2(실행 2와 같음), 여섯 사례를 Flash와 Haiku 5.5로 10회씩, 120회. 검색과 API 형식 강제 없음. 판정은 AI 1명(Claude Opus 5.5)이 `--exp 3 --report` 출력과 응답 원문을 읽고 했다. 사람 확인 전이며 잠정이다.

응답 원본은 실행한 기기의 `run3/responses.jsonl`에만 있고 저장소에 올리지 않는다.

**결론.** 필수 요청을 선호로 잘못 분류한 경우는 이번 60회의 비행시간·고도·우기 사례에서 한 번도 없었다. 그러나 E1(축제 필수)에서 Haiku가 10회 중 2회 자유문장 조건을 따로 만들지 않고 시기 조건(`period`)에 합쳤다. 그 결과 카드가 "확인됨"이 됐다. 이 두 응답은 안전장치 (a)·(b)로 고칠 수 없었다. 두 안 모두 자유문장 조건이 있어야 작동한다. 표시를 LLM의 조건 처리 하나에 맡기면 틀릴 수 있다는 실행 2의 우려는 그대로이고, 틀리는 경로는 분류 오류보다 추출 단계에서 나왔다.

## 사후 탐색 분석 (호출 뒤 추가, 계획의 판정에 소급 적용하지 않음)

**E1 Haiku의 조건 합치기.** 틀린 두 응답(6·8회차)은 조건을 빠뜨린 것이 아니라 시기 조건에 합쳤다. `period`의 `quote`에 사용자 원문 "축제 날짜에 맞는 곳만 원해요"를 넣었고, 따로 `f` 조건을 만들지 않았다. 이해 요약에는 "축제 날짜가 맞는 여행지만"을 적었고, 유의점에는 카드마다 날짜 확인을 안내했다. 시기는 코드가 시즌 자료(달)로만 판정하므로 카드가 "확인됨"이 됐다. 지침 v2에 더한 "앱 입력을 반복하는 `f` 항목을 만들지 않는다"가 이렇게 합치도록 유도했을 가능성이 있다. 가설이다.

이 경우에는 코드로 잡을 수 있는 신호가 있다. 앱 입력 조건(`period`·`duration`·`budget`)의 `quote`가 앱 값이 아니라 자유문장에서 왔으면, 사용자의 요구가 앱 입력에 합쳐진 것이다. 실행 1~3의 264개 응답에 사후로 적용하면 3건이 걸린다. 실행 3의 틀린 두 응답, 그리고 실행 2의 E1 Haiku 1회차다. 실행 2의 응답은 `period`의 `quote`에 원문을 넣으면서 `f1`(필수)도 따로 만들었다. 그래서 카드는 이미 "확인 필요"였고 표시는 바뀌지 않는다. 다른 사례에서 잘못 걸린 응답은 없었다. 문장 뜻을 판별하지 않고 문자열이 원문에 있는지만 보면 된다.

**E2의 조건 미추출.** 20회 모두 "축제가 열리면 좋겠지만 꼭 그렇지 않아도 괜찮아요"를 조건으로 뽑지 않았다. 실행 2의 F10(3/3 미추출)과 같은 양상이다. v2의 "컨셉의 반복은 조건이 아니다"가 날짜 선호까지 컨셉의 반복으로 읽게 했다는 실행 2의 가설과 맞는 결과다. 그러나 v1과 비교하지 않았으므로 확인된 것은 아니다.

**검사기 정정: 날짜 확인 안내의 오탐.** 첫 집계(정정 전 검사기)에서 Flash 4건(E1 3, E2 1의 교토)이 "날짜 안내 없음"으로 나왔다. 원문은 모두 "개최 일자를 확인"이라고 안내하고 있었다. 검사기가 "날짜·일정"만 찾았기 때문이다. 2026-10-17에 검사기의 단어 목록에 "일자"를 더했다. 응답 원본은 바꾸지 않았다. 정정한 검사기로 실행 1~3을 다시 세어 비교하니, 실행 3은 Flash 4건에서 0건이 됐고 실행 1(Flash 3, Haiku 5)과 실행 2(Flash 2, Haiku 0)는 바뀌지 않았다. 이 문서와 앞선 결과 문서의 날짜 안내 수치는 정정한 검사기로 센 값이다. 정정 전 값은 이 문단에만 남긴다.

**E1의 근거 없는 충족 판단.** Flash는 10회 모두, Haiku는 일부 응답에서 축제 조건을 `met`으로 보고했다(Flash 30건, Haiku 13건). 코드는 승인하지 않았다.

## 이 결과로 말할 수 있는 것

1. 비행시간·고도·우기의 필수 요청은 이번 문장에서 두 모델 모두 안정적으로 필수로 분류됐다(60/60). 실행 2의 F13 Haiku 오류는 드문 경우였을 수 있다.
2. 틀리는 경로는 분류보다 추출에 있다. 필수 요청을 앱 입력 조건에 합치거나(E1 Haiku 2/10), 선호 요청을 아예 뽑지 않는다(E2 20/20).
3. (a)·(b)는 추출이 빠지면 쓸 수 없다. (c)는 줄이지만 없애지 못한다(추정 약 2%).
4. 추천 품질에 관해서는 이번 실험으로 말할 것이 없다.

## 다음에 검토할 것

- **지침 v3.** 실행 2 결과와 검토에서 정한 대로 "컨셉의 반복"의 경계를 좁힌다. 컨셉에 날짜·필수 여부 같은 요구를 더하는 문장은 조건이다. 사용자의 요구는 앱 입력 조건에 합치지 말고 `f` 조건으로 둔다고 적는다. 비교 사례는 단순 컨셉 반복("축제를 즐기고 싶어요"), 날짜 선호, 날짜 필수로 나눈다. 기존 F10·E1·E2는 그대로 둔다.
- **코드 신호 후보 (d).** 앱 입력 조건의 `quote`가 자유문장에서 왔으면 위반으로 기록하고 카드를 "확인 필요"로 둔다. 실행 1~3에 사후로 모의하면 표시가 틀린 E1 Haiku의 두 응답을 잡고, 다른 사례에서는 걸리지 않는다. 실행 4의 판정 항목으로 미리 넣고 잰다.
- **선호 조건의 표시 문구.** "확인됨"을 계속 쓸지는 화면 결정이다. E2처럼 확인하지 않은 축제에 기대는 카드가 "확인됨"으로 보인다.
- **(b)와 (c).** (b)는 선호 처리의 제품 결정이 먼저 필요하다. (c)는 호출이 두 배라 (d)와 v3의 효과를 본 뒤에 다시 본다.
