# 비용 확인 단계의 시험 — 계획

2026-10-13 작성. 같은 날 실행 1(6건)을 돌렸다([결과](result.md)). 이 문서는 실행 1의 계획이며, 실행 2의 내용은 결과 문서의 끝에 있다. 실행: `scripts/run_cost_check.py`.

## 왜 하는가

[실제 메모 실행 3~5](../memo-check/run5/result.md)에서 조건 처리 문구를 두 번 고쳤지만, 비용에 관한 값이 없어 답은 "근거 없이 단정"과 "전부 확인 필요" 사이를 오갔다. 사용자가 원한 것은 허용한 범위 안에서 가능한 선택지의 설명이었고, 그러려면 값이 있어야 한다.

추천 호출은 취향으로 후보를 찾는 데까지만 맡기고, 조건은 따로 확인하는 단계를 둔다. 그 단계가 쓸 만한 값을 내는지를 먼저 본다.

지금까지의 실험에서 모델은 검색을 줘도 한 번도 쓰지 않았다. 찾을 것이 정해지지 않았기 때문으로 보고, 이번에는 무엇을 찾아 어떤 형태로 돌려줄지를 정해 준다.

## 구성

- 도시 6곳: 방콕, 타이베이, 푸껫, 싱가포르, 도쿄(실제 메모 실행에서 위쪽에 나온 후보)와 리스본(사용자가 예산상 비현실적이라고 본 도시).
- 도시마다 Gemini Flash 호출 1건, 검색 사용.
- 찾는 것: 서울(인천) 왕복 이코노미 항공료, 중심가 4성급 호텔의 1박 가격. 각각 최저와 최고를 원화로, 근거가 되는 자료의 종류와 기간, 출처 주소와 함께.
- 기억으로 답하지 말고, 찾지 못하면 값을 비우고 찾지 못했다고 적게 했다. 값을 못 얻는 것도 결과로 기록한다.
- 값마다 요청한 조건과 맞는지를 함께 받는다: 날짜가 정확히 그 날짜인지 그 달의 일반 값인지, 1명·1실 기준인지, 세금이 포함됐는지. 검색 결과에 가격이 있다는 것만으로는 부족하다(Codex 검수).
- 보고서에는 조회한 조건과 시각, 출처, 항공과 숙박의 총액, 예산에서 남는 금액, 포함하지 않은 비용을 적는다.
- 모델은 예산에 맞는지 판단하지 않는다. 코드가 항공료와 숙박비(7박, 14박)를 더해 예산과 비교한다.

지침은 [`prompt.md`](prompt.md).

## 가정

| 항목 | 값 | 누가 정했나 |
|---|---|---|
| 시기 | 2027년 1월 중순 | 사용자 |
| 숙소 | 4성급 | 사용자 |
| 예산 | 항공료 포함 300만 원 | 사용자(실행 4의 확인 질문 답) |
| 기간 | 1~2주. 7박과 14박을 각각 계산 | 사용자의 요청 |
| 인원 | 1명, 객실 1개 | 작성자의 가정. 사용자에게 확인하지 않았다 |

## 보는 것

1. 실제로 검색하는가
2. 값의 범위가 판단에 쓸 만큼 좁은가
3. 근거가 요청한 시기의 것인가, 다른 달이나 다른 해의 평균인가
4. 출처를 확인할 수 있는가. 이전 실험에서는 API가 가져온 페이지 목록을 돌려주지 않았고 모델이 적은 주소에 이미지 파일이 섞여 있었다
5. 코드의 판정이 사용자의 감각(리스본은 어렵다, 싱가포르는 1주면 된다)과 맞는가
6. 도시당 비용과 시간
7. 검색 전과 비교해 실제 선택이 쉬워졌는가. 이전 실행에서는 모든 후보에 "예산 안에 드는지 확인"이 붙었다

## 한계

- 값의 정확성은 이 실험만으로 확인되지 않는다. 출처를 열어 대조해야 하고, 몇 곳만 작성자가 따로 검색해 본다.
- 식비, 교통비, 유흥비는 계산에 없다. "항공+숙박이 예산 안"은 여행 전체가 예산 안이라는 뜻이 아니다.
- 가격은 날마다 바뀐다. 오늘 찾은 값은 오늘의 값이다.
- 도시마다 한 번 돌린다.
- 응답 원본은 Google 검색 그라운딩 결과여서 저장소에 올리지 않는다.
- 비용을 확인해도 안전에 대한 단정은 해결되지 않는다. 이 시험은 그 문제를 다루지 않는다.
