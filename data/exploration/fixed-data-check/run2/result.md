# 고정 자료 추천 확인 — 실행 2 결과

2026-10-12 실행. [계획](plan.md). Gemini Flash, 13개 사례를 검색 없음(off)과 검색 있음(on)으로 한 번씩, 26건. 판정은 AI 1명(Claude Opus 5.5)이 응답을 읽고 했다. 사람 확인 전이며 잠정이다. 방식을 고르는 판정이 아니다.

같은 날 고침(Codex 검수): 델리 판정을 '검색 방식이 맞았다'에서 '연도 미입력으로 판정 보류'로 바꿨다. '후보와 순서를 코드가 정한다'는 결론을 '코드는 후보와 기준 순서를 만들고 LLM이 바꾼 부분을 설명한다'로 좁혔다. 고정 자료로 옮기면 틀린 승인이 사라진다는 식의 서술을 고쳤다.

응답 원본은 실행한 기기에만 있다. 검색 방식의 원본은 [그라운딩 조항](../../README.md#저장소에-올리지-않는-기록-2026-10-12)의 대상이다.

## 숫자

| 항목 | 실행 1 (off) | 실행 2 off | 실행 2 on |
|---|---|---|---|
| 낸 도시 중 코드 검사가 제외 | 48곳 중 0 | 45곳 중 0 | 42곳 중 0 |
| 있어야 하는 도시가 모두 있는 사례 | 재지 않음 | 9 / 10 | 8 / 10 |
| 빈 결과 사례 | 1 / 1 | 1 / 1 | 1 / 1 |
| 조건 승인 문제(코드가 센 것) | 재지 않음 | 8건 | 2건 |
| 문장에서 등급·점수를 말한 후보 | 47곳 | 0곳 | 0곳 |
| 추정 비용 | $0.16 | $0.15 | $0.45 |
| 지연 평균 | 7.8초 | 6.7초 | 9.0초 |

검색 방식 13건 중 실제로 검색한 것은 6건(검색어 21개)이다. 검색한 호출의 지연은 9.5~16.9초였다. 호출당 입력은 약 13,500토큰이다.

코드가 센 숫자만으로는 검색 방식이 나아 보이지만, 아래처럼 응답을 읽으면 그렇게 말할 수 없다.

## 지침을 고쳐서 나아진 것 (두 방식 공통)

- **문장에서 등급이 사라졌다.** 47곳에서 0곳. 이유 문장이 핵심 경험을 풀어 쓴 형태가 됐고, "근교는 평가에 포함되지 않습니다" 같은 내부 설명도 없어졌다.
- **호놀룰루가 돌아왔다(F13).** 부 컨셉 등급이 낮다는 이유로 빼지 않았다.
- **뺀 도시와 이유가 따로 나온다.** 시즌 밖 도시를 `excluded`에 이유와 함께 적었다(F02~F06, F09).
- **자료의 사실은 그대로 지켰다.** 시즌, 등급 미달, 근교는 실행 1과 같다.

## 고쳐지지 않은 것 (두 방식 공통)

**주 컨셉 등급 순서를 따르지 않고, 이유 없이 후보를 뺀다(F07).** 지침에 "주 컨셉 등급이 높은 순, 부 컨셉은 순서에만"이라고 적었는데도 두 방식 모두 자연 3등급인 케언스와 퀸스타운을 빼고 자연 2등급인 교토·타이베이·시드니를 냈다. 이번에는 빼는 이유도 적지 않았다. 지침이 있는데 따르지 않은 것이므로 실행 1의 "지침 누락"과 다르다. 다만 지침을 어긴 것과 추천이 나쁜 것은 별개다. 등급 3은 "모든 사용자에게 2보다 먼저"라는 뜻이 아니어서, 등급 순서를 제품의 최종 규칙으로 삼을지는 따로 정할 일이다. 여기서 확인된 문제는 후보가 근거 없이 사라지고 그 사실이 드러나지 않는다는 것이다.

## 검색 없는 방식의 문제

- **말한 조건을 조용히 충족으로 처리했다(F12).** 고도를 피하고 싶다는 요청에 다섯 곳을 모두 `confirmed`로 내고, 미확인도 유의점도 비웠다. 실행 1처럼 "위험이 없습니다"라고 쓰지는 않았지만, 조건 자체를 무시했다.
- **이유 없이 후보를 뺐다(F11).** 6시간 조건에 푸껫 한 곳만 `needs_check`로 냈다. 나머지 넷은 `excluded`에도 없이 사라졌다. 확인할 근거가 없으면 `needs_check`로 남기라는 지침과 어긋난다. 기억으로 뺀 것으로 보이지만 그렇게 적지도 않았다.
- **같은 종류의 조건을 사례마다 다르게 다뤘다.** 우기(F13)는 다섯 곳 모두 `needs_check`로 지침대로 처리했고, 고도(F12)는 전부 `confirmed`, 비행시간(F11)은 한 곳만 남겼다.
- 축제 날짜(F10)의 3건은 `confirmed`지만 유의점에 날짜 확인을 적었다. 달은 자료에 있으므로 이 3건은 채점 기준이 엄격했던 쪽이다.

## 검색 방식의 문제

검색은 자료에 없는 조건에서 결과를 실제로 바꿨다. 그러나 근거를 믿을 수 있는 형태로 남기지 못했고, 틀린 승인이 하나 확인됐다.

**바뀐 것**

- F11: 다섯 곳을 모두 비행시간을 들어 빼고 빈 결과를 냈다(푸껫 6시간 20~30분, 호놀룰루 8시간 이상 등). 사례를 만들 때 예상한 것과 같다.
- F13: 푸껫을 7월 몬순을 이유로 뺐다.
- F10: 델리를 "2026년 디왈리는 11월 8일 전후"라며 뺐다. 이 제외가 맞는지는 판정을 보류한다. 여행 연도가 입력에 없는데 2026년으로 가정했고(2027년 디왈리는 10월 29일), 델리의 다른 10월 축제를 확인하지 않고 디왈리 날짜 하나로 도시를 뺐다.
- F06: 파리와 이스탄불을 "리그가 8월에 개막해 7월에는 정규 경기가 없다"며 뺐다. 자료에 시즌이 없거나 미확인이던 칸이다.

**문제**

1. **틀린 승인(F13 케이프타운).** "우기는 피하고 싶다"는 7월 요청에 케이프타운을 출처를 달아 `confirmed`로 냈다. 케이프타운은 겨울에 비가 오는 기후이고 6~8월이 가장 습한 철이다([영국 왕립기상학회 안내](https://www.rmets.org/metmatters/travellers-guide-cape-town-south-africa), 2026-10-12 검색 요약으로 확인). 실행 1의 검색 없는 응답은 오히려 "7월은 겨울철이며 비가 자주 내릴 수 있다"고 적었다.
2. **출처가 주장을 뒷받침하는지 확인할 수 없다.** API 응답에 실제로 가져온 페이지 목록이 비어 있었다. 남은 것은 모델이 `sources`에 적은 주소뿐이다. 9개 가운데 2개는 내용 페이지가 아니라 이미지 파일 주소다(F10의 멕시코시티는 관광청 사이트의 그림 파일, 교토는 사진 파일). 케이프타운의 출처 페이지는 열어 봤으나 본문을 읽지 못했다.
3. **뺀 도시에는 출처가 없다.** 출력 형식에 `excluded`의 출처 자리를 두지 않았다. F11의 비행시간 다섯 개, F06의 리그 일정은 근거 주소 없이 남았다. 형식을 만든 쪽의 잘못이다.
4. **출처 없이 승인(F12).** 시드니와 타이베이를 고도 확인 없이 `confirmed`로 냈다. 나머지 셋은 위키백과 주소를 댔다.
5. **말한 조건만 좁게 확인하고 유의점을 비웠다(F13).** "우기가 아님"만 확인하고 두바이(7월 폭염), 시드니(겨울)를 유의점 없이 `confirmed`로 냈다. 실행 1은 기억으로 이 유의점을 적었다. "확인된 것만 말하라"는 지침이 쓸모 있는 경고까지 지운 셈이다.
6. **검색을 컨셉 판정에 썼다(F06).** 지침은 말한 조건의 확인에만 쓰라고 했다. 결과는 쓸모 있었지만 지침 밖이다.

## 실패의 분류

| 분류 | off | on |
|---|---|---|
| 자료 오류 | 확인된 것 없음 | 확인된 것 없음 |
| 자료에 없음 → 확인 필요로 처리(지침대로) | F13, F11의 푸껫 | 해당 없음 |
| 자료에 없음 → 조용히 충족 처리 | F12 | F12의 2곳 |
| 자료에 없음 → 근거 없이 제외 | F11의 4곳 | F11·F06(출처 자리가 없었음) |
| 지침을 따르지 않음 | F07 순서 | F07 순서, F06 검색 용도 |
| 틀린 승인 | 확인된 것 없음 | F13 케이프타운 |
| 코드가 잡음 | 0 | 0 |

## 읽는 법과 한계

- **검색 방식이 낫다고도 못하다고도 말할 수 없다.** 조건에 어긋나는 도시를 빼는 데는 도움이 됐고, 틀린 승인 하나와 검증할 수 없는 출처를 남겼다.
- 방식마다 한 번씩 돌렸다. F13의 케이프타운 같은 오류가 얼마나 자주 나는지 모른다.
- 비행시간(F11), 리그 일정(F06), 고도(F12)의 사실은 대조하지 않았다. 대조한 것은 케이프타운의 겨울 강수 하나다.
- F10의 델리는 판정 보류다. 채점은 델리가 있어야 한다고 봤고 검색 방식은 2026년 날짜를 들어 뺐는데, 연도가 입력에 없어 어느 쪽도 옳다고 할 수 없다. "있어야 하는 도시 8/10" 가운데 하나가 이 사례다.
- 사례, 기대, 판정을 모두 AI가 만들었다. 자료 20곳은 사람 검수 전이다.

## 이 결과로 말할 수 있는 것

1. 문장 규칙과 "뺀 도시를 따로 적기"는 지침만으로 고쳐진다.
2. 순서는 지침으로 고쳐지지 않았다. 코드가 등급상 후보를 빠짐없이 준비하고 기준 순서를 만든 뒤, LLM이 지난 경험이나 이번 요청에 따라 바꾼 부분을 설명하는 구성을 시험할 근거가 생겼다. 순서를 코드로 고정하면 누락은 막지만 개인화도 막는다.
3. 조건 확인을 LLM의 `confirmed` 표시에 맡길 수 없다. 검색을 켜도 틀린 승인이 나왔고, 꺼도 조건을 조용히 통과시켰다. 판정에는 표시가 아니라 근거가 되는 값과 출처가 필요하다. 그 값을 고정 자료에 두어도 값이 틀리면 똑같이 잘못 승인된다. 코드가 보장하는 것은 비교의 일관성이지 사실의 정확성이 아니다. 비행시간이면 출발지·직항 여부·소요시간·적용 시점·출처가, 기후면 강수량과 함께 "어느 정도가 피하려는 우기인가"의 기준이 따로 있어야 한다.
4. 검색은 자료에 없는 것을 찾아 주었다(디왈리 날짜, 리그 휴식기). 이번 구성은 출처를 추적할 수 없어 승인 근거로 부족했다. 검색이 부적합하다는 결론은 아니다. 취향에 따른 선택과 사실 조건의 검증을 나눠야 한다는 쪽에 가깝다.

## 정할 것

다음 순서(Codex 권고, 20곳 유지):

1. 코드가 등급상 후보와 기준 순서를 준비한다.
2. [지난 여행 메모 비교](../../memo-check/plan.md): 같은 요청에서 메모만 바꿔 순서가 타당하게 달라지는지 본다. 두 실행 모두 메모를 넣지 않아 개인화는 아직 확인하지 못했다.
3. 조건 확인을 따로 다룬다. 검색 결과의 값과 출처를 남기고, 확인하지 못한 필수 조건은 승인하지 않는다.

비행·기후 자료 제작과 100곳 확대는 그 뒤에 정한다. 남은 결정:

- 검색을 쓴다면 무엇을 근거로 인정할지. 지금 형식으로는 출처를 검증할 수 없다
- 여행 연도를 입력으로 받을지. 달만으로는 해마다 날짜가 바뀌는 축제를 판정할 수 없다
