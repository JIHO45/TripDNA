# 실제 여행 메모 — 실행 6 계획: 예상 비용의 범위

2026-10-13 작성. 아직 호출하지 않았다. 실행: `scripts/run_real_memo.py`(기본이 실행 6).

## 왜 하는가

사용자가 예산의 처리를 정했다([설계 문서의 조건](../../../../docs/recommendation/README.md#조건)). 예산에 맞는지를 판정해 도시를 거르지 않고, 후보마다 예상 비용의 범위를 보여준다. 같은 도시라도 숙소와 씀씀이에 따라 비용이 달라 한 사람의 예산에 맞는지를 정확히 가릴 수 없고, 제휴사의 가격을 써도 마찬가지라는 이유다.

범위의 뜻도 정했다. 처음에는 "가장 싸게 가는 방식부터 납득할 만하게 비싼 방식까지"였다. 같은 날 좁혔다(Codex 지적, 사용자 동의): **사용자가 원하는 여행에서의 범위**다. 호캉스를 원한 사용자에게 가장 싼 숙소의 가격은 실제 선택지가 아니다. 요청에 적힌 숙박 방식과 씀씀이를 기준으로, 아래쪽은 그 여행을 아끼는 쪽으로, 위쪽은 넉넉한 쪽으로 잡는다. 위쪽에 5성급 숙소는 들어가지만 매일 비싼 와인, 바, 고급 식당은 넣지 않는다. 요청에 그런 내용이 없을 때만 처음의 넓은 범위를 쓴다.

LLM에 물으면 대개 이런 범위와 항목이 나온다는 것이 사용자의 예상이다. 그 값이 쓸 만한지를 본다.

## 구성

- 입력은 실행 3~5와 같은 실제 메모와 요청 2건이다.
- 지침은 실행 3의 기준선(P)에 예상 비용 문단과 출력 칸만 더했다. 실행 4·5의 조건 처리 문단은 넣지 않았다. 예산으로 도시를 빼거나 순서를 바꾸지 말라고 적었다.
- 모델은 도시마다 세 가지를 낮은 값과 높은 값으로 낸다: 왕복 항공, 1박 숙박, 하루 지출(식비, 현지 교통, 밤 지출).
- 모델은 낮은 값과 높은 값이 각각 무엇을 가정하는지(숙소 등급, 하루 지출에 든 것)를 함께 적고, 모든 도시에 같은 가정을 쓴다. 두 번의 값이 다를 때 가정이 달라서인지 같은 가정에서 값이 흔들린 것인지 가르기 위해서다.
- 합계는 코드가 낸다. 숙박은 박수만큼, 하루 지출은 머무는 날수(박수 + 1)만큼 곱한다. 7박과 14박의 합계 범위를 계산하고, 사용자가 적은 예산이 그 범위의 아래, 안, 위 가운데 어디인지를 적는다. 예산에 맞는다거나 넘는다고 쓰지 않는다.
- 같은 입력을 두 번 돌린다(PE, PE2).

## 보는 것

1. 범위가 사용자가 정한 뜻에 맞는가. 아래쪽이 터무니없이 싸거나 위쪽이 사치스럽지 않은가
2. 사용자의 감각과 맞는가. 사용자는 싱가포르를 비싸다고, 리스본을 예산상 어렵다고, 푸껫을 넉넉하다고 봤다
3. 두 번의 값이 얼마나 다른가. 같은 도시가 두 번 다 나왔을 때 가정이 같은지부터 본다. 가정이 다르면 숫자의 차이를 흔들림으로 세지 않는다
4. 도시 사이의 차이가 드러나는가. 모든 도시가 비슷한 범위로 나오면 고르는 데 도움이 되지 않는다
5. 비용 때문에 도시를 빼거나 순서를 바꾸지 않았는가
6. 범위가 너무 넓어 쓸모가 없지 않은가

## 평가

방식 비교가 아니므로 가린 시트를 쓰지 않는다. `--report`로 두 번의 결과를 나란히 본다.

읽는 법(Codex 검수):

- 두 번이 비슷하게 나와도 정확하다는 증거가 아니다.
- 사용자의 인상(싱가포르는 비싸다, 푸껫은 넉넉하다)은 견주어 볼 의견이지 정답이 아니다.
- 범위의 양 끝도 가격에 관한 주장이다. "예상"이라고 적어도 모델이 임의로 만든 값이면 판단을 잘못 이끌 수 있다.
- 결과가 안정적이어도 바로 화면에 보여줄 자료로 삼지 않는다. 다음에 일부 항목이라도 실제 가격과 대조해, 일관되게 나오는 숫자가 결정에 쓸 만한 숫자인지 본다.

## 한계

- 값은 모델의 지식이다. 검색도 가격 자료도 쓰지 않는다.
- 사용자의 예산은 항공료 포함 300만 원, 1명으로 두었다. 1명은 작성자의 가정이다.
- 한 사람, 요청 2건, 두 번이다.
- 안전에 대한 단정, 휴양 요청의 도쿄 같은 앞선 문제는 이 실행에서 다루지 않는다.
