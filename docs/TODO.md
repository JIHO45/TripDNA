# 도시·LLM 추천 전환 체크리스트

기준일: 2026-10-06. 제품 범위는 [루트 README](../README.md), 동작 계약은 [추천 설계](recommendation/architecture.md)를 따른다.
이 문서는 **실행 순서와 완료 여부**를 관리한다. 설계 변경은 기준 문서에도 반영한다.

## 현재 위치와 체크 방법

- [x] 사용자 선호·이번 여행 조건·도시 사실·제외를 분리하는 방향과 기억 정책을 문서화했다.
- [x] 옛 국가 축 편집 자료·생성 도구·튜닝 지침을 제거하고 문서를 `docs/`로 정리했다.
- [ ] 아래 데이터 제작·실험·앱 전환 작업을 완료한다. **설계 문서가 있다는 이유로 구현 항목을 체크하지 않는다.**

현재 앱은 국가·5축 추천과 로컬 저장을 사용한다. [번들 로딩 코드](../TripDNA/App/AppDependencies.swift)와 [기존 도메인](../TripDNA/Domain/DomainModels.swift)에서 확인했다. 도시·LLM 전환의 완료 증거는 아직 없다. 기존 기능도 새 구조와 연결한 검증 전에는 아래 항목을 완료 처리하지 않는다.

각 항목은 완료 기준을 충족한 뒤 체크하고, 해당 줄에 **완료일·산출물 경로·검증 결과**를 덧붙인다. 산출물 경로는 실제 파일이 생긴 뒤 연결한다. 막힌 항목에는 원인과 필요한 결정을 남긴다. 일정·검사 결과를 추정해서 채우지 않는다.

현재 작업에 필요한 정책 선택은 완료했다. [확정한 결정과 남은 확인](#확정한-결정과-남은-확인)을 따르며 이미 답한 정책을 다시 묻지 않는다. **B1·D1·D2 완료, D3 사람 검수·자료 확대 중단, 탐색 실험 준비 중**이다. 푸껫의 앱 추천 단위를 본섬 지역으로 정하고 사실 자료 초안을 작성했다. 푸껫은 파일럿 20곳 중 첫 실제 자료이자 조사·검수 절차를 확인하는 사례다. 현재 도쿄·밴쿠버까지 3곳의 초안이 있으며 모두 사람 검수 전이다. 푸껫만으로 전체 도시 형식이나 추천 품질을 검증하지 않으며, 가상 형식 예제인 `example.json`과도 구분한다. 사람 검수는 아직 완료하지 않았다.

## 1. 자료와 사용자 입력 형식

2026-10-06 이후에는 [목록 대 프로필 탐색 실험](evaluation/profile-exploration.md)이 먼저다. 아래 D3 정의는 기존 계약으로 보존하며 실험 결과 뒤 개편한다. 기존 39개 주장과 검수 준비 문서는 참고 자료이고 지금 사용자에게 전수 검수를 요구하지 않는다.

선행 조건 없음. 이 단계는 앱 변경·운영 서버·유료 API 없이 진행할 수 있다.

- [x] **D1 — 도시 자료 형식을 실제 파일로 만든다.** 도시 ID·별칭·나라·적용 지역, 경험·장소, 계절/이동/예약 제약, 비용의 시점·범위, 주장별 출처 URL·근거 ID·확인일·검수 상태·버전을 정의했다. 종류별 3·6·12개월 재확인과 만료 근거 보류, 미상·미검수 구분, 요약에서 원문까지의 추적을 명시했다. **2026-09-30:** [파일 형식](data/city-format.md), [가상 JSON 예제](../data/cities/example.json). [저장된 예제 검사](../scripts/check_city_example.py)를 `python3 scripts/check_city_example.py`로 실행해 JSON 구조·7개 주장·10개 근거 참조·분류 ID·이동 값·검수 메타데이터·비용 범위·월말/윤년 재확인일·만료 및 보류 요약 제외를 확인했다. v2 형식에는 고정 분류 ID·선택 이동 필드·KST 기준일을 반영했다. 실제 도시 사실의 검수는 D3, 실행 로더·검증기는 E1·E2로 남아 있다. 기준: [도시 자료 계약](data/storage-and-privacy.md).
- [x] **D2 — 후보 도시 목록과 선정 이유를 작성한다.** 주요 도시 약 100곳의 후보 목록과 그중 자료 형식을 확인할 15~20곳을 고른다. 초기 후보는 도시 중심으로, 자연 여행 거점 도시를 최소 4곳 포함한다. 핵심 경험의 실제 이동·체험 시간으로 당일 왕복이 어려운 후보는 파일럿 전에 별도 지역 단위를 검토한다. 지역 편중·비슷한 대도시 중복을 점검한다. 목록은 사용자와 확정하며 출처 없는 ‘세계 인기 순위’로 부르지 않는다. 첫 공개 범위 확정과는 별개다.
  **2026-10-04 완료:** 사용자의 D3 착수 지시에 따라 [선정안](data/destination-selection.md)과 [목록 v3](../data/planning/destination-candidates.json)의 원본 100곳·잠정 보충 3곳·파일럿 20곳으로 진행한다. [목록 검사](../scripts/check_destination_candidates.py)의 일반/최적화 실행으로 순위 1~100·파일럿·링크·권역 일치를 확인했다. 푸껫의 원본 집계 범위는 미확인이며 앱 범위만 따로 정했다. 자료 검수는 D3에 남아 있다.
- [ ] **D3 — 먼저 15~20곳의 자료를 작성·검수한다.** 주장마다 출처와 적용 범위를 확인하고 요약과 원자료가 일치하는지 검토한다. LLM 초안이나 옛 국가 숫자를 검수 완료 자료로 취급하지 않는다. 우선 사용자 본인의 자체 검수로 시작하고, 지인 독립 검수자는 확보 후 투입한다. 검수 종류(자체/독립)·검수자·자료 버전·확인일·수정 사항·보류 이유를 남기고, 추천에 쓸 수 있는 자료와 부족한 자료를 구분하면 완료.
  **2026-10-04 진행:** [푸껫 범위 결정](data/destination-selection.md#d3-첫-자료-푸껫의-추천-단위), [실제 자료 초안](../data/cities/th-phuket-island.json), [카탈로그 무결성 검사](../scripts/check_city_catalog.py). 본섬 지역 단위로 선택했으며 data_version 2 기준 4개 출처 기반 주장(올드타운 본섬 위치 포함)과 5개 미상 질문을 기록했다. 도시 주장의 출처는 도시 파일에만 두고 D2 파일에는 범위 결정 근거만 남긴다. 검사는 개수를 고정하지 않고 참조·미상·이동 값·검수 기록 형식·D2 연결을 확인하며, 검수자가 실제로 검수했는지는 증명하지 않는다. LLM 응답·제외·조건 검증은 E2에서 별도로 만든다. 사람이 검수한 주장은 0개이므로 D3는 미완료다.
  **2026-10-05 진행:** 푸껫 `data_version 3`에 운영사 공식 노선·편도 운임·차내 결제, 태국관광청의 몬순·빨간 깃발 안내를 보강했다. 출처가 있는 미검수 주장 11개, 미상 질문 5개, 사람 검수 0개다. 노선 존재와 실제 왕복 소요 시간, 계절 특성과 당일 수영 가능, 차내 결제와 예약 불필요를 분리했다. 2018년 계절 안내는 일반 안내로만 기록하며 최신 현장 상태로 취급하지 않는다. 예약·입장 조건과 시설별 비용은 확인하지 못해 미상으로 유지했다.

[도쿄](../data/cities/jp-tokyo.json) v2(미검수 8·미상 4), [밴쿠버](../data/cities/ca-vancouver.json) v2(미검수 6·미상 5), 푸껫 v4(미검수 11·미상 5)를 저장했다. 사람 검수는 모두 0개다. 목록 v4는 도시 자료 ID 연결만 추가했고 후보 20곳은 유지했다. **다음 단계 진입 기준:** D1·D4·D6으로 도구를 만들 수 있다. 자료 형식의 적합성은 D3에서 확인하며, 실제 사용자 선택 품질 비교는 검수된 자료를 사용한다. 별도 탐색 실험에는 초안·합성 사례를 허용하되 E7 결과로 사용하지 않는다.

### 병행: 현행 앱의 잘못된 추론 수정

- [x] **B1 — 기존 국가 추천의 근거 없는 취향·확신 갱신을 막는다.** 비교 답·여가 방문만으로 모든 축의 확신이 오르는 경로, 국가 값을 여행 벡터의 출발점으로 쓰거나 `visitPriorGainFloor`로 방문만 반영하는 경로, 저장으로 국가 `tasteCore` 쪽으로 이동하는 경로를 제거했다. 직접 선택한 긍정 태그의 명시적 축만 반영한다. 일본·미국·캐나다 방문·비교·저장만으로 취향/확신이 변하지 않는 회귀 검사를 통과했다. **2026-09-30:** [재생 코드](../TripDNA/Application/UTVReplayService.swift), [회귀 검사](../TripDNATests/TasteEvidenceTests.swift). iOS 18.6 시뮬레이터에서 `TripDNATests` 전체 통과. 현행 앱 출시 여부는 도시·LLM 평가 뒤 결정한다.

## 2. PC 비교 도구와 파일럿

도구 제작은 자료 검수와 병행한다. 이 단계에서 출시 앱·집계 서버를 먼저 만들지 않는다. 기준: [비교 실험](evaluation/offline-evaluation.md).

- [ ] **E1 — 같은 입력을 받는 실행 도구를 만든다.** 사용자 사례·도시 자료를 읽어 단순 규칙과 LLM 후보를 실행하고 결과를 파일로 남긴다. 단순 규칙에는 관심 경험을 사용하는 기준선을 포함하며 정교한 새 산식 프로젝트로 확대하지 않는다. 인기순은 동일 후보 범위의 검증 가능한 출처가 있을 때만 추가하고, 불가능하면 누락 이유를 기록한다. 외부 호출 없이 입력·기록·오류 경로를 확인할 수 있으면 도구의 기본 부분 완료.
- [ ] **E2 — 실험 요청·응답 형식과 검증기를 만든다.** 추천, 자유문장 피드백 해석, 상세 답변을 구분하되 공통 실행 코드를 재사용한다. 도시/근거 ID, 중복, 제외, 검수 상태, 판정 가능한 필수 조건과 입력 버전을 검증한다. 잘못된 출력이 성공 결과에 섞이지 않는 실행 검사가 있으면 완료. 문장의 근거 적합성은 사람 검수도 필요하다.
- [ ] **E3 — 모델 후보와 실험 예산을 정한다.** 실행 시점 공식 자료로 고품질·저가 후보의 모델 ID, 단가, 데이터 보관 설정을 확인한다. 입력/출력·반복·재시도·상세 질문을 포함한 예상 호출량을 작성한다. **첫 외부 LLM 파일럿의 총지출 상한은 US$10**이며 호출 전에 실제 사용량과 잔여 한도를 확인한다. 출시 모델·운영 예산은 별도 결정한다.
  **2026-10-06 진행:** 탐색 실험 모델을 Claude Haiku 4.5로 고정했다([계획 v3](evaluation/profile-exploration.md#모델과-실행-설정)). 이후 같은 프로필로 Gemini Flash와 비교하며, 상위 모델은 두 소형 모델이 부족할 때 추가한다. 운영 모델·데이터 보관 설정 확인·호출 비용 계산은 남아 있다.
- [ ] **E4 — 평가 사례를 확보하고 분리한다.** 합성 사례로 오류를 찾고, 실제 사용자 10~20명 규모의 파일럿 참여자는 모집한다. 현재 참여자·독립 검수자는 확보되지 않았다. 외부 전송 범위를 안내하고 동의를 받아 필요한 정보만 사용한다. 프롬프트 개발용과 확대 관문·최종 평가용을 사용자 단위로 구분한다. 확보한 인원·검수 종류(자체/독립)를 결과에 남기고, 표본이 부족하면 결론의 한계를 명시한다.
- [ ] **E5 — 작은 파일럿으로 평가 절차를 검증한다.** 검수된 초기 도시 자료를 사용해 설명·모델 이름을 숨긴 후보 평가를 먼저 하고 설명 검수는 나중에 한다. 반복 실행, 후보 순서 변경, 조건 변경을 구분해 시험한다. 실패·검증 탈락·재시도도 로그와 비용에 포함하고, 실제 실행 결과와 발견 오류를 남기면 완료. 여기서 100곳의 품질이나 경쟁 우위를 승인하지 않는다.
- [ ] **E6 — 최종 평가 기준을 먼저 고정한다.** 파일럿 뒤 후보 적합성 개선, 근거 오류·제외 위반, 비용·지연의 판정 방법과 허용 기준, 최종 사례 수를 사용자와 확정한다. 최종 결과를 보기 전에 버전과 날짜를 남긴다. ‘설명이 그럴듯함’과 ‘선택이 좋아짐’을 별도 채점하면 완료.
- [ ] **E7 — 100곳 확대 관문을 판정한다.** [비교 실험의 확대 관문](evaluation/offline-evaluation.md#100곳-확대-관문)을 단일 기준으로 적용한다. 사용자 단위 결과·검수 종류·실패/차단 오류·비용과 확대/재시험/보류 판단을 남기면 완료. 최소 인원·대표 사례 방식은 사용자 답변으로 확정했으며 실제 참여자 확보는 E4에서 확인한다.

**다음 단계 진입 기준:** 파일럿 오류를 수정하고 E7에서 확대를 결정하며 E6의 최종 기준을 고정한다. 외부 호출은 E3, 실제 개인정보 사용은 E4의 전송 조건을 먼저 충족해야 한다.

## 3. 목표 100곳 검증과 도입 결정

- [ ] **V1 — 검수 카탈로그를 목표 100곳으로 확대한다.** E7에서 확대 결정 후 D3의 형식으로 출처·요약·제약·재확인 기한을 검수하고 자료 버전을 고정한다. 기한 지난 주장은 근거에서 보류하고 관련 필수 조건은 충족 미확인으로 처리한다. 미검수 후보를 제외하고 실제 검수 수를 기록한다. 100곳 미달 결과를 100곳 검증 완료로 보고하지 않는다.
- [ ] **V2 — 동일 조건의 최종 모델 비교를 실행한다.** E6에서 분리한 평가 사례에 동일한 도시 자료·사용자 정보·조건을 적용한다. 선택 품질, 설명, 일관성, 토큰·비용·지연·실패와 사용자별 결과 차이를 보고한다. 100곳의 요약 전달로 누락이나 비용 문제가 생기는지 확인하고, 후보 축소는 필요가 측정될 때 검토한다.
- [ ] **V3 — 기존 앱 대비 변화를 별도로 확인한다.** B1 전후 기준선의 Git 커밋·번들 해시와 남은 추론 오류를 고정한다. 기존에 수정된 싫어요 처리 등을 중복 보정하지 않는다. 새 도시 추천과 비교할 때 입력량·추천 단위 차이를 명시한다. 이 비교를 LLM 자체 효과의 증거와 섞지 않으면 완료.
- [ ] **V4 — 채택·보류와 출시 순서를 결정한다.** 결과에 따라 추천 선택까지 LLM으로 전환할지 결정한다. 설명만 개선되었으면 선택 모델 교체 근거가 부족하다고 기록한다. 채택 시 모델·첫 공개 도시 범위·운영 비용 상한·현재 버전 선출시 여부를 사용자와 확정한다. 미달이면 원인을 자료/질문/모델로 나눠 필요한 실험만 다시 한다.

**앱 전환 진입 기준:** V4에서 채택과 범위를 결정한다. 실험 도구 완성이나 LLM 응답 성공만으로 넘어가지 않는다.

## 4. 채택 후 저장 구조·서버 구현

저장과 서버 구현은 계약이 맞으면 병행할 수 있다. 사용자 기록은 로컬 저장을 유지한다. 도시 자료의 운영 배포·갱신·캐시 방식과 서버 DB 필요 여부·제품 선택은 이 단계에서 구현 전에 결정한다. 현재 JSON 카탈로그로 실험하며 Firebase 제외 범위는 유지한다. 기준: [직접 증거와 이관](recommendation/preference-evidence.md), [저장·전송 경계](data/storage-and-privacy.md).

- [ ] **I1 — 사용자 로컬 저장과 도시 자료 로딩을 구현한다.** 직접 증거/출처/철회, 이번 여행 ID/조건, 확인된 방문 도시, 범위별 제외, 북마크, 버전별 추천·근거를 저장한다. 재시작 뒤 복원과 저장 실패 처리를 확인한다. 도시 자료는 결정한 배포 방식으로 로딩하고 자료 버전·근거 검수·만료를 확인하면 완료. 원문을 요약 캐시로 대체하지 않는다.
- [ ] **I2 — 기존 기록을 이관한다.** 여행·평가·명확한 원문 답변·북마크·나라 제외·기존 기한을 보존한다. 도시 미확인은 미확인으로 남기고 파생 5축을 새 선호로 복사하지 않는다. 반복 이관의 중복 방지와 실패 시 원본 보존을 검사하면 완료. 기존 국가 북마크를 임의 도시로 바꾸지 않는다.
- [ ] **I3 — 모델 호출 서버와 전송 정책을 구현한다.** 키 보호, 요청 크기/형식 검증, 인증·남용 방지, 시간 제한·재시도, 사용자별/전체 지출 제한을 구현한다. 원본 사진·EXIF·불필요 식별자가 전송되지 않는지 확인한다. 제공자/서버 로그 보관·삭제 범위와 사용자 안내를 확정하고 실제 동작을 검증하면 완료. 전체 사용자 집계는 포함하지 않는다.
- [ ] **I4 — 추천·기억 반영 경계를 연결한다.** 서버 출력 검증 후 앱에서도 최신 입력·제외를 재확인한다. 명시 버튼은 직접 처리하고 자유문장만 해석한다. 저장 성공 뒤 안내·되돌리기를 제공하며 모호한 범위는 확인한다. 모델 출력으로 임의 DB 수정을 실행할 수 없으면 완료.
- [ ] **I5 — 캐시·동시 변경·실패를 구현한다.** 취향/조건/제외/자료/모델/프롬프트 버전 변경 시 관련 결과를 무효화한다. 늦은 응답을 폐기하고, 오프라인·후보 부족·한도 초과 시 유효 캐시 또는 정확한 실패 상태를 보여준다. 재추천 실패로 저장된 제외가 취소되지 않고, 탭 재진입만으로 불필요한 호출이 생기지 않으면 완료.
- [ ] **I6 — 실제 노출·반응 계측을 연결한다.** 도시·표시 순서·당시 입력과 모델/자료 버전·반응·비용·실패를 [계측 계약](evaluation/metrics.md)에 맞춰 남긴다. 미노출 후보를 부정 반응으로 세지 않고, 실험 로그와 기존 국가 모델 기록을 새 성과에 무표시로 합치지 않으면 완료.

## 5. 사용자 화면과 지문 전환

선행 조건: V4의 범위 결정. 화면 초안은 저장·서버 구현과 병행하되 완료는 실제 저장·요청 연결 후 판정한다. 기준: [화면별 스펙](screens/README.md).

- [ ] **U1 — 온보딩·여행 등록·평가를 전환한다.** 사진 등록 뒤 직접 선호 입력을 제공하고 도시 확인·미상·건너뛰기를 보존한다. 평가 이유와 재방문 의향의 범위를 구분한다. D5의 문항을 실제 입력 부담과 정보 효과로 검토해 최종 문구·화면을 정하면 완료.
- [ ] **U2 — 추천 탭을 도시 중심으로 연결한다.** 저장된 취향으로 첫 추천, 선택 여행 조건, 방문 도시 허용/새로운 곳만 보기, 북마크, 다른 후보 보기, 제외·재추천을 구현한다. 카드의 주 행동은 ‘추천에서 계속 제외’로 명시하고 안내·되돌리기를 제공한다. ‘이번 여행에서 제외’와 ‘다른 후보 보기’는 메뉴에 둔다. 최대 3개 카드와 카드 교체 방식은 기본안임을 확인하고 최종 화면에서 정한다. 정보 부족·조건 미확인을 정확히 표시하면 완료.
- [ ] **U3 — 도시 상세·추가 질문을 연결한다.** 검수 DB 정보는 바로 보여주고 개인화 설명을 생성·재사용한다. 근거와 유의점을 표시하고 자료에 없는 답은 미확인으로 처리한다. 최신 정보는 검수된 공식 링크로 안내하며, 열람·질문이 취향이나 제외를 자동 변경하지 않으면 완료.
- [ ] **U4 — 기억·제외 관리와 새 여행 시작을 연결한다.** 기억의 원문·범위·출처·수정/삭제와 제외 해제를 제공한다. 이번 여행 제외는 재시작 후 유지되고 새 여행에서 초기화되며, 계속 제외는 유지되어야 한다. 나라 제외 해제가 별도의 도시 제외를 지우지 않으면 완료.
- [ ] **U5 — 지문·홈·Wrapped·공유를 새 증거에 연결한다.** 지문 표현을 사용자와 정하고 직접 증거로 설명할 수 있는 요약을 표시한다. 옛 레이더 값을 새 의미로 바꿔 재사용하지 않는다. 철회된 취향이 공유·요약에서 되살아나지 않고 기존 공개 범위·미리보기를 지키면 완료. 하루 한 장과 여행 기록 기능도 회귀 확인한다.
- [ ] **U6 — 옛 추천 경로를 제거한다.** 홈·온보딩·추천·상세·공유의 호출부와 새 저장 이관이 검증된 뒤 국가 벡터 추천·점수 표시·불필요한 번들 의존을 제거한다. 역사 기록 해석에 필요한 타입까지 무조건 지우지 않는다. 기존 데이터 복원과 새 추천 실행이 모두 통과하면 완료.

## 6. 출시 검사와 병행 업무

- [ ] **R1 — 필수 시나리오 전체를 앱에서 검증한다.** D6의 16개 시나리오를 저장·재시작·네트워크 실패까지 포함해 실행하고 결과를 남긴다. 핵심 로직은 자동 검사, 화면/권한/공유는 필요한 UI·실기기 검사로 확인한다. 모델의 설명으로 코드 검사를 대신하지 않는다.
- [ ] **R2 — 출시할 빌드의 회귀 검사를 실행한다.** `TripDNA` 빌드, 관련 `TripDNATests`·`TripDNAUITests`, 실제 기기 데이터 유지·삭제·공유를 확인한다. 실행하지 못한 검사는 이유와 남은 항목을 기록한다. 과거 테스트 통과를 새 빌드 결과로 복사하지 않는다.
- [ ] **R3 — 운영·심사 준비를 완료한다.** 선택 모델의 실제 운영 비용, 한도 도달·장애 대응, 전송 안내·보관/삭제, 개인정보 처리방침·권한 문구·프라이버시 선언·아이콘·설치 URL·제출 자료를 확인한다. 출시 시점 공식 요건을 다시 검토하고 최종 제출 범위를 사용자와 정한다.
- [ ] **R4 — 제휴 경로를 별도로 검증한다.** 승인·계약 조건을 확인하고 도시 ID와 제휴 목적지, 표시 문구, sub-id, 실기기 링크 귀속을 점검한다. 수수료/제휴 유무가 후보 선택에 영향을 주지 않아야 한다. 기존 구현의 존재와 공개 가능한 제휴 설정을 구분하며 승인 대기를 추천 실험의 선행 조건으로 두지 않는다.
- [ ] **R5 — 출시 후 관측을 시작한다.** 추천 적합성·근거/제외 오류·기억 수정·첫 추천 도달·공유·재사용·제휴 확정 예약을 확인한다. 수집 경로가 없는 전 사용자 수치를 측정 중이라고 보고하지 않는다. 상세 열람·저장을 만족도의 정답으로 쓰지 않는다.

## 7. 출시 후 별도 결정: 사용자 집계로 개선

- [ ] **A1 — 집계의 목적과 수집 범위를 정한다.** 도시 사실 검수와 ‘어떤 선호·조건에서 만족했는가’ 학습을 분리한다. 동의·보관·철회·삭제·접근 통제를 정하며 과거 로컬 기록을 자동 업로드하지 않는다.
