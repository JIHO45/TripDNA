# 제휴 정책

상태: 구현 목표. 수익모델에서 제휴가 차지하는 위치는 [루트 README](../README.md#목표)를 따른다. 아래 2026-09-15 조사 내용은 당시 참고 기록이며 그 뒤 단가·법규·제공자 조건을 재검증하지 않았다. 공개 전에 공식 자료와 실제 귀속을 다시 확인한다.

### 원칙 (변경 불가)

1. **제휴 수수료 유무는 취향 적합도 산정에 절대 사용하지 않는다.** 추천은 제휴와 독립적으로 계산한다.
   영향의 방향은 한쪽으로만 흐른다. **제휴 → 랭킹은 금지. 랭킹 → 제휴 링크 선택은 허용.**
   즉 추천에서 선택한 경험과 검증된 도시 근거로 액티비티를 연결할 수 있다.
2. **제휴 관계를 화면에 표시한다.** 표시 방법은 아래 "표시 문구" 항에서 확정한다.
3. **클릭은 매출이 아니다.** 외부 링크 클릭과 예약 완료·정산을 구분해서 본다. 구현 방식은 아래 "측정" 항에서 확정한다.
4. 무료 단계에서 **"왜 추천했는지"와 "안 맞을 수 있는 점"은 반드시 보여준다.** 판단에 필요한 정보를 수익 목적으로 가리지 않는다.

### 붙일 위치: 여행 상세가 1순위, 추천 상세가 2순위

액티비티 예약은 **나라를 고르는 시점이 아니라 항공·숙소를 확정한 뒤**에 일어난다. 쿠키 윈도우는 GetYourGuide 31일, Klook 30일(호텔 7일)이라 "어느 나라 갈까" 단계의 클릭은 실제 예약까지 대부분 살아남지 못한다. 제품 목표에서 "국가 추천 단계는 구조적으로 수익 구간이 아님"이라고 적은 것과 같은 이유다.

| 순위 | 위치 | 역할 | 쓰는 도시 |
|---|---|---|---|
| **1** | 여행 등록 완료 / `TripDetailView` (출발 전 예정 여행) | **전환.** 확정 예약 1건은 여기서 나온다 | `TripLeg.cities` — 사용자가 직접 입력한 실제 도시. 시드 불필요 |
| 2 | `RecommendationDetailView` 액티비티 섹션 | 탐색·노출 | 새 구조에서는 추천 도시 ID와 검증된 제휴 목적지 연결 |

추천 상세의 섹션 구성:

```
왜 추천하나요
현실 적합
알아둘 점
이 도시에서는 뭐 할까   ← 새 구조. 추천 도시의 액티비티 제휴 링크
```

앞 3개 섹션은 전부 "당신의 취향" 이야기인데 네 번째만 일반 관광 정보면 톤이 끊겨 광고 블록으로 읽힌다. **선택된 도시·경험과 맞는 검증된 액티비티를 연결한다.** ("음식 탐방을 원해서 — 오사카 푸드 투어")

### 표시 문구

「추천·보증 등에 관한 표시·광고 심사지침」 2024-12-01 개정에서 **"수수료를 지급받을 수 있음" 같은 조건부·불확정 표현은 명확한 표시문구가 아닌 것으로 분류**됐고, 매출 실적에 따라 나중에 대가를 받는 경우(= 제휴 링크)도 공개 의무 대상임이 명시됐다.

- 문구는 **단정형.** "이 링크로 예약하면 TripDNA가 수수료를 **제공받습니다**."
- 위치는 추천 내용과 **근접하게, 링크 카드 위에.** 접기·더보기 뒤에 두지 않는다.
- 지침은 본문보다 크게 하거나 색을 달리해 쉽게 인식되게 하라고 한다. **`Color.dnaSlate` 캡션은 본문보다 흐리므로 그대로 쓰지 않는다.**

> 이 지침의 세부 조항은 블로그·카페 등 문자 매체 기준으로 쓰여 있고 앱 화면에 어느 조항이 그대로 준용되는지는 미확인이다. 위 세 가지(근접·단정형·충분한 대비)는 어느 해석에서도 안전한 선이므로 그 선을 지킨다.

### 측정: sub-id로 한다

`AnalyticsEvent`는 SwiftData 로컬에만 쌓인다. 현행 앱에는 이벤트 집계 서버가 없으므로 **다른 기기에서 일어난 클릭을 이 로컬 기록으로 관측할 수 없다.** 로컬 이벤트의 용도는 본인 기기 검증뿐이다.

제휴 측정은 **링크의 sub-id에 맥락을 인코딩하고 제휴사 대시보드에서 역으로 읽는 방식**을 채택한다. 향후 LLM 호출 서버를 도입해도 이벤트 집계를 자동 추가하지 않는다.

```
subid = <진입지점>_<표시위치 또는 D-day>_<도시ID>
예시 형식: rec_1_jp_osaka / trip_d14_jp_osaka
```

제휴사가 지원하는 필드 길이·형식을 확인한 뒤 적용한다. 사용자 식별자·취향 원문은 넣지 않는다. 클릭 수와 확정 예약을 진입 지점·표시 위치·도시별로 확인하며, 이 문서의 제휴 지표는 이 경로를 사용한다.

### 필요한 데이터: 추천 도시와 제휴 목적지 연결

추천한 도시 ID와 검증된 제휴 목적지 ID를 연결한다. 제휴 목적지가 없다는 이유로 추천 후보를 제외하지 않는다.

- 제휴 ID·링크는 도시의 경험 사실과 구분한다. 모델의 후보 선택에 수수료나 제휴 유무를 넣지 않는다.
- 기존 국가 CSV에 대표 도시를 끼워 넣어 새 도시 추천 DB를 대신하지 않는다.
- 여행 상세는 사용자가 실제 등록한 도시를, 추천 상세는 선택된 도시를 기준으로 연결한다.
- 도시 이름이 모호하거나 제휴 목적지를 확인하지 못한 경우 잘못된 도시 링크를 만들지 않는다.

여기서 따라 나오는 두 가지 제약:

1. **외부 링크 열기는 한 줄 작업이 아니다.** 유저 폰에 제휴사 앱이 깔려 있으면 유니버설 링크가 앱을 열고 그 순간 귀속이 사라진다. `SFSafariViewController`도 iOS 11부터 앱별로 분리된 쿠키 저장소를 쓰므로, 거기서 만든 쿠키는 사용자가 나중에 Safari로 예약할 때 따라가지 않는다. **제휴사 앱이 가로채지 않고 웹으로 열리는 방법을 제휴사별로 확인하고 실기기로 검증한다.**
2. **제휴 승인을 추천 개발의 직렬 블로커로 두지 않는다.** 출시 준비에서 링크 자리·표시 문구·sub-id 구조를 준비하고, 승인된 제휴 ID와 목적지를 확인한 뒤 공개한다.
