# 저장·전송·도시 자료의 경계

2026-10-23 변경(사용자 결정): [iCloud 백업](#icloud-백업)을 추가했다. 이전에는 기기 간 동기화·복구를 제공하지 않았다. 같은 날 Apple 로그인을 뺐다.
2026-10-08 정합성 보완: 도시별 평가 원문 전송, 로컬 추천 캐시, 목록 밖 도시 요청의 서버 보관을 반영했다.
2026-10-17 추가: 출시 차단 요건의 개인정보 초안을 위해 미정 항목의 [결정 선택지(초안)](#결정-선택지초안)를 붙였다. 정책 본문은 바꾸지 않았다. 같은 날 사용자 요청으로 “폐기한 Firestore 컬렉션과 규칙을 다시 배포하지 않는다”를 지웠다. Firestore 구조는 미정이다.
상태: 새 구조의 논리적 데이터 계약. 서버 제품 선택은 추천 구조를 따르며 새 Swift 저장 타입과 구현은 미완료다.
기준: [사용자 기억](../recommendation/memory.md), [추천 구조](../recommendation/README.md).

## 이관할 기존 저장소 (구현 현황)

- 여행·평가·랭킹·피드백·프로필·이벤트: SwiftData.
- 사진: LocalPhotoStore의 기기 내 파일.
- 국가·태그: 앱 번들 JSON. 기존 앱 실행을 위한 자료이며 새 도시 DB로 사용하지 않는다.
- 기기 간 백업·복구는 아직 구현되지 않았다. 목표는 아래 [iCloud 백업](#icloud-백업)이다.
- 현행 저장소 구현은 [SwiftDataStore](../../TripDNA/Infrastructure/SwiftDataStore.swift)를 참조한다.

## 저장 방식과 도입 단계

- 사용자 기록: 현행 SwiftData·LocalPhotoStore의 기기 내 저장을 유지한다. 새 직접 증거·조건·제외 등의 로컬 저장 구조와 이관은 I1·I2에서 구현한다.
- 공용 도시 자료: 현재 `data/cities/`의 JSON 파일로 작성·검수·버전 관리하고 PC 비교 실험에서 읽는다. “도시 DB”·“검수한 DB”는 이 카탈로그의 논리적 이름이다.
- 앱 운영용 도시 자료의 배포, 외부 DB, Firebase 사용 범위: 2026-10-07에 정했다. [추천 구조의 추가 결정](../recommendation/README.md#2026-10-07-추가-결정-구독-자료-배포-저장)을 따른다.
- LLM 호출 서버: 키 보호·요청 검증·호출/비용 제한을 위한 채택 후 요구사항이다. 서버 경유를 사용자 기록의 클라우드 저장·동기화나 행동 집계 도입으로 해석하지 않는다.

## 새 구조에서 구분할 기록

- 직접 증거: 출처 ID, 원문/선택, 범위, 시점, 활성/철회, 수정 연결.
- 이번 여행: 지속되는 ID, 선택 입력 조건, 변경 버전.
- 방문: 나라, 확인된 도시 ID 또는 미확인 원문, 날짜 정밀도, 사용자 확인 여부.
- 제외: 대상 종류/ID, 이번 여행 ID 또는 계속 적용, 이유, 생성/해제 시점.
- 북마크: 도시 ID와 저장 시점. 제외와 독립이며 저장을 제외 해제로 해석하지 않는다.
- 도시별 평가: 여행·도시 식별 정도, 별점, 좋았던 점·아쉬웠던 점의 메모 원문, 수정·삭제와 버전. 도시 미상·기존 여행 전체 평가는 임의 도시로 배분하지 않는다.
- 추천: 당시 입력/자료/프롬프트/모델 버전, 순서, 도시 ID, 개인화 설명과 근거, 반영한 기억과 원본 평가 연결, 설명이 의존하는 조건. 로컬 결과 캐시이며 공용 도시 자료나 영구 선호로 자동 승격하지 않는다.
- 제외 예외: 이번 요청에서 명시한 대상과 이번 여행 범위를 원래 제외 설정과 구분한다.
- 노출·반응: 실제 보여준 추천 ID·도시·위치와 행동을 연결한다.

캐시를 원본 사용자 진술의 유일한 저장처로 삼지 않는다. 평가 수정/삭제와 기억 철회는 관련 파생 결과를 무효화한다.

## 도시와 근거

아래는 보존한 `data/cities/` 자료를 읽는 계약이다. 검색으로 얻은 사실의 허용 기준은 [출처](../recommendation/sources.md)를 따르며 이 필드를 검색 응답에 그대로 강제하지 않는다.

파일 필드·상태·만료 판정은 [도시 자료 파일 형식](city-format.md)에 정의한다. [가상 예제](../../data/cities/example.json)는 형식 확인용이며 실제 검수 카탈로그가 아니다.

도시 레코드에는 안정적 ID, 이름/별칭, 나라, 적용 지역, 검수 상태, 자료 버전을 둔다.
경험별로 장소 ID·추천 범위 안/밖/미확인 관계, 활동, 추천을 바꾸는 예약/계절/접근 제약과 근거 ID를 연결한다. 배편·숙박 필요 여부는 근거가 있는 값과 미확인을 구분한다. 버스 요금·배차·상세 시간표는 필수 수집 대상이 아니며 이미 조사한 자료는 `detail_only`로 보존할 수 있다.
근거에는 주장, 출처 URL, 확인일, 적용 지역/시기, 검수 상태가 필요하다.
자료에는 검수 종류(자체/독립), 검수자, 자료 버전과 검수일을 남긴다. 우선 자체 검수로 시작하며 독립 검수는 인력을 확보한 뒤 적용한다.

- 비용은 통화·시점·포함 항목·1인/전체 범위를 함께 둔다.
- 위치가 가까워도 이동 조건을 확인하지 않은 근교를 같은 체험권으로 단정하지 않는다.
- 추천용 짧은 요약은 상세 근거로 추적 가능해야 한다.
- 미검수 자료와 기존 국가 축은 새 도시 사실의 근거가 아니다.
- 직접 출처 검수 없이 “안전”, “예산 충족”, “예약 가능” 배지를 만들지 않는다.
- 가격·운영·예약은 최대 3개월, 교통·접근·계절 제약은 최대 6개월, 위치·상설 경험은 최대 12개월마다 재확인한다. 더 짧은 공식 유효기간이나 확인된 변경을 우선한다. 기한 지난 주장은 근거에서 보류하고 관련 필수 조건은 미확인으로 처리한다.

## LLM 전송과 서버

LLM을 앱에 채택할 때, 앱의 영속 사용자 기록과 별개로 키 보호·요청 검증·호출 제한용 서버를 구현한다. 현재 앱에 구현된 서버 기능은 아니다.
추천 입력의 원문은 [흐름](../recommendation/README.md#흐름)과 [지난 여행의 기억](../recommendation/README.md#지난-여행의-기억)에 있다. 최근 도시별 별점과 좋았던 점·아쉬웠던 점 메모 원문, 원하는 여행(티어), 기억하는 취향도 전송 대상이다(2026-10-24 티어·기억 명시). 원문 평가와 사용자가 직접 확정한 평소 선호를 구분한다. 전송할 평가의 수·길이·선택 기준은 미정이다.
원본 사진·EXIF·전체 위치 이력·불필요한 계정 식별자는 보내지 않는다.
첫 전송 전에 메모 원문과 확인된 방문 도시가 추천을 위해 외부 모델에 전달됨을 안내하고 정해진 동의 절차를 적용한다. 동의하지 않으면 전송하지 않으며 로컬 기록과 유효한 기존 결과는 이용할 수 있다.

서버는 모델 제안이 허용된 후보·근거를 사용하는지 검증하고, 앱은 저장 직전 이번 여행 예외를 반영한 최신 제외·입력·평가 버전을 다시 확인한다.
임의 DB 경로나 도구 호출을 모델 출력으로 실행하지 않는다. API 키는 앱에 넣지 않는다.
인증·남용 방지 제품 선택은 [서버 결정](../recommendation/README.md#2026-10-07-추가-결정-구독-자료-배포-저장)을 따른다. 세부 운영은 미정이다. 앱 로그인은 두지 않는다.

LLM 요청 처리와 전체 사용자 행동 집계는 다르다. 요청 본문을 집계 학습 데이터로 자동 보관하지 않는다.
제공자 보관 설정, 요청 로그 최소화, 보관 기간·삭제 절차·전송 안내를 출시 전에 확정한다.

## 목록 밖 도시 요청과 서버 보관

2026-10-08에 사용 횟수 외에 요청된 목록 밖 도시 이름의 서버 기록을 추가했다. 여행 원장·평가 메모·도시 카탈로그·검색 결과를 공용 DB에 저장하는 결정은 아니다. 도시 자료는 기존 번들 배포를 유지한다.

- 목적은 도시 추가 수요의 확인이다. 이름 언급, 회피 요청, 실제 방문 희망을 구분하는 판정·집계 규칙은 구현 전에 정한다.
- 기록 항목, 이름 정규화·동명 도시 처리, 중복 집계 방지, 사용자 연결 여부, 보관 기간·삭제·동의 시점은 미정이다. 도시 요청 기록을 이유로 자유문장 전체나 평가 메모를 자동 보관하지 않는다.
- 집계·검토 기준은 [추천 구조의 미정 목록](../recommendation/README.md#미정)에 있다. 요청 누적을 도시 자료의 검수 완료나 자동 공개로 해석하지 않는다.
- LLM 전송 동의와 도시 요청 집계의 목적·보관 범위를 구분해 안내한다. 필요한 동의·보관·삭제 계약을 정하기 전 실제 수집을 시작하지 않는다.

## 결정 선택지(초안)

상태: **사용자 결정 전.** 위 정책 본문의 미정 항목을 고르기 위한 선택지이며 확정 정책이 아니다. 법률 자문이 아니다. Apple 요건의 출처와 확인일은 [개인정보 초안](../privacy-draft.md#확인한-apple-요건)에 있다. 고른 안은 위 본문과 [추천 구조](../recommendation/README.md#미정)에 반영하고 이 절에서 지운다.

### A. 메모 원문의 LLM 전송 안내·동의 시점

App Review Guidelines 5.1.2(i)는 제3자 AI와 개인 데이터를 공유할 때 명확한 고지와 명시적 허락을 요구한다. 아래 안은 모두 그 허락을 받는 시점의 차이다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A1 | 첫 “추천받기” 직전 한 번 동의 화면. 설정에서 철회 | 실제로 전송하는 순간에 맥락이 분명하다. 온보딩이 길어지지 않는다 | 첫 추천 직전에 한 단계가 더 생긴다 |
| A2 | 온보딩에서 미리 동의 | 추천 흐름이 끊기지 않는다 | 추천을 쓰지 않을 사용자에게도 묻는다. 무엇이 언제 전송되는지 체감이 약하다 |
| A3 | A1 + 매 호출 전 보낼 평가 미리보기·빼기 | 전송 범위를 사용자가 직접 통제한다 | 화면·구현이 늘고 매번 확인이 번거롭다 |

추천안(사용자 결정 전): **A1.** 동의 화면에 보낼 항목(별점, 메모 원문, 확인된 방문 도시, 자유문장, 원하는 여행, 기억하는 취향)과 받는 곳(중계 서버, LLM 제공자)을 적고, 동의하지 않으면 기존 정책대로 전송하지 않는다. 제공자가 정해지면 이름을 적는다. 제공자가 바뀌면 다시 동의를 받는다.

### B. 서버(Cloud Functions) 측 보관 여부·기간·삭제

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| B1 | 요청 본문(메모·자유문장)을 저장·로그하지 않음. 오류 로그에는 요청 ID·상태 코드·토큰 수만 | 보관·삭제 대상이 없다. App Store의 “collect” 정의상 본문을 실시간 처리 후 버리면 서버 측 수집으로 볼 여지가 줄어든다 | 품질 문제를 재현하기 어렵다 |
| B2 | 오류 시에만 본문을 짧은 기간(예: 7일) 보관 후 자동 삭제 | 실패 원인을 분석할 수 있다 | 보관·삭제 절차와 공개 문구가 필요하다. 프라이버시 선언에서 수집으로 잡힌다 |
| B3 | 사용자 동의 시에만 본문을 품질 개선용으로 보관 | 실험 자료를 얻는다 | 별도 동의·삭제 요청 처리가 필요하다. “요청 본문을 집계 학습 데이터로 자동 보관하지 않는다”는 본문 원칙과의 경계를 새로 정해야 한다 |

추천안(사용자 결정 전): **B1.** LLM 제공자 쪽 보관(남용 감시 기간, 학습 사용 여부, 무보관 옵션)은 제공자 선택 뒤 약관으로 확인한다. 제공자가 실시간 처리보다 오래 보관하면 B1이어도 프라이버시 선언에 수집으로 잡힐 수 있다(미확인, 제공자 약관 확인 필요).

### C. 전송할 평가의 수·길이 기준

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| C1 | 최근 10건(도시 평가 단위), 메모는 건당 길이 상한(예: 500자)으로 자름 | 논의한 값과 맞고 비용이 예측된다 | 오래된 핵심 기억이 빠진다 |
| C2 | 최근 N건 + 사용자가 고정한 평가 | 중요한 기억을 남길 수 있다 | 고정 기능이 필요하다 |
| C3 | 토큰 예산 안에서 최근순으로 채움 | 비용 상한이 분명하다 | 사용자에게 몇 건이 갔는지 설명하기 어렵다 |

추천안(사용자 결정 전): **C1.** “최근”은 여행일 기준, 동률은 평가일. 숫자는 실험으로 다시 정할 수 있다. 상한 결정 자체는 [추천 구조의 미정](../recommendation/README.md#미정)에도 걸려 있어 함께 고친다.

### D. 목록 밖 도시 요청 기록

| 안 | 항목 | 사용자 연결 | 보관·삭제 | 장점 | 단점 |
|---|---|---|---|---|---|
| D1 | 정규화한 도시 이름(국가), 의도 구분, 요청 월 | 연결 안 함. 익명 UID를 저장하지 않음 | 집계 카운트만 남기고 원 기록은 즉시 합산 | 개인정보 성격이 가장 약하다. 삭제 요청 대상이 거의 없다 | 같은 사람의 반복 요청을 걸러낼 수 없다 |
| D2 | D1 + 익명 UID의 단방향 해시 | 중복 제거에만 사용 | 일정 기간(예: 12개월) 뒤 해시 삭제, 집계는 유지. 앱 데이터 삭제 시 해당 해시 삭제 | “서로 다른 N명” 기준이 가능하다 | 해시도 사용자와 연결된 데이터로 볼 수 있어 선언·삭제 절차가 필요하다 |
| D3 | 도시 이름과 요청 원문 일부 | UID 연결 | 기간 보관 | 의도 판정을 사후 검토할 수 있다 | 자유문장 보관 금지 원칙과 충돌한다 |

추천안(사용자 결정 전): **D2를 LLM 전송 동의와 따로 묻는 선택 항목으로.** 중복 없는 수요 기준을 쓰려면 사용자 구분이 필요하다. 그 기준을 포기하면 D1이 더 단순하다. D3은 본문 원칙상 권하지 않는다.

### 공통으로 정해야 하는 것

- 철회 방법: 설정에서 LLM 전송 동의를 끄면 새 전송을 멈춘다. 이미 처리된 요청은 B·제공자 보관 정책을 따른다고 안내한다.
- 삭제 범위: 앱 “전체 데이터 삭제”가 서버의 사용 횟수·도시 요청 기록·익명 UID까지 지우는지. 지우지 못하면 그 사실을 표시한다(위 [삭제](#삭제복구실패) 원칙).

## iCloud 백업

2026-10-23 결정. 구현 전이다.

- 대상: 여행·구간·도시별 평가·랭킹·취향(티어·기억)·제외·저장한 도시·하루 한 장 사진. 사진은 기기에 저장한 리사이즈본이며 원본 사진첩을 올리지 않는다.
- 저장 위치: 사용자 Apple 계정의 iCloud. 앱 로그인은 필요 없다. 우리 서버(Firebase)에는 사용자 기록을 두지 않는다는 원칙은 그대로다.
- 복구: 같은 Apple 계정으로 로그인한 새 기기에서 앱을 설치하면 기록을 되살린다.
- 상태 표시: 마지막 백업 시각을 보여준다. iCloud가 꺼져 있거나 용량이 부족해 백업되지 않으면 그 사실을 보여준다. 실제로 백업되지 않은 상태를 “백업됨”으로 표시하지 않는다. 오프라인 기록을 “동기화 대기”로 꾸미지 않는다.
- 삭제: 앱의 전체 데이터 삭제는 iCloud에 있는 사본도 지운다. 지우지 못했으면 남은 범위를 알린다.
- 나중의 서버 동기화를 위해 미리 지키는 것(2026-10-23): 기록마다 UUID 문자열 ID를 쓰고, 사진은 기기 경로가 아닌 `local://photos/{UUID}.jpg`로 가리킨다. 저장 스키마 V2부터 여행·카드 반응·하루 한 장·단일 값 행에 마지막 수정 시각(`updatedAt`)을 남긴다(V1에서 옮긴 행은 비어 있다). SwiftData는 [SwiftDataStore](../../TripDNA/Infrastructure/SwiftDataStore.swift)만, 사진 파일은 LocalPhotoStore만 다루고 화면·추천 로직은 저장소 프로토콜을 거친다. 백업·동기화 코드도 이 경계 안에 둔다.
- 참고: SwiftData의 CloudKit 연동을 쓰면 `@Attribute(.unique)`를 쓸 수 없다. 현재 스키마는 이를 쓰므로, 구현 방식을 고를 때 함께 정한다.
- 미정: 기본으로 켤지 사용자가 켤지, 여러 기기의 동시 사용과 충돌 처리, 구현 방식(SwiftData의 CloudKit 연동 등), 사진 용량이 사용자 iCloud를 얼마나 쓰는지 안내할지, 개인정보 표시(nutrition label)에서 어떻게 다룰지(Apple 문서 확인 전).

## 삭제·복구·실패

- 사용자 삭제는 원본과 관련 파생 기억·캐시·노출 스냅샷의 연결까지 검토한다.
- 서버 보관이 생기면 기기 삭제만으로 끝났다고 표시하지 않는다. 실제 적용 범위를 알린다.
- 저장 실패 시 원본 입력을 보존하고 재시도할 수 있어야 한다.
- 취향/조건이 바뀐 요청의 늦은 응답은 폐기한다.
- 앱 재시작은 새 여행이 아니다. 이번 여행 제외가 사라지지 않아야 한다.
- 이관은 [기존 데이터 이관](../recommendation/memory.md#기존-데이터-이관)을 따른다.
