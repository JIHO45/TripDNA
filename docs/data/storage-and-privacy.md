## 이관할 기존 저장소 (구현 현황)

- 여행·평가·랭킹·피드백·프로필·이벤트: SwiftData.
- 사진: LocalPhotoStore의 기기 내 파일.
- 국가·태그: 앱 번들 JSON. 기존 앱 실행을 위한 자료이며 새 도시 DB로 사용하지 않는다.
- 기기 간 백업·복구는 아직 구현되지 않았다. 목표는 아래 [iCloud 백업](#icloud-백업)이다.
- 현행 저장소 구현은 [SwiftDataStore](../../TripDNA/Infrastructure/SwiftDataStore.swift)를 참조한다.

## 저장 방식과 도입 단계

- 사용자 기록: 현행 SwiftData·LocalPhotoStore의 기기 내 저장을 유지한다. 새 직접 증거·조건·제외 등의 로컬 저장 구조와 이관은 I1·I2에서 구현한다.
- 공용 도시 자료: 현재 `data/cities/`의 JSON 파일로 작성·검수·버전 관리하고 PC 비교 실험에서 읽는다. “도시 DB”·“검수한 DB”는 이 카탈로그의 논리적 이름이다.
- 앱 운영용 도시 자료의 배포, 외부 DB, Firebase 사용 범위: 2026-10-07에 정했다. [추천 구조의 추가 결정](../recommendation/README.md#2026-10-07-추가-결정-구독-자료-배포-저장)을 따른다.
- LLM 호출 서버: 키 보호·인증·입력 상한 검사는 구현돼 있다. 사용 횟수·비용 계수는 미구현이다. 서버 경유를 사용자 기록의 클라우드 저장·동기화나 행동 집계 도입으로 해석하지 않는다.

## 새 구조에서 구분할 기록

- 직접 증거: 출처 ID, 원문/선택, 범위, 시점, 활성/철회, 수정 연결.
- 이번 여행: 지속되는 ID, 선택 입력 조건, 변경 버전.
- 방문: 나라, 확인된 도시 ID 또는 미확인 원문, 날짜 정밀도, 사용자 확인 여부.
- 제외: 대상 종류/ID, 이번 여행 ID 또는 계속 적용, 이유, 생성/해제 시점.
- 북마크: 도시 ID와 저장 시점. 제외와 독립이며 저장을 제외 해제로 해석하지 않는다.
- 도시별 평가: 여행·도시 식별 정도, 별점, 좋았던 점·아쉬웠던 점의 메모 원문, 수정·삭제와 버전. 도시 미상·기존 여행 전체 평가는 임의 도시로 배분하지 않는다.
- 추천: 당시 입력/자료/프롬프트/모델 버전, 순서, 도시 ID, 개인화 설명과 근거, 반영한 기억과 원본 평가 연결, 설명이 의존하는 조건. 로컬 결과 캐시이며 공용 도시 자료나 영구 선호로 자동 승격하지 않는다.
- 제외 예외: 이번 요청에서 명시한 대상과 이번 여행 범위를 원래 제외 설정과 구분한다.
- 노출·반응: 실제 보여준 추천 ID·도시·위치와 행동을 연결한다.

캐시를 원본 사용자 진술의 유일한 저장처로 삼지 않는다. 평가 수정/삭제와 기억 철회는 관련 파생 결과를 무효화한다.

## 도시와 근거

아래는 보존한 `data/cities/` 자료를 읽는 계약이다. 검색으로 얻은 사실의 허용 기준은 [출처](../recommendation/sources.md)를 따르며 이 필드를 검색 응답에 그대로 강제하지 않는다.

파일 필드·상태·만료 판정은 [도시 자료 파일 형식](city-format.md)에 정의한다. [가상 예제](../../data/cities/example.json)는 형식 확인용이며 실제 검수 카탈로그가 아니다.

도시 레코드에는 안정적 ID, 이름/별칭, 나라, 적용 지역, 검수 상태, 자료 버전을 둔다.
경험별로 장소 ID·추천 범위 안/밖/미확인 관계, 활동, 추천을 바꾸는 예약/계절/접근 제약과 근거 ID를 연결한다. 배편·숙박 필요 여부는 근거가 있는 값과 미확인을 구분한다. 버스 요금·배차·상세 시간표는 필수 수집 대상이 아니며 이미 조사한 자료는 `detail_only`로 보존할 수 있다.
근거에는 주장, 출처 URL, 확인일, 적용 지역/시기, 검수 상태가 필요하다.
자료에는 검수 종류(자체/독립), 검수자, 자료 버전과 검수일을 남긴다. 우선 자체 검수로 시작하며 독립 검수는 인력을 확보한 뒤 적용한다.

- 비용은 통화·시점·포함 항목·1인/전체 범위를 함께 둔다.
- 위치가 가까워도 이동 조건을 확인하지 않은 근교를 같은 체험권으로 단정하지 않는다.
- 추천용 짧은 요약은 상세 근거로 추적 가능해야 한다.
- 미검수 자료와 기존 국가 축은 새 도시 사실의 근거가 아니다.
- 직접 출처 검수 없이 “안전”, “예산 충족”, “예약 가능” 배지를 만들지 않는다.
- 가격·운영·예약은 최대 3개월, 교통·접근·계절 제약은 최대 6개월, 위치·상설 경험은 최대 12개월마다 재확인한다. 더 짧은 공식 유효기간이나 확인된 변경을 우선한다. 기한 지난 주장은 근거에서 보류하고 관련 필수 조건은 미확인으로 처리한다.

## LLM 전송과 서버

현재 앱은 Firebase 중계로 Anthropic API를 호출한다. 키 보호·인증·입력 상한 검사와, 아직 없는 호출 횟수 제한을 구분한다. 아래는 목표 계약이며 실제 구현 범위는 [현재 구현 점검](#현재-구현-점검2026-10-29)을 따른다.
추천 입력의 원문은 [흐름](../recommendation/README.md#흐름)과 [지난 여행의 기억](../recommendation/README.md#지난-여행의-기억)에 있다. 최근 도시별 별점과 좋았던 점·아쉬웠던 점 메모 원문, 원하는 여행(티어), 기억하는 취향도 전송 대상이다(2026-10-24 티어·기억 명시). 원문 평가와 사용자가 직접 확정한 평소 선호를 구분한다. 전송할 평가의 수·길이·선택 기준은 미정이다.
원본 사진·EXIF·전체 위치 이력·불필요한 계정 식별자는 보내지 않는다.
첫 전송 전에 메모 원문과 확인된 방문 도시가 추천을 위해 외부 모델에 전달됨을 안내하고 정해진 동의 절차를 적용한다. 동의하지 않으면 전송하지 않으며 로컬 기록과 유효한 기존 결과는 이용할 수 있다.
2026-10-25 결정(사용자): 지난 여행 평가(별점·메모 원문·다녀온 도시)를 처음 보내기 직전에 동의 시트로 묻는다. 동의하지 않으면 평가만 빼고 추천은 진행한다. 설정 "권한과 보내는 정보"의 스위치로 나중에 켜고 끌 수 있고, 끄면 다음 추천부터 보내지 않는다. 입력한 조건과 자유문장은 동의 없이 입력 시트의 안내 문구만 보여주고 보낸다. 이것까지 명시적 동의 대상으로 할지는 아래 A에서 정한다.

목표 계약: 서버는 모델 제안이 허용된 후보·근거를 사용하는지 검증하고, 앱은 저장 직전 이번 여행 예외를 반영한 최신 제외·입력·평가 버전을 다시 확인한다.
임의 DB 경로나 도구 호출을 모델 출력으로 실행하지 않는다. API 키는 앱에 넣지 않는다.
인증·남용 방지 제품 선택은 [서버 결정](../recommendation/README.md#2026-10-07-추가-결정-구독-자료-배포-저장)을 따른다. 세부 운영은 미정이다. 앱 로그인은 두지 않는다.

LLM 요청 처리와 전체 사용자 행동 집계는 다르다. 요청 본문을 집계 학습 데이터로 자동 보관하지 않는다.
제공자 보관 설정, 요청 로그 최소화, 보관 기간·삭제 절차·전송 안내를 출시 전에 확정한다.

## 현재 구현 점검(2026-10-29)

로컬 작업 트리의 코드를 읽어 확인했다. 배포된 함수와의 동일성, 콘솔 설정, 실제 로그 내용은 이번에 확인하지 않았다. UI·자료 작업 중인 파일은 읽기만 했다.

### 전송 경로와 항목

- 앱 → Firebase 중계: `system`, `user`, `model`, `maxTokens`, 질문하기의 `webSearchMaxUses`를 보낸다. 헤더에는 Firebase 익명 로그인 ID 토큰과 App Check 토큰을 붙인다. 처음 필요할 때 익명 계정을 만들며 로그인 화면은 없다. 근거: [클라이언트](../../TripDNA/Recommendation/City/CityLLMClient.swift), [인증](../../TripDNA/Recommendation/City/CityLLMCredentials.swift).
- Firebase → Anthropic: 프롬프트와 사용자 입력, 모델·출력 상한 및 필요 시 검색 도구 설정을 전달한다. 앱의 Firebase UID·ID 토큰·App Check 토큰을 Anthropic 요청 필드로 옮기지는 않는다. API 인증에는 서버 비밀값을 쓴다. 자유문장에 사용자가 직접 쓴 식별 정보까지 제거하는 기능은 없다. 근거: [중계 함수](../../functions/index.js).
- 조건 추출: 원하는 것·피하고 싶은 것 자유문장이 있으면, 고른 컨셉과 해당 원문 및 세부 항목 목록을 먼저 보낸다. 성공하면 별도의 추천 생성 호출로 이어진다. 따라서 **추천 한 번과 외부 API 호출 한 번은 같지 않다.** 근거: [추천 서비스](../../TripDNA/Recommendation/City/CityRecommendationService.swift), [입력 조립](../../TripDNA/Recommendation/City/CityLLMRequest.swift).
- 추천 생성: 컨셉·시기·기간·인원·예산과 그 기준, 원하는 것·피하고 싶은 것 원문, 추출 조건, 평소 티어·회피 메모, 후보 도시 표와 일부 제외 표시를 보낸다. 지난 여행 평가에 동의한 경우 도시·국가·별점·좋았던 점·아쉬웠던 점도 포함한다. 현재 평가는 평가 시각 순 최대 10건이며 메모별 길이 제한은 없다. 요청 안의 `m1` 같은 임시 ID만 프롬프트에 쓰고 여행의 `tripID`는 보내지 않는다. 이는 [C](#c-전송할-평가의-수길이-기준)의 제안인 여행일 순·메모 길이 제한과 다르다. 근거: [평가 선택](../../TripDNA/Recommendation/City/CityMemory.swift), [동의 적용](../../TripDNA/Recommendation/City/CityRecommendationSection.swift).
- 질문하기: 질문 원문, 대상 도시와 번들 자료 일부, 카드 이유·유의점·비용, 조건 요약과 원래 요청의 컨셉·인원·자유문장을 보낸다. 평가 목록을 직접 붙이지는 않지만 카드 설명에 평가에서 파생된 내용이 있을 수 있다. 평가 전송 스위치를 끄는 것을 질문·조건 전송 중단으로 해석하면 안 된다. 검색 질의에는 모델이 입력에서 가져온 내용이 들어갈 수 있으며, 현재 코드에는 검색 질의에서 개인 내용을 제거하는 단계가 없다. 근거: [질문 서비스](../../TripDNA/Recommendation/City/CityQuestion.swift).
- 앱 → Firebase `metric`(2026-10-31 추가, 출시 빌드만): `{event}` 이벤트 이름 하나와 App Check 토큰만 보낸다. 익명 ID 토큰·도시·내용은 보내지 않는다. 서버는 Firestore `metrics/{UTC 날짜}`의 해당 이름 수를 1 올리고 로그를 남기지 않는다. 이름 목록은 [보내는 쪽](../../TripDNA/App/ServerMetricsSink.swift)과 [중계 함수](../../functions/index.js)의 `METRIC_EVENTS`가 같아야 한다(`ServerMetricsTests`). 합계는 사람과 연결되지 않으므로 전체 삭제 대상이 아니다. 끄는 설정은 없다.
- 이 LLM 경로는 사진·EXIF·전체 위치 이력을 보내지 않는다. 사진 위치의 Apple 역지오코딩은 별도 경로이며 [개인정보 초안](../privacy-draft.md)을 따른다.

### 남는 기록과 현재 삭제 범위

- **우리 함수의 본문 저장:** Firestore 쓰기나 요청·응답 본문을 로그에 남기는 코드가 없다. 오류 로그에는 상류 상태 코드와 예외 종류를 남긴다. 사용량·목록 밖 도시 기록·구독 검증 및 삭제 API도 없다. 함수가 본문을 저장하지 않는다는 것과 Firebase 서비스 전체가 아무 기록도 보관하지 않는다는 것은 다르다.
- **Firebase 인증·운영:** 익명 계정이 생기고 토큰 검증에 쓰인다. HTTP 운영 로그·인증 기록·App Check 처리 정보의 실제 항목, 위치, 보관 설정은 콘솔에서 따로 확인해야 한다. 소스만으로 “UID·IP를 전혀 보관하지 않는다”고 선언할 수 없다.
- **기기 추천 기록:** `CityRecommendationLogs`에는 입력·평가·프롬프트·원본 응답·실패 정보가 저장될 수 있다. 추천 서비스에는 이 파일의 자동 만료 처리가 없다. 네트워크 세션은 `.ephemeral`이지만 의도적으로 저장한 이 기록까지 없애지는 않는다. 마지막 결과·저장한 도시는 별도 로컬 저장소에도 남는다.
- **전체 삭제:** [현재 삭제 경로](../../TripDNA/App/AppDependencies.swift)의 `deleteAccount`는 SwiftData 기록·로컬 사진·추천 로그를 지우고 평가 전송 동의를 초기화한다. 2026-10-31부터 마지막에 Firebase 익명 계정을 지우고(실패하면 기기에서 로그아웃), 서버의 Auth 삭제 트리거 `deleteUserData`가 그 uid의 `usage/{uid}` 문서를 지운다. 로그아웃만 된 경우 문서는 `expireAt`(그 달 끝 + 7일)에 Firestore TTL로 지워진다(TTL 정책은 운영 설정, 배포 전). iCloud 삭제 호출은 없다(iCloud 기능 없음). 로컬 사용자 ID 재생성과 Firebase 익명 UID 삭제는 별개다. 일부 삭제 실패는 호출자에게 전달되며 모든 저장소가 한 번에 원상 복구되는 작업은 아니다.
- **동의 철회:** 현재 스위치는 이후 추천에 평가 목록을 붙이지 않게 한다. 이미 전송된 제공자 데이터나 기기의 기존 추천 기록을 자동 삭제하는 기능은 아니다.

2026-10-29 공식 문서를 읽었다. 다음은 일반 정책이며 TripDNA 계정에 실제 적용된 계약·설정의 확인을 대신하지 않는다.

### E. 사용량을 세는 단위와 재설치

이미 정한 내용은 [가격·한도](../recommendation/README.md#2026-10-07-추가-결정-구독-자료-배포-저장)와 [추천 1회의 정의](../recommendation/README.md#llm-호출과-횟수)를 유지한다. 무료는 Firebase 익명 ID 단위, UTC 월초 초기화이며 추천·질문 한도는 각각 센다. 익명 UID는 물리 기기나 사람과 영구적으로 일치하는 ID가 아니다. 구독 한도는 결제·갱신 주기이며 연간 구독의 월별 사용량 구간 계산은 구현 전 명확히 해야 한다.

남은 선택은 UID 변경·재설치 우회에 얼마나 대응할지다.

- **E1: 익명 UID + App Check + 단시간 호출 제한.** 최소 구현이다. UID가 달라지면 무료 한도를 다시 받을 수 있다는 한계를 받아들인다. App Check만으로 같은 사람의 재가입이나 정상 앱의 반복 호출을 막는다고 보지 않는다.
- **E2: E1 + 별도 기기 단위 남용 방지 수단 검토.** 우회를 더 줄일 수 있지만 추가 식별 정보·복구·삭제 정책과 플랫폼 제약 검증이 필요하다. 구체 기술과 보관 항목은 아직 정하지 않는다.

제안(미승인): 소수 테스터는 E1로 시작하되 서버 비용 제한을 함께 둔다. 공개 출시 전 실제 남용·비용을 보고 E2 필요성을 판단한다. 앱 로그인 추가나 개인정보를 이용한 기기 지문은 이번 초안의 전제로 삼지 않는다.

### F. 성공·실패·재시도의 차감

선택지에 공통인 기준안(미승인): 인증·입력 검증·잔여 한도 확인을 통과하지 못한 요청, 외부 호출 전 취소는 차감하지 않는다. 이미 정한 로컬 조건 수정·다른 후보 보기와 추천 카드 없이 여행 등록으로 이어지는 호출의 미차감은 유지한다. 기술 실패와 정상 처리됐지만 원하는 결과가 없는 경우를 구분한다.

- **F1: 사용 가능한 결과 성공 시 1회.** 추천은 유효 카드가 있는 결과, 질문은 읽을 수 있는 답을 성공 기준으로 삼는다. 조건 추출 실패·응답 잘림·형식 오류·네트워크 실패는 미차감한다. 사용자가 결과를 받지 못한 실패에 한도를 쓰지 않지만, 서버가 성공을 검증하는 구조와 실패 남용 방지가 필요하다.
- **F2: 외부 호출 시작 시 1회, 서버가 확인한 기술 실패는 복원.** 최초 차감은 단순하지만 취소·응답 유실·앱 파싱 실패의 복원 기준이 까다롭다. 사용자가 결과를 못 받았는데 차감될 수 있다. 이미 확정한 미차감 예외도 사후 복원해야 한다.

제안(미승인): F1. 다만 현재 중계는 HTTP 성공과 `content`·`stop_reason`만 전달하고 카드·질문 유효성은 앱이 판단한다. 서버 HTTP 200을 곧바로 성공 차감으로 삼거나 앱의 “실패” 신고만 믿고 무제한 복원하면 안 된다. 서버 검증에 필요한 최소 구조화 입력·결과 판정 계약을 정해야 하며 프롬프트 원문 저장을 요구하지는 않는다.

별도로 결정할 경계 사례:

- 추천이 정상 생성됐지만 예산 필터 뒤 카드가 0개: 미차감 / 정상 처리 1회 차감. “카드 없이 여행 등록” 예외와 같은 경우로 자동 간주하지 않는다.
- 질문 답이 “확인하지 못했어요”뿐인 경우: 미차감 / 정상 답변으로 차감. 검색 자체 오류·응답 형식 오류와 구분한다.
- 전송 후 취소·앱 종료·타임아웃: 결과가 서버에서 완성돼도 사용자가 못 받았다면 어떻게 처리할지. 취소만으로 제공자 비용까지 없어지는 것은 아니다.
- 사용자가 새로 누른 재시도: 실패 작업의 이어받기 / 새 작업. 성공했던 입력을 다시 생성하는 경우와 구분한다.

### G. 중복 요청과 내부 재시도

현재 프록시 계약에는 작업 종류·작업 ID·단계 ID가 없다. 현재 앱은 자유문장 조건 추출과 추천 생성을 서로 다른 HTTP 요청으로 보낸다. 서버의 설치된 Anthropic SDK는 기본 최대 2회 자동 재시도를 두며 함수는 이를 덮어쓰지 않는다. 앱의 새 추천, 내부 두 단계, SDK 재시도를 각각 무료 한도 1회로 세면 안 된다. SDK 기본값은 설치 버전 확인 결과이며 향후 고정·변경 여부는 미정이다.

- **G1: 같은 작업 ID는 한 번만 차감하고, 결과 본문은 서버에 저장하지 않음.** UID·작업 종류·작업 ID·단계·상태·시각·차감 여부만 단기 보관한다. 동시에 같은 작업이 오면 외부 호출을 중복 실행하지 않는다. 이미 완료된 작업의 응답을 잃었을 때는 같은 본문을 돌려줄 수 없어, 미수신 복구 또는 새 호출 처리 규칙이 필요하다.
- **G2: G1 + 응답을 짧게 보관해 재전달.** 통신 단절 복구가 쉬워지지만 응답에 개인화된 조건·평가 내용이 들어갈 수 있다. 본문 미보관 B1과 양립하지 않으므로 B 재결정·보관 기간·삭제 계약 없이는 도입하지 않는다.

제안(미승인): B1을 유지하려면 G1. 작업 ID를 바꾼 재전송과 같은 ID에 다른 입력을 넣는 경우의 거부 기준, 동시 호출의 원자적 한도 예약, 처리 중 만료·함수 중단의 복구도 정의한다. 장기 한도와 별도로 실패·검색·SDK 재시도까지 포함한 비용 보호를 둔다. 한도 기간이 바뀌는 중 재전송돼도 같은 작업을 두 번 차감하지 않도록 최초 예약 기간에 연결한다. 보관 기간이 끝난 작업 ID의 재사용은 거부하는 등 경계를 정한다.

### H. 사용량 기록의 보관과 전체 삭제

아래는 새 Firestore 구현에 대한 제안이며 실제 컬렉션명·필드명·기간은 확정하지 않았다. 원문 메모·질문·도시별 추천 응답은 B1에 따라 제외한다.

- **필요한 최소 항목 제안:** 인증된 익명 UID, 추천/질문 구분, 서버가 정한 사용 기간, 사용·예약 횟수. G1을 고르면 작업 ID·단계·상태·생성/만료 시각·차감 여부를 단기 추가한다. 비용 상한을 구현하려면 사용 토큰·검색 횟수 등 계측도 필요하나 현재 함수는 저장하지 않는다. 구독 권리는 클라이언트 주장이 아닌 서버 검증 결과를 기준으로 하며 구독 기록 항목·연결·복원 계약은 별도 확정한다.
- **보관 기간 선택:** H1은 사용 기간 종료 후 정산·재시도 유예가 끝나면 삭제, H2는 문의 대응을 위해 이전 기간도 일정 기간 보관. 제안은 H1이며 유예 기간 후보는 7일, 작업별 중복 방지 기록은 완료 후 24시간이다. 숫자는 미승인이고 네트워크 복구·환급 정책에 맞춰 확정해야 한다. 앱에서 지난 기록을 볼 요구가 없다면 장기 사용 이력을 만들지 않는다. 정해진 만료 뒤 접근 차단과 실제 삭제 완료를 구분하고 자동 삭제 실패를 확인한다.
- **삭제 선택 H3:** 전체 삭제 요청 시 사용량·작업 기록과 Firebase 익명 계정을 함께 삭제한다. 설명이 단순하지만 새 UID로 무료 한도를 다시 받을 수 있다. 남용 방지를 이유로 원래 UID를 몰래 남기지 않는다.
- **삭제 선택 H4:** 여행 기록 삭제와 한도용 최소 기록 삭제의 범위를 나누고, 한도용 기록은 정한 기간까지만 남긴다. 한도 초기화 우회를 줄일 수 있지만 삭제 예외의 필요성·보관 기간·안내 및 적용 요건 확인이 먼저다. 이를 선택하고도 “모든 데이터가 삭제됐다”고 표시하지 않는다.

H3/H4 추천은 보류한다. E의 남용 허용 범위와 함께 사용자가 결정해야 한다. 서버 삭제를 구현할 때는 익명 인증을 잃기 전에 연결 데이터를 지우고 실패하면 재시도할 수 있게 해야 한다. 로그·제공자 보관·향후 iCloud 사본은 별도 삭제 범위와 남은 기간을 알린다. 앱의 데이터 삭제 버튼만으로 Anthropic의 모든 기록이 즉시 지워진다고 약속하지 않는다.

### 공통으로 정해야 하는 것

- 철회 방법: 현재 평가 전송 스위치는 이후 추천의 평가 목록만 제외한다. 조건·질문까지 포함하는 전체 LLM 전송 철회는 A에서 범위를 정한다. 이미 처리된 요청은 B·제공자 보관 정책을 따른다고 안내한다.
- 삭제 범위: 앱 “전체 데이터 삭제”가 서버의 사용 횟수·도시 요청 기록·익명 UID까지 지우는지. 지우지 못하면 그 사실을 표시한다(위 [삭제](#삭제복구실패) 원칙).

## iCloud 백업

2026-10-23 결정. 2026-10-31 구현(통째 백업, 기본 켜짐, 실기기 미확인). 방식·충돌·삭제 처리는 [TODO의 iCloud 백업](../TODO.md) 항목과 `ICloudBackup.swift` 주석에 있다. 아래 '미정' 중 기본값·충돌·구현 방식은 그날 정했다.

- 대상: 여행·구간·도시별 평가·랭킹·취향(티어·기억)·제외·저장한 도시·하루 한 장 사진. 사진은 기기에 저장한 리사이즈본이며 원본 사진첩을 올리지 않는다.
- 저장 위치: 사용자 Apple 계정의 iCloud. 앱 로그인은 필요 없다. 우리 서버(Firebase)에는 사용자 기록을 두지 않는다는 원칙은 그대로다.
- 복구: 같은 Apple 계정으로 로그인한 새 기기에서 앱을 설치하면 기록을 되살린다.
- 상태 표시: 마지막 백업 시각을 보여준다. iCloud가 꺼져 있거나 용량이 부족해 백업되지 않으면 그 사실을 보여준다. 실제로 백업되지 않은 상태를 “백업됨”으로 표시하지 않는다. 오프라인 기록을 “동기화 대기”로 꾸미지 않는다.
- 삭제: 앱의 전체 데이터 삭제는 iCloud에 있는 사본도 지운다. 지우지 못했으면 남은 범위를 알린다.
- 나중의 서버 동기화를 위해 미리 지키는 것(2026-10-23): 기록마다 UUID 문자열 ID를 쓰고, 사진은 기기 경로가 아닌 `local://photos/{UUID}.jpg`로 가리킨다. 저장 스키마 V2부터 여행·카드 반응·하루 한 장·단일 값 행에 마지막 수정 시각(`updatedAt`)을 남긴다(V1에서 옮긴 행은 비어 있다). SwiftData는 [SwiftDataStore](../../TripDNA/Infrastructure/SwiftDataStore.swift)만, 사진 파일은 LocalPhotoStore만 다루고 화면·추천 로직은 저장소 프로토콜을 거친다. 백업·동기화 코드도 이 경계 안에 둔다.
- 참고: SwiftData의 CloudKit 연동을 쓰면 `@Attribute(.unique)`를 쓸 수 없다. 현재 스키마는 이를 쓰므로, 구현 방식을 고를 때 함께 정한다.
- 미정: 기본으로 켤지 사용자가 켤지, 여러 기기의 동시 사용과 충돌 처리, 구현 방식(SwiftData의 CloudKit 연동 등), 사진 용량이 사용자 iCloud를 얼마나 쓰는지 안내할지, 개인정보 표시(nutrition label)에서 어떻게 다룰지(Apple 문서 확인 전).

## 삭제·복구·실패

- 사용자 삭제는 원본과 관련 파생 기억·캐시·노출 스냅샷의 연결까지 검토한다.
- 서버 보관이 생기면 기기 삭제만으로 끝났다고 표시하지 않는다. 실제 적용 범위를 알린다.
- 저장 실패 시 원본 입력을 보존하고 재시도할 수 있어야 한다.
- 취향/조건이 바뀐 요청의 늦은 응답은 폐기한다.
- 앱 재시작은 새 여행이 아니다. 이번 여행 제외가 사라지지 않아야 한다.
- 이관은 [기존 데이터 이관](../recommendation/memory.md#기존-데이터-이관)을 따른다.
