# 추천 지침 비교 실험

상태: 2026-10-06 사전 계획 v3(집계 단위·동률·보류·미판정 처리 명확화). 호출 전이며 결과는 없다. [목록 대 프로필 탐색 실험](profile-exploration.md)의 실행 1·2에 이어지는 실행 3(개발용 선별)과 실행 4(확인)를 다룬다. 실행 4의 세부 설정은 실행 3 뒤에 지침을 고정하면서 이 문서에 추가한다.

## 배경과 목적

실행 1·2에서 반복된 실패의 상당수는 입력 자료보다 추천 지침과 관련된 것으로 보였다. 체류 조건을 어긴 추천, 대안에 같은 기준을 적용하지 않은 추천, “확인하세요”로 판단을 대신한 답, 사용자에게 내부 자료를 언급한 답이다. 당시 지침은 출력 제한에 비해 추천 판단의 기준이 빈약했다. 결과는 “모델의 추천 능력이 부족하다”가 아니라 “그 지침과 입력 조합에서 그런 실패가 생겼다”로 읽는다.

이 실험은 지침을 바꾸면 사용자 조건 처리와 답변 방식이 달라지는지 본다. 프로필은 바꾸지 않는다.

순서: 개발용 비교(실행 3) → 지침 고정 → 손대지 않은 사례로 확인(실행 4) → 고정한 지침 위에서 제약 입력 재평가(별도 계획).

## 이 단계에서 볼 수 있는 것과 없는 것

입력은 도시 목록만 준다. 따라서 사용자 조건 처리와 답변 방식은 볼 수 있지만, 자료 사이의 사실 혼합이나 프로필·내부 용어 노출을 막는 능력은 검증되지 않는다. 그 부분은 이후 제약 입력 비교에서 확인한다.

실행 1·2의 “약 120km”와 도쿄 “겨울 눈”이 다른 곳의 사실을 옮겨 쓴 것이라는 설명은 가능한 원인에 대한 가설이다. 모델이 그 내용을 어디서 가져왔는지는 확인하지 못했다.

## 실행 3: 개발용 선별

같은 모델·입력·사례·출력 형식에서 지침 세 가지를 비교한다.

| 방식 | 지침 | 비고 |
|---|---|---|
| G0 | 실행 1·2의 시스템 지침 그대로 | 과제 문구에 `note`가 추가된 **비교용 기준선**이다. 실행 1·2와 완전히 같은 기준선이 아니므로 결과를 합산하지 않는다. |
| G1 | [`g1-claude.md`](../../data/exploration/guidelines/g1-claude.md) | Claude Opus 5.5 작성, 교차 검토로 수정한 v2 |
| G2 | [`g2-codex.md`](../../data/exploration/guidelines/g2-codex.md) | Codex 작성 v1. Claude 초안과 실행 1·2 결과를 본 뒤 썼다 |

두 지침을 합친 안은 만들지 않는다. 두 지침 모두 실행 1·2의 실패를 본 뒤에 쓴 것이다.

- 고정: 모델 `claude-haiku-4-5`, 추론·프롬프트 캐시 미사용, 도시 목록 입력(프로필 없음), 출력 상한, 자동 재시도 없음.
- 사례: 개발용 N1~N6([`cases-n.json`](../../data/exploration/cases-n.json), 기준은 [`cases-claude.md`](../../data/exploration/drafts/cases-claude.md)). 한국어 입력만이다.
- 출력 형식: 추천 과제에 `note` 한 문장을 추가한다. 후보가 2곳보다 적으면 필수이고 그 실제 이유를 쓴다. 세 방식에 같은 과제 문구와 같은 형식 검사를 적용한다.
- 호출: 6사례 × 3방식 × 2과제 = 36회, 1회 실행. 방식 순서는 사례마다 돌려 가며 배치한다(G0·G1·G2, G1·G2·G0, G2·G0·G1 …). 개발용 선별이므로 반복 실행은 하지 않는다.
- 기록: `data/exploration/runs3/`. 실행은 `scripts/run_profile_exploration.py --run 3`.
- 비용: 실제 요청 길이로 계산한 상한은 36회에 US$0.42다(입력을 문자당 2토큰, 출력을 상한 1,024토큰 전부로 가정). 실행 1·2의 실제 사용량에 비추면 이보다 훨씬 낮을 것으로 예상하지만 추정이다. 누적 지출은 US$0.45이며 첫 파일럿 상한 US$10 안이다.

### 판정

사례별 기준은 사례 파일에 호출 전에 고정한 내용을 쓴다. 기준에 수치가 필요한 항목(N2의 기온, N3의 직항 시간, N6의 도로 이동 시간)은 응답에 실제로 나온 도시에 대해 판정 전에 출처를 확인한다. 보류 응답은 아래 규칙에 따라 허용 목록 쪽도 확인한다.

승패에는 실행 1·2와 같은 판정 순서만 쓴다.

1. 조건·제외 위반과, 미확인 변동·안전 정보의 단정.
2. 틀린 사실과 유의점 누락.
3. 답변의 직접성.

미리 정하는 처리 규칙:

- 혼합은 동률이 아니다. “낫거나 같음”은 우세 또는 차이 없음만 뜻한다.
- 과장과 자료 밖 사실은 틀린 사실로 세지 않고 따로 기록한다. 틀림은 출처로 확인된 경우에만 쓴다.
- 빈 추천과 줄인 추천은 그 자체로 실패가 아니다. 사례 기준상 조건에 맞는 후보가 없거나 충족을 확인할 수 없는 경우의 보류는 **적절한 보류**로 충족이다. 조건에 맞는 후보가 있는데도 내지 않은 경우는 **과도한 보류**로 3번(답변의 직접성)에서 불리하게 센다. 빈 추천 비율만으로 우열을 정하지 않는다.
- 후보 수만으로 과도한 보류를 판정하지 않는다. 과제는 “최대 2곳”이고 억지로 채우지 않는 것이 원칙이므로, 적합한 후보 1곳을 낸 응답은 다른 적합한 후보가 있더라도 과도한 보류가 아니다. 요청에 충분히 답했는지와 `note`에 적은 보류 이유가 타당한지를 본다.
- 과도한 보류는 두 경우다. 후보를 하나도 내지 않았는데 허용 목록 20곳 가운데 사례 기준을 충족하는 후보가 확인되는 경우, 또는 `note`의 보류 이유가 사실과 맞지 않는 경우(충족하는 조건을 충족하지 못한다고 한 경우 등)다.
- 빈 추천은 응답에 나온 도시만으로 검수할 수 없으므로 허용 목록 쪽을 따로 확인한다. 확인된 충족 후보가 없으면 적절한 보류다. 출처가 부족해 판단할 수 없으면 그 항목을 미판정으로 남긴다.
- `note` 누락, 코드 블록 등 출력 형식 위반과 내부 용어 노출은 승패에 넣지 않고 건수로 보고한다.
- 판정은 AI 검수로 하고, 지침을 쓰지 않은 쪽의 교차 검토를 거친 뒤 확정한다. 검수자는 방식을 가린 시트로 먼저 판정한다. 공식 출처를 대조하지 않은 사실 판정은 잠정으로 표시한다.

### 지침 선택 규칙 (호출 전 고정)

**집계 단위.** 응답 하나가 단위다. 방식마다 응답은 12개(6사례 × 추천·상세)다. 응답별로 세 평가 항목 각각의 위반 유무를 0 또는 1로 적는다. 한 응답 안에 같은 항목의 문제가 여러 개 있어도 1이다. 추천과 상세는 다른 응답이므로 같은 오류가 양쪽에 나오면 각각 센다. 세부 오류는 건수와 별도로 기록한다. 방식의 항목별 건수는 0~12다.

- 1번 항목: 조건·제외 위반 또는 미확인 변동·안전 정보의 단정이 있는 응답 수.
- 2번 항목: 출처로 확인된 틀린 사실 또는 유의점 누락이 있는 응답 수.
- 3번 항목: 답변 불능(질문에 직접 답하지 않음) 또는 과도한 보류인 응답 수.

**선택 절차.** 세 방식에서 시작해 단계마다 남길 방식을 추린다.

1. 남은 방식 가운데 1번 건수의 최솟값을 구한다. 최솟값에서 1건 이내인 방식만 남긴다.
2. 남은 방식에 대해 2번 건수로 같은 절차를 적용한다.
3. 남은 방식에 대해 3번 건수로 같은 절차를 적용한다.
4. 둘 이상 남으면 모델용 본문이 더 짧은 지침을 고른다. G0이 남아 있으면 G0을 유지한다.
5. **혼합 확인(최종 선택 전).** 위에서 고른 방식 W를 나머지 두 방식 각각과 세 항목에서 비교한다. 어느 방식 V가 한 항목에서라도 W보다 2건 이상 적으면, W가 앞 단계에서 이겼더라도 혼합으로 본다. 이 경우 선택을 보류하고 W와 V의 항목별 건수와 차이가 난 응답을 기록한다. 억지로 승자를 정하지 않는다.

예: 1번 건수가 G0=0, G1=1, G2=2이면 최솟값 0에서 1건 이내인 G0과 G1만 다음 단계로 간다.

**미판정 처리.** 미판정은 응답 전체가 아니라 항목 단위다. 한 응답의 한 항목이 미판정이어도 그 응답의 다른 항목에서 확인된 위반은 그대로 센다. 미판정 항목은 건수에 넣지 않은 채 위 절차를 적용한 뒤, 모든 미판정 항목을 위반 없음(0)으로 놓았을 때와 위반 있음(1)으로 놓았을 때 각각 절차를 다시 적용한다. 어느 경우든 선택 결과가 달라지면 선택을 보류한다.

개발용 사례 6개, 1회 실행의 결과다. 선택된 지침이 낫다는 증거가 아니라 확인 단계로 가져갈 후보를 정하는 절차다.

## 실행 4: 고정한 지침의 확인 (설정은 실행 3 뒤에 추가)

- 실행 3에서 고른 지침을 고정하고, G0과 확인용 사례 C1~C6([`cases-c.md`](../../data/exploration/drafts/cases-c.md))으로 비교한다. 고정한 뒤에는 지침을 고치지 않는다.
- C 사례는 지침 고정 전에 실행하지 않고, 지침을 고치는 근거로 쓰지 않는다.
- C 사례는 완전히 독립된 평가가 아니다. 작성자와 수정자 모두 두 지침 초안을 본 상태였고, 지침 작성자 중 한 쪽이 사례의 구조 문제를 고쳤다. 이 한계를 결과에 적는다.
- 호출 수, 반복 규칙, 채택 조건은 실행 3의 결과를 보기 전의 원칙(위 판정·처리 규칙)을 그대로 쓰되, 구체적인 수치는 지침 고정 시점에 이 문서에 적고 그 뒤에 호출한다.

## 한계

- 모델 1개, 한국어 입력, 사례 12개(개발용 6, 확인용 6), AI 검수다.
- 지침으로 준수가 보장되지 않는다. 허용 ID, 출력 형식, 내부 용어 노출처럼 명확히 검사할 수 있는 것은 앱에서 코드로 확인해야 한다. 이번 실험은 그 구현을 다루지 않는다.
- 채택되는 지침이 [핵심 설계](../recommendation/architecture.md) 7절보다 강한 제한(고정 조건 위반 후보의 사전 제외, 유의점으로 위반을 덮지 않기)을 담고 있으면 설계 문서를 맞춰 고쳐야 한다. 이 실험 결과만으로 출시용 정책을 바꾸지 않는다.
