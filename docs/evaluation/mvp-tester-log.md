# MVP 사용 기록 양식

2026-10-25 작성(사용자 결정). MVP에서는 비교 실험 대신 Joe와 소수의 테스터가 직접 추천을 받아 보며 문제를 고친다([추천 구조](../recommendation/README.md#2026-10-17-결정-조건-판정과-순위)의 핵심 경험 절). 이 문서는 그 기록 방식이다. 2026-10-25: 앱에 도시 추천 흐름(번들 자료·코드 순위·LLM 설명)을 연결했고, 추천 한 번마다 입력·버전·보낸 요청·받은 응답이 기기의 `Application Support/CityRecommendationLogs/<id>.json`에 남는다(`CityRecommendationRecord`). 아래 양식의 입력과 받은 도시는 그 파일에서 옮긴다. 도시 문제·설명 문제는 사람이 적는다. 아직 기록은 없다.

2026-10-25 개정: 기록할 때는 관찰만 적고, 원인은 모아서 볼 때 분류한다. 이전에는 "도시 문제는 등급·순위, 설명 문제는 지침"으로 바로 연결했으나, 도시가 이상한 원인은 등급 외에도 여럿이라 고쳤다.

## 기록 원칙

- **관찰 먼저, 원인은 나중에.** 기록하는 사람은 무엇이 이상했는지만 적는다. 왜 그런지 추측해 적지 않는다. 원인은 기록을 모아 볼 때 [아래 분류](#원인-분류)로 나눈다.
- **도시가 이상한 것과 설명이 이상한 것을 나눠 적는다.** 같은 추천에 둘 다 있으면 둘 다 적는다.
- **같은 조건으로 다시 받아 볼 수 있게 적는다.** 요청 문장, 티어, 조건, 날짜를 그대로 남긴다. 앱이 입력 버전(후보 자료·프롬프트·모델 버전)을 저장하면 그 값도 남긴다.
- **한 번 나온 문제보다 반복되는 문제를 고친다.** 한 사례만 보고 등급표나 지침을 바꾸지 않는다.
- 개인 정보와 지난 여행 메모 원문은 테스터의 동의 없이 기록에 옮기지 않는다.

## 한 건의 기록

| 항목 | 적을 내용 |
| --- | --- |
| 날짜·기록자 | 2026-11-01, Joe |
| 입력 | 요청 문장, 티어(주·부 컨셉), 시기·예산·기간 조건 |
| 받은 도시 | 3곳과 순서 |
| 도시에서 이상한 점 | 없음 / 있음. 있으면 어느 도시가 어떻게 이상했는지, 기대한 도시가 있었다면 어디인지 |
| 설명에서 이상한 점 | 없음 / 있음. 있으면 해당 문장을 그대로 옮기고, 무엇이 이상했는지(틀린 사실, 과장, 요청과 무관함 등) |
| 기타 | 속도, 오류, 그 밖의 메모 |

## 원인 분류

모아서 볼 때 관찰 하나에 원인 후보를 붙인다. 한 관찰에 원인이 여럿일 수 있고, 확인하지 못하면 "미분류"로 둔다.

| 원인 | 예 | 고치는 곳 |
| --- | --- | --- |
| 요청·취향 해석 | 자유문장이나 지난 여행 메모를 잘못 읽음 | 지침(조건 추출) |
| 후보 필터 | 조건·제외·사는 나라 처리로 후보가 잘못 빠지거나 남음 | 추천 코드 |
| 시즌 처리 | 시기에 맞지 않는 경험으로 추천, 미확인 세부를 충족으로 처리 | 시즌 자료·추천 코드 |
| 점수·순위 계산 | 티어 합산이나 탐색 카드 선택이 이상함 | 추천 코드 |
| 도시 등급 | 해당 세부의 등급이 다른 도시와 비교해 맞지 않음 | [등급 판정 절차](../data/destination-grading.md)로 해당 세부 재판정 |
| 설명 지침 | 틀린 사실, 과장, 요청과 무관한 내용 | 지침(설명) |

- 같은 원인이 여러 번 나오면 고친다. 틀린 사실(날짜·가격·운영 정보)이 반복되면 지침에서 그 주장을 금지하거나 줄인다.
- 설명의 사실 오류가 특정 도시에서 반복되면 그 도시의 핵심 경험 문장을 다시 넣을 후보로 적는다.
- 기록 수, 테스터 수, 언제 지침 조정을 마칠지는 정하지 않았다.
