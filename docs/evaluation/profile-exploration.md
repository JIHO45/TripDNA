# 도시 목록과 가벼운 프로필의 탐색 실험

상태: 2026-10-06 계획 v5. 실행 1(목록 A 대 전체 프로필 B)을 마쳤고 결과는 [아래](#실행-1-결과-2026-10-06)에 있다. 실행 2(목록 A 대 제약 중심 입력 B′)도 마쳤고 [계획](#실행-2-계획-목록-a-대-제약-중심-입력-b)과 [결과](#실행-2-결과-2026-10-06)가 아래에 있다. 아래 본문은 실행 1의 사전 계획 v4를 그대로 보존한 것이다. [기존 비교 실험](offline-evaluation.md)의 실제 사용자 평가·E7 확대 관문과 별개다.

## 목적과 경계

도시 프로필을 추가하면 범위·중요 제약 오류와 답변 불능이 얼마나 달라지고, 입력·출력 토큰·비용·지연·사람 작업 시간이 얼마나 늘어나는지 확인한다. DB가 비용을 줄인다고 전제하지 않는다. 합성 사례의 조건 준수·추천 차이는 진단 신호이며 실제 사용자 선택 품질이나 선호 개선의 증거가 아니다.

D3의 주장별 사람 검수·도시 자료 확대는 중단한다. 기존 3곳의 39개 주장은 보존하며 검수 완료로 승격하지 않는다. 자료 형식 v3, `city-format.md`, 핵심 설계 4.2·12절과 D3 완료 정의의 최종 개편은 결과 뒤에 한다. 이 실험에서는 초안을 사용할 수 있으며 앱에 노출하거나 확대 관문 통과 자료로 사용하지 않는다.

## 비교 방식

- A: 파일럿 20곳의 허용 ID·이름·나라만 제공한다.
- B: A와 같은 목록에 도시별 가벼운 프로필 초안을 추가한다. 초안은 상위 모델(Claude Opus 5.5)이 고정된 [작성 지침](../../data/exploration/profile-prompt.md)만 보고 쓴 것이며 실행 전 사람 보정은 하지 않는다. 프로필에는 범위, 대표 경험·장소, 추천을 바꾸는 중요 제약을 담되 없는 내용은 채우지 않는다. 이는 실험 입력안이며 운영 스키마 확정이 아니다.
- C: 기존 엄격한 3곳 자료는 파일 크기·입력 크기와 유효 근거 수만 기록한다. 현재 사람 검수 0개이므로 사용 가능한 근거 0개다. LLM 호출·선택 품질·답변 불능 비교에 포함하지 않는다. 토큰 수는 선택한 모델의 직렬화·토크나이저 기준을 함께 적고 파일 바이트를 토큰으로 부르지 않는다.

후보는 [목록 v4](../../data/planning/destination-candidates.json)의 `pilot: true` 20곳이다. 원본 ID와 앱 추천 ID의 기존 연결을 적용하며 푸껫은 `th-phuket-island`로 통일한다. 양쪽의 허용 ID·이름·나라·후보 순서는 완전히 같게 고정한다. 정답 힌트·평가용 공식 출처는 입력에 섞지 않는다.

모델 버전, 생성 설정, 시스템 규칙, 출력 제한, 사용자 사례, 실행 도구는 A/B가 같다. 차이는 프로필 추가뿐이다. A도 일반 지식을 사용할 수 있고 B도 프로필 밖 안정적 사실을 말할 수 있다. 두 방식 모두 미확인 변동·안전 정보나 필수 조건 충족을 단정할 수 없다. 자동 웹 검색·외부 도구는 사용하지 않는다. 링크를 출력하도록 요구하지 않으며 검수되지 않은 URL을 생성하면 별도 오류로 기록한다.

프로필의 경험 분류가 필요하면 기존 9개 분류 ID를 재사용한다. 모든 도시에 모든 분류를 채우지 않으며 `meeting_people`을 밤 문화나 동행으로 대체하지 않는다. 단순 규칙과의 비교는 이후 실험으로 남긴다.

## 모델과 실행 설정

- 실험 모델은 Claude Haiku 4.5(`claude-haiku-4-5`) 하나로 고정한다. Haiku가 추천을 더 잘한다는 근거로 고른 것이 아니다. 소형 등급 후보 사이의 우열이 확인되지 않아 하나를 고정했다. 운영 모델은 확정하지 않는다.
- 추론(thinking)은 켜지 않고 프롬프트 캐시도 사용하지 않는다. 입력·출력 토큰을 그대로 측정하며 캐시 효과는 운영 비용 추정에서 따로 다룬다.
- 2026-10-06 [공식 단가](https://platform.claude.com/docs/en/about-claude/pricing)는 100만 토큰당 입력 US$1, 출력 US$5다. 호출 전에 다시 확인한다. 72호출 비용은 아직 계산하지 않았으며 첫 호출의 실제 사용량으로 확인한 뒤 나머지를 실행한다.
- 사용자 문장은 한국어만 사용한다. 앱은 영어·한국어로 시작할 계획이지만 이 실험은 영어 입력을 측정하지 않는다. 언어 비교는 [기존 비교 실험](offline-evaluation.md)의 별도 항목으로 남긴다.
- 결론은 이 모델·한국어 입력에 한정한다. 프로필 효과는 모델에 따라 달라질 수 있으므로 다른 모델로 일반화하지 않는다.

이후 순서는 다음과 같다. 이 실험으로 잠정 프로필을 고정한 뒤 같은 사례·프로필로 Gemini Flash와 비교한다. 운영 모델은 제약·사실·형식 검사를 통과한 모델 중 실제 사용자가 더 자기 취향에 맞다고 평가한 쪽으로 정하고, 품질 차이가 불분명하면 비용·지연으로 정한다. 실제 사용자 평가에 넣을 모델과 이 선택 규칙은 [확대 관문](offline-evaluation.md#100곳-확대-관문)에 따라 실행 전에 고정한다. 상위 모델(Sonnet·Opus 등)은 두 소형 모델의 품질이 부족할 때 원인 구분용으로 추가한다.

## 측정 범위와 보정 대상

- 입력 후보는 20곳이지만, 상세 질문과 사전 평가 쟁점은 푸껫·퀸스타운·케언스·밴쿠버·도쿄 5곳에 집중된다. 나머지 15곳은 입력 토큰·초안 작성 비용에 포함된다. 추천에 등장하면 그 응답도 검수하되, 우연히 노출된 사례로 20곳 전체 프로필의 효과를 주장하지 않는다.
- S1·S2·S3·S6은 추천 요청부터 특정 도시를 고려하거나 체류한다고 말한다. S4도 푸껫을 명시하고 대안을 허용하므로 도시 언급 없는 열린 선택 과제는 S5뿐이다. 대부분은 지정·고려 도시의 조건 설명과 제약 처리 실험이며 열린 추천 선택 품질을 검증하지 않는다.
- 대표 경험·장소의 일반적인 가치를 판정하기에는 사례가 부족하다. 범위·제약 개선을 경험 정보 전체의 효과로 해석하지 않으며, 차이를 찾지 못했다고 경험·장소 정보를 제거하지 않는다.
- 실행 전 사람 보정은 하지 않는다(v4 변경). 가장 비용이 적은 방식인 AI 초안 프로필만으로 충분한지 먼저 본다. 20곳 모두 사람 승인 자료가 아니며 ID·필드 형식 등 기계 검사만 공통 적용한다.
- 초안 작성자는 시험 사례와 평가 쟁점을 보지 않는다. 작성 지침에는 도시 목록·기존 범위안·형식만 넣는다. 기존 범위안(푸껫 본섬, 퀸스타운의 밀퍼드사운드 제외 등)은 사례보다 먼저 정한 편집 결정이므로 프로필에 포함한다.
- 사람 작업은 응답을 공식 출처와 대조하는 검수에 집중한다. 사람 보정 시간은 이번에 측정하지 못한다. 사용자가 실행 뒤 프로필을 확인해 발견한 오류는 결과 해석에 기록하되 이번 실행의 입력을 소급 수정하지 않는다.

## 합성 사례 6개

아래 사용자 문장을 공통 입력으로 고정한다. 추천 요청과 상세 질문은 서로 독립된 호출이며 상세 질문은 추천 결과와 무관하게 같은 지정 여행지를 묻는다. 각 상세 호출에 같은 사용자 조건을 다시 제공한다. 이전 생성 응답을 입력에 넣지 않아 추천 후보 차이가 상세 답변 조건을 바꾸지 않게 한다.

### S1 — 푸껫 본섬과 주변 섬

- 사용자: “바다 풍경을 보고 쉬고 싶어요. 푸껫을 고려하지만 이번에는 본섬 안에서만 다니고 배를 타지 않을 거예요. 이 조건에 맞는 후보를 골라주세요.”
- 상세: “푸껫 본섬만 다니는 조건인데 피피섬 체험도 포함해도 돼요? 배를 타야 하나요?”
- 평가 쟁점: 본섬과 주변 섬 혼합, 명시한 배편 제외 위반. 장소 범위와 이동 필요를 구분한다. 푸껫 추천 자체를 정답으로 강제하지 않는다.

### S2 — 퀸스타운과 밀퍼드사운드

- 사용자: “호수와 산 풍경을 느긋하게 보고 싶어요. 퀸스타운을 고려 중이고 하루 왕복 이동은 합쳐 2시간까지만 원해요. 밤에는 같은 숙소로 돌아와야 해요.”
- 상세: “이 조건으로 퀸스타운에서 밀퍼드사운드를 당일에 여유롭게 다녀올 수 있나요?”
- 평가 쟁점: 사용자의 이동 상한과 당일 가능을 구분한다. 근거 없이 시간을 채우거나, 가능한 모든 교통수단에 대해 당일 불가능이라고 단정하는 답도 점검한다. 현행 여행지 범위와 경로·수단별 조건을 대조한다.

### S3 — 케언스 출항 리프 체험

- 사용자: “산호초와 바다 풍경을 보고 싶어요. 케언스에 머물고 배는 탈 수 있지만 다른 도시로 이동해 출항하거나 선상 숙박은 원하지 않아요.”
- 상세: “케언스에서 출항해 같은 날 돌아오는 리프 체험을 생각 중이에요. 사전 예약이 필수인가요?”
- 평가 쟁점: 출항 거점·숙박 조건을 보존하는지, 특정 상품이 정해지지 않았는데 예약 필수/불필요를 단정하는지 확인한다. 리프 전체나 다른 항구 상품을 케언스 경험으로 합치지 않는다.

### S4 — 몬순기 해수욕

- 사용자: “9월 여행은 바다 수영이 가장 중요해요. 푸껫도 고려 중이지만 수영을 못할 가능성이 큰 조건이면 다른 후보를 원해요.”
- 상세: “9월의 푸껫 까따 해변에서 수영해도 안전한가요? 빨간 깃발이 없으면 괜찮다고 보면 되나요?”
- 평가 쟁점: 일반 계절 위험과 방문일 상태를 구분하고 안전을 보장하지 않는지 확인한다. 사용자 의도에 필요한 유의점이 빠졌는지도 별도로 센다. 단순히 모든 수영을 불가능하다고 하는 답을 정답으로 두지 않는다.

### S5 — 새로운 사람 만나기

- 사용자: “혼자 여행하면서 새로운 사람과 대화하고 싶어요. 술자리·클럽은 싫고 낮에 참여하는 활동을 원해요. 동행이 없다는 이유로 혼자 조용히 쉬는 여행을 추천하지는 말아주세요.”
- 상세: “밴쿠버에서 낮에 참여할 수 있는 활동을 택하면 새로운 사람을 만날 수 있다고 보장할 수 있나요?”
- 평가 쟁점: `meeting_people`을 음주·밤 문화·기존 동행으로 치환하지 않는지, 상호작용 기회와 만남 보장을 구분하는지 확인한다. 근거 없는 특정 모임의 현재 운영·참가 가능을 점검한다.

### S6 — 안정적 경험과 변동 예약 정보

- 사용자: “전통 건축과 동네 산책을 좋아해요. 도쿄도 고려하고 있어요. 자유롭게 걷는 경험이 좋고 시설 내부 관람은 필수가 아니에요.”
- 상세: “아사쿠사에서 가미나리몬·나카미세·센소지 주변을 걸으려면 예약해야 하나요? 상점과 내부 시설도 같은 조건인가요?”
- 평가 쟁점: 거리 탐방과 시설·상점 이용을 구분한다. 안정적 경험을 답할 수 있는지 보면서 예약·현재 영업을 일괄 단정하지 않는지 확인한다. 다른 5개 사례의 범위·제약 집중에 대한 대조 사례다.

평가용 기대 판단과 출처는 호출 전에 별도 고정한다. 위 쟁점은 출처 검수 완료 사실이나 모범 답안이 아니다. 예상한 위험은 6개 상세 질문 모두에 있으므로, 모델이 관련 도시를 추천하지 않아도 상세 평가 기회가 사라지지 않는다.

## 출력과 호출 수

- 추천: 후보 최대 2곳. 후보마다 사실 최대 2문장과 유의점 1문장을 별도로 받는다. 개인화 이유는 이 문장 안에서 사용자 입력과 연결한다. 유의점 안의 사실도 검수한다.
- 상세: 직접 답변 최대 2문장과 확인 필요·적용 한계 1문장. 한 문장에 여러 사실을 묶지 않도록 요청한다. 미확인을 숨겨 문장 수만 맞추지 않는다.
- 기본 실행: 6사례 × 2방식 × 2과제(추천·상세) = 24호출/응답 슬롯. 후보 순서는 A/B 동일, 실행 순서는 사례별 A/B와 B/A를 번갈아 사용한다.
- 결과가 갈린 사례만 양쪽의 추천·상세를 각각 2회 더 실행한다. 사례당 추가 8호출, 최대 48호출 추가. 전체 상한은 72호출이다.
- 자동 재시도는 하지 않는다. 실패·빈 응답·잘림·형식 초과를 그대로 기록한다. 기술 실패가 있으면 해당 쌍은 미판정이며 좋은 응답만 골라 대체하지 않는다. 필요한 재실행은 새 계획·예산으로 분리한다.

72호출 기준으로 입력·출력 상한, 추론 토큰 등 제공자 과금 항목을 포함해 비용을 계산한다. 첫 외부 파일럿 US$10 상한은 이 탐색 실행과 공유하며 별도 US$10을 추가하지 않는다. 기존 지출·잔여 한도를 확인하고 충분하지 않으면 호출 전에 계획을 수정한다. 상한 때문에 반복을 끝내지 못한 사례는 미판정으로 남긴다.

## 사람 대조와 측정

생성 방식 이름을 숨긴 응답을 자체 검수자가 공식 출처와 대조한다. 프로필 자체를 정답으로 쓰지 않는다. 사람이 프로필도 보정했다면 완전한 눈가림이 불가능함을 기록한다. 모든 원본 응답을 보존하고 검증기에 차단된 결과도 평가·비용 기록에서 빼지 않는다.

- 사실 판정: 맞음 / 틀림 / 확인 불가. 주장별 출처·대조일·이유를 결과 로그에 적는다. 입력에 없는 것만으로 틀림이라고 판정하지 않는다.
- 자료 밖 사실: B의 사실 중 프로필이 뒷받침하지 않는 비율이다. A에서는 N/A로 기록한다. A의 허용 ID·후보 밖 위반은 별도로 검사한다. 사용자 진술과 순수 조언은 도시 사실 분모에 넣지 않는다.
- 사실 오류: 틀린 주장 수 / 대조 가능한 주장 수와 오류 응답 수 / 대조 가능한 응답 수를 함께 기록한다. 확인 불가 수·전체 주장 수·빈 응답·기술 실패를 함께 보여주며 확인 불가를 정상으로 세지 않는다.
- 중요한 제약: 사전 쟁점별 충족 / 위반 / 판단 불가를 기록한다. 상세는 방식당 고정된 6개 평가 기회다. 추천에서는 해당 제약과 관련된 후보·경험을 제시한 기회 수를 분모로 쓴다. 필요한 유의점 누락도 별도 기록한다. 분모 0은 N/A다.
- 상세 답변 불능: 핵심 질문에 직접 답하지 못한 상세 응답 수 / 반환된 상세 응답 수. 부분 답변은 별도 분류한다. 모름을 적절히 밝힌 경우도 답변 범위에는 반영하되 오류로 취급하지 않는다. 안전 보장처럼 애초에 보장할 수 없는 요청은 그 한계를 정확히 설명하면 답변한 것으로 본다. 기술 실패는 답변 불능에 합치지 않는다.
- 호출: 실제 입력/출력/추론/캐시 토큰, 제공자 사용량, 실제 비용, 요청부터 완료까지 지연, 응답 길이. 시간대·혼잡 변동이 있으므로 1회의 지연 차이를 안정적 성능 차이로 해석하지 않는다.
- 사람 비용: 프로필 초안 작성·사람 보정·평가용 출처 준비·응답 사실 대조에 쓴 실제 시간을 각각 기록한다. 작업하지 않은 단계는 미실행으로 두고 시간을 추정하지 않는다.

출력 상한 내 기본 실행은 최대 108문장, 전체 72호출은 최대 324문장을 대조하는 규모다. 문장에 여러 사실이 들어 있거나 제한을 넘으면 실제 주장 수와 추가 검수 시간을 기록한다. 검수 중 정한 시간 한도에 도달하면 미검수는 확인 불가로 남기고 결론을 보류한다. 전수 대조하지 않은 응답을 정상으로 승인하지 않는다.

## 차이가 난 사례와 반복 판정

첫 실행의 사례 단위 비교는 추천·상세를 함께 묶어 다음 순서로 평가한다.

1. 허용 ID·제외·필수 조건 위반 또는 미확인 안전/변동 정보의 단정이 적은 방식.
2. 위가 같으면, 공식 출처로 확인된 틀린 사실이 적고 확인 불가·유의점 누락이 더 많지 않은 방식.
3. 위가 같으면, 새로운 사실 오류·확인 불가를 늘리지 않고 핵심 상세 질문을 더 직접적으로 답한 방식.

한 방식이 일부 지표에서 좋고 다른 지표에서 나쁘면 혼합, 대조 부족·기술 실패가 있으면 미판정이다. 후보 이름·문체·토큰 수만 다른 것은 반복 대상 차이가 아니다. A 우세/B 우세/혼합 사례를 모두 반복하며 유리한 방향만 선택하지 않는다. 첫 실행 동률·미판정은 이 계획에서 반복하지 않는다.

총 3회 중 같은 방향이 2회 이상이면 그 사례에 한해 일관된 방향으로 기록한다. 반대 방향·혼합·실패도 함께 보고한다. 첫 결과로 선택한 반복 표본이므로 3회를 독립 표본처럼 합산하거나 통계적 유의성·일반적 우월성을 주장하지 않는다. 프로필이나 프롬프트를 반복 사이에 고치지 않는다.

## 결과가 자료 형태로 이어지는 규칙

- B 우세가 서로 다른 2개 이상 사례에서 위 반복 기준을 충족하고, A의 일관된 우세 사례가 없으며 B가 새로 만든 중요한 제약 위반이 없으면: 해당 5곳·평가 쟁점에서 프로필 추가가 도움이 된 신호로 기록한다. 범위·중요 제약 중 어떤 입력 차이가 기여했는지 사람이 대조하며 추정은 추정으로 남긴다. 대표 경험·장소의 일반적 가치나 개별 필드의 인과 효과는 이 실험으로 확정하지 않는다.
- B의 이득이 범위·중요 제약에만 나타나면: ID·범위·중요 제약 중심으로 줄이는 안을 우선한다. 대표 경험·장소의 추가 가치가 입증되거나 불필요해졌다고 하지 않는다. 단순 규칙 기준선(E1)의 경험 분류와 호출 없는 상세 기본 정보는 별도 용도로 유지·평가한다.
- 양쪽 모두 오류가 없고 상세 답변 범위도 같거나 일관된 차이가 없으면: 이 사례에서 차이를 발견하지 못한 것이다. 효과 없음의 증명은 아니다. 이번 범위·제약 과제의 추가 입력은 최소 자료를 잠정 기본안으로 두되, 경험 분류·대표 장소의 제거 근거로 쓰지 않는다. 단순 규칙 기준선(E1)과 호출 없는 상세 기본 정보의 자료 요구는 별도다. 100곳 확대·현재 사용자 품질 승인은 하지 않는다.
- 이득·새 오류가 섞이거나 B 우세가 1개 사례뿐이면: 그 항목만 보완 대상으로 남기고 별도 고정한 재시험을 준비한다. 전체 프로필 확장은 보류한다.
- 프로필의 틀린 내용에서 비롯된 응답 오류가 확인되면: 해당 항목만 사람이 보정해 같은 사례로 재시험한다. AI 초안만으로는 그 항목에 부족하다는 결과로 기록한다.
- 확인 불가·미검수·기술 실패·예산 부족으로 판단할 수 없으면: 미판정이다. 무차이·성공으로 처리하지 않는다.

모든 경우에 작성·보정·대조 시간을 함께 보고한다. 20곳에서 100곳으로 단순 5배 환산한 수치는 시나리오 추정일 뿐 실제 운영비가 아니다. 낮은 API 비용만으로 프로필 방식을 채택하지 않는다.
