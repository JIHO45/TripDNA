## 추천 단위와 입력

도시를 중심으로 추천하고 나라는 위치·묶음 정보로 둔다. 나라를 먼저 고르는 필수 단계는 없다. 사용자가 특정 나라·도시를 조건으로 정한 경우에만 그 범위를 적용한다. 후보의 식별은 [후보 계약](../README.md#candidates), 조건의 의미와 우선순위는 [사용자 기억](../README.md#memory)을 따른다.

추천 경험의 범위는 **한 번의 여행에서 함께 경험할 수 있는 여행권**으로 설명한다. 도시 중심 식별은 유지하되 행정 경계나 같은 나라라는 이유로 먼 경험들을 한 후보에 합치지 않는다. 여행권은 새 후보 ID 체계를 만드는 뜻이 아니다.

경험 제공 여부는 명소의 존재만으로 판단하지 않는다. 그 경험 묶음에 필요한 최소 체류 기간·이동 수단과 적용 범위를 근거에 연결하고, 예약 필요·혼자 참여 가능·차량 필요처럼 확인 가능한 접근 조건을 다룬다. 조건은 예·아니요·미확인을 구분하며, 미확인을 ‘아니요’나 조건 충족으로 바꾸지 않는다. 최소 일수는 도시 전체의 고정값으로 추정하지 않는다. 이 원칙은 자료나 검색 결과의 해석 기준이며 보류한 전체 프로필 제작을 재개하는 지시가 아니다.

입력은 활성 사용자 증거, 이번 조건, 방문 정보, 제외, 허용 후보와 입력 버전이다. 정보가 부족하면 탐색 제안임을 구분하고 날짜·예산 등 추가 답변을 첫 추천의 필수 관문으로 만들지 않는다.

## 매칭 원칙

사용자의 원하는 경험과 여행지에서 접근 가능한 경험을 연결한다. 사람과 여행지에 같은 성향 벡터를 붙여 가까운 곳을 찾지 않는다. 이번 요청에 따른 제외 예외를 반영한 뒤, 실제 추천 카드에는 유효한 제외·필수 조건 검사를 적용한다. LLM 입력을 조건으로 먼저 줄일지는 [미정](#미정)이다. 명시적 우선순위는 보존하며 순위 결정과 코드 계산의 역할은 [순위 계산](#순위-계산)을 따른다.

계획성 자체는 여행지 순위 계산에서 제외한다. “예약 필수 체험은 피하고 싶다”, “운전할 수 없다”처럼 직접 밝힌 조건은 계획형/즉흥형 점수로 바꾸지 않고 해당 경험의 접근 조건과 대조한다.

구분할 근거가 없는 후보는 동점 또는 우열을 판단하기 어려운 후보로 보여준다. 표시 순서만으로 더 잘 맞는다고 설명하거나 임의의 점수 차이를 만들지 않는다. 미확인 필수 조건은 충족으로 승인하지 않으며 처리는 [확인 불가 원칙](sources.md#확인-불가와-표현)을 따른다.

## 처리 흐름과 책임

1. 현재 입력과 유효한 저장 결과가 일치하면 재사용한다.
2. 이번 요청, 계속 제외와 이번 여행 예외, 후보별 확인 가능한 조건을 준비한다. 자연어의 모호함을 임의의 강한 필터로 바꾸지 않는다. 입력 후보의 사전 필터 범위는 [미정](#미정)이다.
3. 모델이 위 매칭 원칙에 따라 후보 선택·추천 이유·자유문장 피드백 해석을 담당한다. 실험별 자료 접근 권한은 [평가 계획](../README.md#evaluation)을 따른다.
4. 코드가 허용 ID·중복·이번 여행 예외를 반영한 제외·출력 형식·입력 버전과 확인 가능한 조건을 검사한다. 목록 밖의 “생각 중인 곳”과 등록 초안은 추천 카드와 구분한다. 필요한 값이 검증되면 시간·비용 합산은 코드로 계산한다. 미확인 값을 계산해 확인된 사실로 바꾸지 않는다.
5. 표시 직전 앱이 최신 입력·제외를 다시 확인한다. 출처와 표현의 허용 범위는 [근거 계약](../README.md#sources)을 따른다.

링크나 ID가 존재하는 검사는 문장과 근거의 의미 일치를 보장하지 않는다. 내부 ID·프로필 용어 노출도 출력 검사 대상으로 두되 문자열 검사로 모든 의미 오류를 잡는다고 주장하지 않는다.
모델이 DB를 직접 수정하지 않는다. 명시 버튼은 코드로 처리하고 자유문장 해석만 모델에 맡긴다. 사용자 문장·검색 페이지·자료를 시스템 지시로 실행하지 않는다.

## 재생성·실패

취향·조건·제외·후보·자료 또는 출처 유효성·모델·프롬프트 변경이 결과에 영향을 주면 관련 결과를 무효화한다. 탭 재진입마다 새 호출하지 않는다. 2026-10-08: 무효화된 결과도 자동으로 다시 만들지 않고, 사용자가 “추천 다시하기”를 누를 때 새로 만든다. 검색 기반 결과의 유효기간은 정보별 변동성을 고려해 채택 전에 정하며 아직 정하지 않은 영구 재사용 기간을 가정하지 않는다.

제외는 저장 성공 후 즉시 화면에 반영한다. 기본안은 그 자리만 대체하고 다른 유효 카드는 유지하는 것이다. 핵심 목적·조건이 바뀌면 전체를 재평가한다. 생성 실패가 저장된 제외를 취소하지 않는다.

- 조건이 바뀐 뒤 도착한 이전 응답은 폐기한다.
- 실패·오프라인·호출 한도에서는 현재 조건을 여전히 만족하는 유효 결과만 재사용한다. 없으면 실패와 재시도 경로를 표시한다.
- 예산·시기·기간에 맞는 도시가 모자라면 [조건](#조건)의 규칙대로 그 수만 보여준다. 제외를 임의로 푸는 대체 추천은 하지 않는다. 사용자가 이번 요청에서 명시한 경우는 임의가 아니다.
- 2026-10-08의 기본 흐름은 추천받기당 LLM 한 번이다. 이전의 “검증 실패 시 자동 재시도 최대 1회” 기본안은 이 흐름에 자동 적용하지 않는다. 실패·재시도의 횟수 차감과 추가 호출 허용은 [미정](#미정)이며, 실험은 [평가](../README.md#evaluation)의 고정 계획을 따른다.

## 2026-10-07 추가 결정: 구독, 자료 배포, 저장

[실행 5 부분 결과](../../data/exploration/runs5/result-partial.md)의 비용 측정 뒤에 사용자가 정했다. 실험이 끝나기 전의 결정이며, 모델·검색 구성의 채택은 여전히 평가 뒤에 한다.

**LLM 기능에 구독을 도입한다.**

- LLM을 쓰는 추천과 질문 답변이 대상이다. 계기는 검색을 쓰는 호출의 원가다(Haiku 기준 추천 약 US$0.085, 상세 약 US$0.039, 검색 없는 호출은 약 US$0.002).
- 2026-10-08 변경: LLM을 구독자에게만 제공하고 무료 사용자에게는 쓰지 않는다는 2026-10-07 결정을 철회했다. 무료·구독 사용자의 LLM 사용 범위와 한도는 미정이다.
- 가격, 상품 형태(월 구독, 기간제 이용권 등), 사용량 한도는 미정이다. 구독을 뺐던 이전 판단의 근거는 태그 `docs-versioned-2026-10-07`의 `docs/v1/project.md`에 있다.
- 로그인을 필수로 만들지 않는 원칙은 유지한다.

**도시 자료는 앱 번들로 배포한다.**

- 후보 목록(약 100곳)과 채택되는 도시 자료를 앱 번들에 넣고 앱 업데이트로 갱신한다. 서버에서 내려받는 구조와 서버 DB는 두지 않는다.
- 번들 자료는 앱 업데이트 사이에 바뀌지 않는다. 가격·운영 시간·시즌 일정처럼 자주 바뀌는 사실은 번들에 넣지 않고, 필요하면 검색으로 확인한다.
- 번들에 담을 새 자료의 내용은 [도시 등급](#도시-등급)과 [LLM 호출과 횟수](#llm-호출과-횟수)를 따른다. 세부 파일 형식은 미정이며 기존 상세 프로필과 같은 형식이라고 가정하지 않는다.

**여행 기록·도시 자료·검색 결과의 외부 DB는 두지 않는다.**

- 사용자 기록은 기기에만 둔다. LLM을 부를 때 필요한 내용을 기기에서 꺼내 함께 보낸다.
- 검색으로 확인한 사실을 여러 사용자가 재사용하는 공용 저장소도 지금 만들지 않는다. 원가를 낮추는 수단으로 나중에 검토할 수 있다.
- LLM 호출 서버는 여전히 필요하다. API 키를 앱에 넣을 수 없고 구독 여부를 확인해야 하기 때문이다.
- 사용량과 목록 밖 도시 요청의 서버 저장 범위는 아래 Firebase 결정에 따른다. 한도·차감·집계·보관·삭제의 세부 규칙은 미정이다.

**서버와 서버 저장에는 Firebase를 쓴다.**

- LLM 호출 중계는 Cloud Functions, 서버 저장은 Firestore로 한다. 사용자가 2026-10-07에 정했다. 나중에 사용자 평가를 모을 자리까지 같은 곳에 두기 위해서다.
- Firebase는 2026-09-10에 로컬 저장으로 바꾸며 뺐고 이후 제품 범위에서 제외해 왔다. 기록된 이유는 “당시 로컬 저장 선택”이며, 같은 날 구독을 빼고 목표를 출시·유입으로 바꿨다. 구독과 사용자 평가 수집이 다시 계획에 들어오면서 그 전제가 달라졌다.
- 이 결정은 제품 선택이다. 2026-10-07의 포괄적인 “외부 DB를 지금 두지 않는다”는 범위를 2026-10-08에 좁혔다. 사용자 기록은 기기에, 도시 자료는 앱 번들에 둔다. Firestore에 들어갈 수 있는 것은 사용자별 사용 횟수와, 2026-10-08에 더한 요청된 목록 밖 도시의 이름이다. 사용자 평가의 수집은 출시 후 별도 결정이다.
- 로그인 화면 없는 사용자 식별에는 Firebase 익명 로그인을, 정식 앱에서 온 요청인지 확인하는 데는 App Check를 쓴다.
- 구독 확인은 앱이 보낸 구매 정보의 서명과 만료일을 Cloud Functions에서 애플 공식 라이브러리로 검증한다. 구독 관리 서비스는 붙이지 않고 시작하며, 환불·가족 공유 등 예외 처리가 커지면 다시 본다.
- 알려진 한계: Firestore는 여러 조건으로 묶어 세는 집계 질의에 약하다. 칸별 평가 수는 저장 시점에 따로 세어 두거나 밖으로 내보내 계산해야 한다. 요금은 읽기·쓰기 횟수에 따라 붙고, Cloud Functions에서 외부 API를 부르려면 종량 요금제가 필요하다. 현재 요금과 한도는 확인하지 않았다.

## 2026-10-08 결정: 컨셉 기반 추천

상태: 사용자 결정과 PC 계산에 근거한 설계. 앱 미구현. 근거 기록은 [충족률 계산](../../data/exploration/coverage-check/result.md), [두 단계 컨셉 계산](../../data/exploration/coverage-check/result-v2.md), [칩 대 LLM 비교](../../data/exploration/chips-vs-llm/result.md)다. 세 기록 모두 미검수 등급표와 AI 한 명의 판정에 기댄 잠정 결과이며, 추천이 취향에 맞는지는 검증하지 않았다.

컨셉과 티어의 의미는 [사용자 기억](memory.md#컨셉과-티어), 화면 동작은 [추천 화면](../screens/recommendations.md)이 담당한다.

### 흐름

2026-10-08 재정리: 같은 날 먼저 적은 “자유문장이 없으면 LLM을 부르지 않는다”, “LLM이 고르지 않은 도시를 추가 후보로 채운다”를 철회했다. 카드마다 개인화한 이유와 유의점을 쓰려면 호출이 필요하고, LLM 없이 만든 카드는 품질을 위해 내지 않기로 했다.

1. **입력.** 추천 탭에서 이번 여행의 주 컨셉 하나를 반드시 고른다. 세부, 함께 하고 싶은 것(부 컨셉 최대 2개), 조건(시기·기간·예산), 다녀온 곳 포함 여부, 자유문장은 선택이다. 화면에서는 ‘주 컨셉·부 컨셉’이라는 말을 쓰지 않는다.
2. **호출.** “추천받기”를 누르면 LLM을 한 번 부른다. 보내는 것은 컨셉, 조건, 자유문장, 티어, 최근 여행 평가(도시별 별점과 메모 원문), 제외 목록, 도시 목록의 압축 표(이름과 등급)다.
3. **응답.** LLM은 요청을 어떻게 이해했는지의 요약, 순위를 매긴 도시들, 도시마다 이번 요청에 맞는 이유와 안 맞을 수 있는 점·확인할 조건, 이번에 반영한 기억, 해석이 기대는 조건(예: 시기)을 돌려준다.
4. **검증과 표시.** 코드가 허용 ID·제외·조건을 검사하고 카드를 최대 3장 보여준다. 카드의 “여기서 즐길 핵심 경험”은 LLM이 매번 쓰지 않고 저장된 도시 자료에서 꺼낸다.
5. **조건 수정.** 시기·기간·예산을 바꾸면 받아 둔 도시들을 코드가 다시 거른다. 호출하지 않고 횟수도 쓰지 않는다.

이번에 명시한 요청은 과거 기억과 제외보다 우선한다. 예전에 일본을 제외했어도 이번에 일본 여행을 요청하면 확인을 묻지 않고 이번 여행에 한해 일본을 포함하며, 그 사실을 알린다. 계속 제외 설정 자체는 지우지 않는다.

LLM을 쓸 수 없으면(오프라인, 호출 실패, 한도 소진) 새 추천을 받을 수 없다. 이미 받은 카드는 [재생성·실패](#재생성실패)의 유효성·삭제·제외 규칙 안에서 재사용한다. 오프라인이라는 이유로 무효화된 설명이나 삭제한 기억을 되살리지 않는다.

이미 갈 곳을 정한 사용자는 추천이 아니라 [여행 등록](../screens/trip-registration.md)으로 들어간다.

### 순위 계산

순위는 LLM이 정한다. 아래 순서는 PC 계산에 쓴 코드 규칙이며, LLM에 주는 참고 순서나 응답 검증으로 쓸지는 [미정](#미정)이다.

1. 주 컨셉이 2등급 미만인 도시를 뺀다.
2. 주 컨셉의 등급(세부를 골랐으면 그 세부의 등급), 그다음 부 컨셉 등급의 합으로 순서를 정한다.
3. 동점이면 티어로 푼다. 1·2·3티어의 가중치는 3·2·1이다. 3티어도 약한 긍정으로 계산에 넣는다.
4. 그래도 같으면 동점으로 보여준다.

티어에 놓지 않은 컨셉은 점수에 넣지 않는다. 도시를 내리거나 빼지 않는다. 티어는 추천 화면에 다시 보여주지 않고 계산과 LLM 입력에만 쓴다. 매칭 백분율은 표시하지 않는다. 순위 차이를 설명할 근거가 없으면 1·2·3위를 붙이지 않고 후보의 차이를 설명한다.

### 도시 등급

- 도시마다 큰 컨셉과 세부에 네 단계의 등급을 둔다. 숫자가 아니라 이름으로 적는다. 판정할 때는 앞에 “이 경험을 좋아하는 여행자에게”를 붙여 읽는다.
  - **여행지를 선택할 만함**: 그 경험을 위해 이 여행지를 고를 만하다.
  - **일부러 시간을 낼 만함**: 여행 중에 일부러 시간을 내어 즐길 만하다.
  - **간다면 즐길 만함**: 그곳에 간다면 함께 즐길 만하다.
  - **찾지 못함**: 추천할 만한 경험을 아직 찾지 못했다. 내부 자료용이며, 그 경험이 없다는 증명이 아니므로 사용자에게 “없는 도시”라고 말하지 않는다.
- 이 문서와 실험 기록의 “3·2·1·0등급”은 위 네 이름의 이전 표기다. “주 컨셉 2등급 이상”은 “일부러 시간을 낼 만함 이상”을 뜻한다.
- 도시 등급과 사용자 티어는 다른 것이다. 티어는 사용자가 놓는 것이고 1티어가 가장 원하는 것이다. 이전 표기에서는 도시 등급의 숫자가 클수록 높아 방향이 반대였다. 화면에는 티어만 보이고 도시 등급은 보이지 않는다. LLM 입력에서 둘이 섞이지 않게 도시 등급은 이름으로 보낸다.
- 등급은 도시의 성격 점수가 아니라 “그 경험을 거기서 얼마나 잘 할 수 있는가”다. 사용자 쪽 값(원하는 것)과 뜻이 다르며 둘의 거리를 재지 않는다.
- 큰 컨셉의 등급은 그 아래 세부 등급의 최댓값이다.
- 등급은 그 경험이 가능한 시기에 갔을 때의 수준이다. 행사가 열리거나 시설이 운영되는 달이 정해진 세부는 그 달을 숫자로 따로 저장하고, 사용자가 시기를 넣었으면 코드가 그 달로 거른다. 달은 그 세부의 핵심 경험 문장에 적은 경험들의 달을 합친 범위다. 달이 제한될 것 같은데 확인하지 못한 세부는 비워 두지 않고 미확인으로 표시한다. 달이 없는 세부(제한 없음)와 미확인 세부는 다르며, 시기 조건이 있는 추천에서 미확인 세부를 조건 충족으로 치지 않고 확인이 필요하다고 알린다. 시기가 주어지면 시즌 밖 세부를 뺀 나머지로 큰 컨셉 등급, 부 컨셉 합산, 보여줄 핵심 경험을 계산한다(예: 축제 세부의 달이 5·7·10월로 저장된 도시는 6월에 축제를 빼고 이벤트 등급을 구한다). 시즌 밖 세부가 있다는 이유만으로 도시를 빼지 않는다. 달은 후보를 좁히는 조건일 뿐 그날 행사가 있다는 확인이 아니다. 특정 날짜의 경기·공연은 자유문장이 맡고, 카드에는 날짜 확인이 필요하다고 알린다. 우기처럼 날씨에 따른 시기는 이 달에 넣지 않고 월별 기후 자료로 다룬다.
- 등급은 그 도시 여행으로 자연스럽게 묶이는 범위에서 매긴다. 같은 숙소를 거점으로 당일에 그 경험을 할 수 있고 그 도시 여행의 흔한 일정인지를 본다. 별도 목적지로 다녀오는 근교(예: 도쿄의 하코네)는 등급의 근거에 넣지 않고 근교 경험으로 따로 적는다. 근교를 전부 넣거나 전부 빼지 않는다. 범위는 사람이 판단하며, 등급이 갈리는 경계 사례만 기록한다.
- 검수는 후보 진입을 바꾸는 1↔2 경계와 주 컨셉 순서를 바꾸는 2↔3 경계부터 한다. 0↔1도 부 컨셉 합산에 영향을 주지만 우선순위가 낮다.
- LLM으로 초안을 만들고 사람이 검수한다. 지금 있는 것은 파일럿 20곳의 미검수 초안뿐이다.
- 출시 후보는 100곳 이상으로 한다(사용자 결정). 추천 품질을 위해 줄이지 않는다.
- 도시 × 컨셉마다 “여기서 즐길 핵심 경험”을 한두 문장으로 만들어 저장한다. 누구에게나 같은 도시 정보이며 등급의 근거가 된다. 개인화 문장(맞는 이유, 안 맞을 수 있는 점)은 공용 도시 자료로 저장하지 않고 새 추천 때마다 쓴다. 받은 결과의 재표시를 위한 로컬 보관은 [저장 계약](../data/storage-and-privacy.md#새-구조에서-구분할-기록)을 따른다.
- 2026-10-12 변경(사용자 결정): 등급을 숫자에서 이름으로 바꾸고 뜻을 다시 적었다. 이전에는 “3은 그 경험만을 목적으로 올 만한 곳, 2는 여행의 주요 일정이 될 만한 곳, 1은 있기는 한 곳, 0은 추천 근거를 찾지 못한 곳”이었다. 바꾼 이유는 둘이다. 사용자 티어(1이 최고)와 숫자의 방향이 반대라 섞였고, “얼마나 좋은가”보다 “여행에서 어떤 비중을 둘 만한가”가 판정하기 쉽다. 뜻이 같지 않다. 가운데 단계의 문턱이 조금 낮아지고 아래 단계의 문턱이 높아지며, 축제와 대회 같은 칸은 위 단계로 올라갈 수 있다. [20곳 초안](../../data/exploration/city-draft/notes.md)은 이전 뜻으로 매긴 것이어서 다시 매겨야 한다.
- 2026-10-12 변경(사용자 결정). 근거는 [5곳 초안](../../data/exploration/city-draft/notes.md)이다.
  - 0의 뜻: 이전에는 “사실상 없는 곳”이었다. 없음을 증명하려면 칸마다 부재 근거가 필요해 100곳에서 감당할 수 없고, 0과 1의 차이는 후보 진입을 바꾸지 않아 바꿨다. 미확인 칸은 두지 않는다.
  - 이벤트 연중 기준: 이전에는 “이벤트 컨셉의 등급은 연중 볼 것이 있는 정도”였다. 이 기준으로는 교토의 축제처럼 특정 달에만 큰 경험이 낮게 매겨지고, 달을 문장에만 적으면 그 밖의 달에 추천되는 것을 막지 못해 철회했다.
  - 근교: 이전에는 정하지 않았다. 초안에서 편도 약 1시간 30분 이내를 포함했더니 도쿄가 하코네 때문에 자연 2등급이 되어 뺐다.
- 도시 이름은 한국어와 영어로 저장한다. 표기 차이와 오타는 LLM이 대응을 제안하되, 코드는 목록의 ID와 대조한다. 동명·미확인 도시를 임의로 연결하지 않고 원문을 보존한다.

### 지난 여행의 기억

- 추천 호출에 최근 여행 평가의 별점과 메모 원문을 그대로 넣는다. 보내는 양의 상한은 미정이다(논의한 값은 최근 10건).
- LLM은 여행지 선택과 관련 있는 내용만 쓴다. “날씨가 별로였다” 같은 당시 조건은 쓰지 않는다. 별점만 있고 메모가 없으면 이유를 추측하지 않는다.
- LLM이 돌려준 “이번에 반영한 기억”을 결과 화면에 “지난 여행에서 참고한 내용”으로 보여준다. 실제로 쓴 것만 보여준다.
- 메모를 미리 정리해 저장해 두는 방식은 MVP 이후에 검토한다. 지금은 평가를 저장만 한다.
- 메모가 외부로 전송되므로 [전송 안내와 동의](../data/storage-and-privacy.md#llm-전송과-서버)의 대상이다.

### 조건

- 받는 조건은 예산(최대 금액), 시기(여행 예정일), 기간이다. 동행은 여행 기록용으로 받고 순위 계산에 쓰지 않는다. 비행시간과 비자는 조건으로 받지 않는다. 나라·지역은 조건 칸을 따로 두지 않고 자유문장으로 받는다.
- 조건은 LLM에도 넘긴다. LLM은 조건을 알아야 확인할 점을 쓸 수 있다. 조건에 맞는지 판정하는 일은 코드가 한다.
- 시기는 그 날짜에 날씨가 나쁜 도시를 거르는 데 쓴다. “따뜻한 곳” 같은 날씨 선호는 자유문장으로 받는다.
- 조건에 맞는 도시가 3곳보다 적으면 그 수만 보여준다. 조건에 맞지 않는 도시로 채우지 않는다.
- 조건에 맞는 도시가 하나도 없을 때의 동작은 [미정](#미정)이다.
- LLM의 해석이 기대는 조건을 사용자가 바꾸면(예: 특정 날짜의 공연) 이전 설명을 그대로 두지 않고 다시 확인이 필요하다고 알린다.
- “이번엔 비싸요” 같은 반응은 기억으로 저장하지 않는다. 사용자가 예산 조건을 고친다.
- 예산 판정은 [루트 README](../../README.md#범위)의 제외 범위(총예산 적합 보장, 실시간 항공 가격) 안에서 대략값으로만 한다.
- 2026-10-13 결정(사용자): 예산은 맞는지를 판정해 도시를 거르는 조건으로 쓰지 않고, 후보마다 **예상 비용의 범위**를 보여준다. 이전에는 예산을 코드가 판정하는 조건으로 두었다. 바꾼 이유: 같은 도시라도 숙소와 씀씀이에 따라 비용이 크게 달라 한 사람의 예산에 맞는지를 정확히 가릴 수 없고, 제휴사의 가격을 쓰더라도 사용자가 더 비싼 방을 고를 수 있어 마찬가지다. 실험에서도 근거 없이 "예산 안"이나 "예산 초과"를 말하는 것이 문제였다([실제 메모 실행 5](../../data/exploration/memo-check/run5/result.md), [비용 확인](../../data/exploration/cost-check/result.md)).
  - 범위는 **사용자가 원하는 여행에서의 범위**다. 요청에 적힌 숙박 방식과 씀씀이를 기준으로, 아래쪽은 그 여행을 아끼는 쪽으로, 위쪽은 넉넉한 쪽으로 잡는다. 위쪽에 5성급 숙소는 들어가지만 매일 비싼 와인, 바, 고급 식당에 가는 것은 넣지 않는다. 같은 날 처음 정한 것은 "가장 싸게 가는 방식부터 납득할 만하게 비싼 방식까지"였는데, 호캉스를 원하는 사용자에게 가장 싼 숙소의 가격은 실제 선택지가 아니어서 좁혔다. 요청에 숙박 방식이나 씀씀이가 없을 때만 넓은 범위를 쓴다.
  - 범위의 양 끝도 가격에 관한 주장이다. "예상"이라고 적는 것으로 근거의 문제가 사라지지 않는다. 값이 호출마다 비슷하게 나오는지와 별개로, 일부 항목은 실제 가격과 대조해 쓸 만한지 확인한 뒤에 화면에 쓴다.
  - 항공, 숙박, 식비 같은 항목별로 보여준다. 예상이라고 밝히고 계산의 가정(기간, 인원)을 함께 적는다.
  - 예산을 충족한다거나 넘는다고 단정하지 않는다. 사용자가 적은 예산이 그 범위의 어디에 놓이는지는 보여줄 수 있다.
  - 값을 어디서 얻을지(추천 호출에서 LLM이 내는 값, 도시별로 저장한 자료, 제휴사의 가격)와 얼마나 믿을 만한지는 정하지 않았다. LLM이 내는 값은 호출마다 달라질 수 있어 먼저 재 본다.

### LLM 호출과 횟수

- “추천받기” 한 번이 추천 1회다. 조건 수정과 “다른 후보 보기”는 횟수에 넣지 않는다.
- 추천 카드 없이 여행 등록으로 이어진 호출은 횟수에 넣지 않는다.
- 무료와 구독으로 무엇을 나눌지는 모두 미정이다(2026-10-08). 추천 횟수(논의한 값은 무료 3회), 기준 기간, 도시에 대한 상세 질문을 누구에게 제공할지가 여기에 든다.
- 받은 추천은 사용자가 새로 추천받기 전까지 그대로 보여준다. 탭에 다시 들어와도 자동으로 호출하지 않는다.
- 검색은 기본으로 쓰지 않고 고정 자료(등급, 핵심 경험, 월별 기후, 체류비)로 판정한다. 자유문장에 사실 확인이 필요한 내용이 있을 때만 검색한다. 이 구성은 아직 실험하지 않았다.
- 지금까지의 실험은 이 구성을 검증하지 않았다. [칩 대 LLM 비교](../../data/exploration/chips-vs-llm/result.md)는 이전 9개 분류, 20곳 목록, 검색을 쓴 LLM의 결과다.

### 목록에 없는 도시

사용자가 목록 밖 도시를 말하면 의도에 따라 다르게 처리한다.

- **이미 가기로 한 경우:** 여행 등록 초안으로 잇는다. 사용자가 등록 화면으로 이동하기를 선택하면 도시·나라·명시한 날짜·컨셉을 채워 열고, 사용자가 저장하기 전에는 여행을 만들지 않는다. 예산이나 “3박 정도” 같은 계획 조건을 확정 정보로 바꾸지 않는다.
- **후보로 알아보는 경우:** 그 도시를 “생각 중인 곳”으로 화면에 남기고 목록 안의 다른 도시를 추천한다. 사용자가 고려하는 곳과 앱이 추천하는 곳을 구분해 보여준다.
- **그 도시와 함께 갈 곳을 원하는 경우:** MVP 이후에 다룬다. 여행 상세의 “함께 갈 곳 찾기”에서 시작하는 안을 논의했다. 방문 순서와 도시별 숙박일을 계산하는 단계는 그보다 뒤다.

목록 밖 도시에 대해 무엇을 말할지는 LLM이 판단한다. 목록 안 도시와 비교할 때 아는 내용을 말할 수 있다. 다만 등급과 저장된 핵심 경험은 목록 안 도시에만 있다. 목록 밖 설명도 [출처·확인 불가 원칙](sources.md#확인-불가와-표현)을 따르며, 모델 지식으로 말한 내용을 검수한 도시 자료로 표시하지 않는다.
요청된 목록 밖 도시의 이름은 서버에 기록해 어느 도시를 먼저 추가할지 정하는 근거로 쓴다. 기록 항목과 동의는 [저장·전송](../data/storage-and-privacy.md)의 원칙에 따라 정해야 한다.
한 번의 여행을 도시별로 쪼개 기록하게 하지 않는다. 여행 하나에 여러 도시를 둔다.

### 미정

- 조건에 맞는 도시가 하나도 없을 때의 대안 표시와 재추천. 예산 초과 후보를 별도로 보여주는 것은 제안이며 미확정이다. 초과 금액은 통화·포함 범위가 같은 근거 있는 비용 추정으로만 계산할 수 있다. 원인이 시기·기간·제외·자료 미확인일 수도 있어 예산 인상만으로 해결된다고 가정하지 않는다.
- 로컬 조건 수정의 미차감과 새 LLM 호출의 미차감은 별개다. “이 조건으로 다시 추천받기”의 차감 여부·반복 한도·실패 처리는 미정이다. 응답에 없는 도시를 로컬에서 새 개인화 카드로 만들지는 않는다.
- LLM에 보내는 도시 목록을 조건으로 먼저 거를지, 전체를 보내고 조건 통과 여부를 표시할지. 조건 밖 대안을 LLM이 돌려주게 하려면 그 후보도 입력에 포함해야 하지만, 전체 전송만이 유일한 방법이라고 확정하지 않는다.
- 코드 순위 계산의 역할(LLM에 주는 참고 순서, 응답 검증, 또는 쓰지 않음).
- LLM이 돌려주는 도시 수(논의한 값은 8~10곳)와 100곳 규모 목록에서 고르는 품질(실험 필요).
- 보내는 여행 평가의 상한과 최근의 기준(여행일·평가일), 선택 단위(여행·도시 평가). 목록 밖 도시 요청의 집계 단위·중복 처리·기간·검토 기준도 미정이다. 논의한 5회와 서로 다른 5명은 같은 기준이 아니며 자동 공개 기준으로 확정하지 않았다.
- 도시 질문 기능에서 목록 밖 도시도 물을 수 있게 할지.
- 환경을 피하고 싶은 경우(혼잡, 소음 등)는 자유문장으로 받는다는 것까지만 정했다.
- 세부 등급을 전부 매길지. 2등급 이상만 적으면 기록 없음과 없음을 구분하지 못했다.
- 세부 목록의 확정과 기준 파일의 v2 전환([경험 어휘](memory.md#경험-어휘)).
- 예산에 항공료를 넣을지, 1인 기준인지 일행 전체인지. 도시별 체류비 자료의 출처.
- 예산 조건을 어디까지 지킬지는 2026-10-13에 정했다: 엄격하게 지키지 않고 예상 범위를 보여준다([조건](#조건)). 아래는 그 전의 검토 기록이다. 예산을 엄격하게 지키는 추천이 필수라면 날짜·인원에 맞는 가격 근거가 있어야 한다. 그 근거 없이 출시하려면 “예산을 아직 확인하지 못한 탐색 추천”이라는 한계를 받아들여야 한다. “예상”이라는 표시만으로 둘을 함께 해결할 수 없다. 실험에서 본 것: 지침 문구만으로는 근거 없는 단정과 “전부 확인 필요” 사이를 오갔고([실제 메모 실행 5](../../data/exploration/memo-check/run5/result.md)), 일반 웹 검색을 쓴 한 번의 시도는 요청한 날짜의 가격을 얻지 못했다([비용 확인](../../data/exploration/cost-check/result.md)). 검토 중인 초기 형태: 취향과 요청으로 후보를 추천하고, 근거가 있는 대략의 비용은 계산 가정과 함께 참고로만 보여주며(자동 탈락에 쓰지 않는다), 사용자가 고른 후보에서 날짜·인원을 반영한 예약 사이트 조회로 연결한다. 제휴사의 가격 API는 병행해 알아보되 출시 조건으로 두지 않는다. 링크에 날짜·인원을 실을 수 있는지와 API의 종류(링크 생성인지 날짜별 가격인지)는 확인하지 않았다.
- 날씨가 나쁘다는 기준(우기, 태풍, 혹서, 혹한 중 무엇을 거를지).
- 비자·비행시간을 카드의 안내로 보여줄지.
- 무료와 구독의 구분 전체: 추천 횟수와 기준 기간, 상세 질문의 제공 대상과 횟수.
- 검색 없이 고정 자료를 넣은 LLM 구성의 품질(실험 필요).
- 100곳 이상에 대한 등급·핵심 경험·기후·체류비 자료의 제작과 검수 방법. 세부 29개면 등급만 2,900칸이다. 소수 도시에서 판정 기준과 검수 시간을 먼저 잰다. 근교와 미확인 처리는 2026-10-12에 [정했다](#도시-등급). 남은 것은 세부별 1↔2 기준 예시의 확정과 사람 검수다.
- 사람이 판정한 취향 사례. 지금까지의 계산은 동점과 쏠림, 조건 위반만 보았다. 새 구성 전체는 검증한 적이 없다.
- 추천 전의 짧은 확인 질문(2026-10-12 제안, 미정). 지난 기록이 막연해서 후보 선택이 갈릴 때만 한 가지를 묻고 답을 받은 뒤 추천한다. 매번 거치는 절차가 아니며 건너뛸 수 있다. 질문은 기존 컨셉을 다시 고르게 하지 않고 그 경험에서 무엇이 좋았는지를 묻는다(예: 그때와 비슷한 맛, 새로운 현지 음식을 먹어 보는 즐거움, 먹던 장소와 분위기). 특정 음식을 먹었다고 가정하지 않는다. 답은 그 여행 기록에 붙여 저장하되 평소 취향으로 넓히지 않는다. 2026-10-13 추가(사용자 의견과 [실제 메모 실행](../../data/exploration/memo-check/run4/result.md)): 질문은 막연한 메모뿐 아니라 뜻이 갈리는 조건(예산에 항공료가 드는지 등)에도 쓴다. 선택지는 버튼으로 고르고, 여러 개를 함께 고를 수 있으며, 맞는 것이 없으면 “기타”에 직접 적는다. 실행에서는 답을 받은 추천이 조건을 과하게 좁혀 오히려 나빠졌으므로 답을 어떻게 쓰게 할지가 먼저 정해져야 한다. 질문 호출의 횟수 차감은 정하지 않았다. 바로 추천한 결과와 질문에 답한 뒤의 결과를 비교하는 실험이 먼저다.
- 앱의 지침과 도시 자료가 같은 정보를 받은 일반 LLM보다 나은 추천을 내는지. 지금까지의 실험은 조건·등급·문장 형식만 보았고 지난 여행 메모를 넣은 적이 없다([비교 계획](../../data/exploration/memo-check/plan.md)).

## 여행지 값의 갱신 (출시 후)

처음에는 고정된 자료로 시작하고, 사용자 평가가 쌓이면 검증을 거쳐 고친다. 출시 전에는 구현하지 않는다. 숫자 기준과 주기는 미정이며 아래 원칙만 고정한다.

- **대상은 적합성이다.** 어떤 취향·조건의 사용자에게 그 여행지의 어떤 경험이 맞았는지를 갱신한다. 사실(계절, 운영, 이동)은 인기나 평가 수로 바꾸지 않는다. 사실과 어긋나는 보고가 몰리면 다시 확인할 신호로 쓴다.
- **기준은 전체 사용자 수가 아니라 칸별 근거의 양이다.** 도시 × 경험 × 사용자 조건의 한 칸에 평가가 충분히 쌓였을 때 그 칸만 갱신 후보가 된다.
- **근거는 다녀온 뒤의 평가와 그 이유다.** 방문 사실, 클릭, 저장은 쓰지 않는다. 보여주지 않은 후보를 싫어한 것으로 세지 않는다.
- **방문자의 취향 평균을 여행지의 특성으로 되먹이지 않는다.** “누가 갔나”가 아니라 “간 사람이 무엇을 좋게 평가했나”를 쓴다.
- **묶어서 검증한 뒤 반영한다.** 평가 한 건마다 자동으로 바꾸지 않는다. 떼어 둔 평가로 새 값이 이전 값보다 실제 만족을 잘 맞히는지 확인하고, 사람이 확인한 버전으로 반영하며 되돌릴 수 있게 한다.
- **반영 방식은 미정이다.** 집계 통계를 LLM 입력에 넣는 방법과 별도 순위 모델을 데이터가 생긴 뒤 비교한다.
- **2026-10-08 방향:** 사용자가 늘수록 도시 등급이 정확해지는 것을 앱의 강점으로 삼는다. 처음의 정수 등급을 출발값으로 둔다. 갱신 방식은 미정이다. 등급이 실수가 되면 지금의 순서(주 컨셉, 부 컨셉, 티어)에서 작은 차이가 부 컨셉과 티어보다 우선하게 되므로 동점으로 볼 범위를 함께 정해야 한다. 별점에는 날씨·숙소·동행이 섞여 있어 “그 경험을 위해 갈 만한 정도”와 같은 값이 아니다.
- **이를 위해 정해야 하는 것:** 도시별 평가는 [여행 평가](../screens/trip-evaluation.md)에서 정했다. 남은 것은 컨셉별 별점을 추가로 받을지, 도시 ID 식별·재방문·도시 미상 기록을 어떻게 처리할지, 도시 전체 평가를 컨셉별 갱신에 연결할지, 서버 수집 동의를 언제 받을지다.

이 갱신에는 사용자 평가를 모으는 서버 저장이 필요하다. 도입은 별도 결정이며, 수집 목적·항목·보관 기간·동의·철회·삭제를 정하기 전에는 평가를 집계·학습용 서버 저장소로 보내지 않는다. 추천 호출을 위한 일시적 메모 전송은 [전송 계약](../data/storage-and-privacy.md#llm-전송과-서버)에 따른 별도 목적이다. 지금 할 일은 나중에 칸별로 셀 수 있는 형태로 기기에 기록을 남기는 것뿐이다([계측](../README.md#metrics)).

## 채택 전에 남은 결정

출시 모델·검색 제공자와 구체적인 검색 판정·실패 처리, 공개할 도시별 자료의 검수, 비용·지연 허용치, 결과 유효기간은 미정이다. 도시 자료의 배포 방식은 위에서 앱 번들로 정했다. 검색을 조건부로 쓰는 방향과 호출 정책은 [LLM 호출과 횟수](#llm-호출과-횟수)를 따르며 실제 운영 구성은 측정 후 정한다. 프로필·검색·상위 모델 어느 것도 아직 출시 품질을 입증하지 않았다.
