## 1. 결정과 검증할 가설

### 합의한 방향

- 추천의 중심을 나라에서 **도시**로 옮긴다. 나라는 도시의 위치·묶음 정보로 유지한다.
- 사용자 선호와 여행지 특성을 분리한다. 나라 방문으로 계획성·사교성 등을 추론하지 않는다.
- 저장된 취향으로 추천 탭 첫 진입 시 바로 후보를 보여준다. 날짜·예산·동행·기간은 선택 입력이다.
- LLM은 제공받은 사용자 정보와 검수한 여행지 DB를 바탕으로 후보 선택, 설명, 피드백 해석을 맡는다.
- 첫 버전의 상세 설명·추가 답변은 검수한 DB에 근거한다. 최신 확인이 필요한 정보는 공식 링크로 안내한다. 자동 웹 검색은 넣지 않는다.
- 사용자의 제외 요청을 기억한다. 제외 범위를 도시에서 나라 전체나 다른 취향으로 임의 확대하지 않는다.
- 수작업 매칭 공식의 추가 설계는 멈추고 같은 자료로 LLM의 선택 품질을 검증한다.

### 사용자 제안과 설계상 기본안

- 사용자는 세계의 주요 여행 도시 **약 100곳**을 제안했다. 이를 초기 카탈로그 목표로 삼는 안을 권한다. D2 조사 후보는 원본 100곳·잠정 보충 3곳·파일럿 20곳으로 확정했다. 첫 공개 목록은 자료 검수와 평가 뒤 결정한다. 목록과 진행 상태는 [후보 선정안](../data/destination-selection.md)을 따른다.
- 자료 형식 검증은 그중 성격이 다른 15~20곳으로 먼저 하고 100곳으로 확대한다. 작은 표본에서의 성공만으로 100곳의 품질을 승인하지 않는다.
- 기본 카드 수는 최대 3곳으로 제안한다. 조건에 맞는 곳이 부족하면 억지로 채우지 않는다.
- 방문 도시도 추천하고 “새로운 곳만 보기”를 제공한다. 이유 없는 도시 부정 반응은 계속 제외로 저장한다. 명시적인 평소 취향은 자동 저장 후 안내·되돌리기를 제공한다. 세 정책은 사용자 답변으로 확정했다(6절).

**검증할 가설:** 적은 입력에서도, 사용자가 좋아하고 싫어하는 이유와 이번 여행 조건을 구분해 기억하면 더 적합한 도시·경험을 제안할 수 있다. LLM 사용이나 도시 100곳 자체를 경쟁 우위의 증거로 삼지 않는다.

## 2. 왜 기존 축을 그대로 확장하지 않는가

계획을 싫어하는 사용자가 사진첩으로 일본·미국·캐나다를 등록했는데 지문이 계획 쪽으로 이동한 것이 출발점이다. 국가 값에 사용자의 성향을 끌어맞추는 구조가 원인이다.

- “도쿄에 갔다”는 방문 사실이다. 도시·미식·계획을 선호한다는 답이 아니다.
- “도쿄가 좋았다”는 여행지 평가다. 무엇이 좋았는지 모르면 경험 선호로 분해하지 않는다.
- 혼자 새로운 사람을 만나고 싶은 사람과 친구와 시간을 보내고 싶은 사람은 서로 반대 유형이 아니다.
- 친구와 여행한다는 이유로 밤 문화를 좋아한다고 추론하지 않는다.
- 도시와 자연은 동시에 좋아할 수 있다. 모름·둘 다 좋아함·둘 다 싫어함을 구분한다.

기존 5축의 값을 새로운 항목의 숫자로 변환하면 기존 오류를 보존하게 된다. 새 모델의 원천은 직접 답변과 여행 기록의 원문·구조화된 사실이다.

## 3. 사용자 정보: 하나의 점수 벡터로 압축하지 않는다

### 3.1 평소 선호

명시적으로 말한 좋아하는 경험, 피하고 싶은 경험, 여행 스타일을 보관한다.

예: “현지 음식을 먹는 게 가장 중요하다”, “자연도 도시도 좋다”, “혼자 조용히 쉬는 시간을 좋아한다”, “예약으로 하루를 꽉 채우는 건 싫다”.

초기 분류 어휘는 도시 탐방·자연·미식·휴식·문화/역사·액티비티·쇼핑·밤 문화·새로운 사람 만나기로 제안한다. 목록 밖의 선호도 원문으로 보존한다. 이 목록은 질문 9개나 점수 9개를 반드시 만들라는 뜻이 아니다.

각 선호에 필요한 것은 내용, 적용 범위, 출처 답변, 기록 시점, 활성/철회 상태다. LLM이 근거 없는 강도·확률·성격 점수를 만들지 않는다. 사용자가 “가장 중요”라고 말한 우선순위는 그대로 보관한다.

### 3.2 이번 여행

동행, 출발지, 날짜/계절, 기간, 예산과 포함 범위, 이번에 원하는 경험을 별도로 둔다.

- 미입력은 모름이다. 과거 여행의 평균이나 동행 빈도로 채우지 않는다.
- 예산에는 통화, 1인/일행 전체, 항공 포함 여부가 필요하다. 추천을 크게 바꾸는 모호함만 짧게 확인한다.
- “이번에는 자연을 보고 싶다”는 이번 여행에 적용한다. 도시 선호를 지우지 않는다.
- 명시한 이번 목적이 평소 취향보다 우선하되, 확정 제외와 필수 조건은 지킨다.
- 현재 여행은 앱 재시작 후에도 유지한다. “새 여행 시작”에서 조건과 이번 여행 제외를 새로 시작한다.

### 3.3 여행·관심 기록

방문 도시/나라, 직접 평가, 좋았던 이유·아쉬웠던 이유, 저장한 후보를 구분한다.

- 사진 위치는 방문 후보를 제안하고 사용자가 확인한다. 통과·거주·환승 여부를 방문 만족도로 추론하지 않는다.
- 나라만 확인되면 나라 방문으로 남긴다. 그 나라의 도시를 전부 방문 처리하지 않는다.
- 저장은 북마크다. 저장 한 번으로 취향을 그 도시 특성 쪽으로 이동시키지 않는다.
- 상세 열람이나 “서핑도 할 수 있어?”라는 질문은 취향 확정이 아니다.
- “A가 B보다 좋았다”는 두 여행의 상대 평가만 남긴다. 이유 없이 모든 특성의 확신을 올리지 않는다.
- 재방문 의향은 해당 여행지에 대한 의향이다. 일반적인 새로움 성향으로 확대하지 않는다.

## 4. 도시 DB: 점수보다 실제로 가능한 경험과 근거

여기서 “도시 DB”는 검수한 공용 도시 자료 카탈로그를 뜻한다. 현재 저장 형식은 `data/cities/`의 JSON이며 특정 DB 서비스 도입을 의미하지 않는다. 사용자 로컬 기록과 분리하고 [저장 단계](../data/storage-and-privacy.md#저장-방식과-도입-단계)를 따른다.

### 4.1 단위와 범위

화면의 중심 이름은 “도쿄”, 보조 정보는 “일본”이다. 도시마다 안정적인 ID와 별칭·나라·위치를 둔다.

도시의 모든 경험을 행정구역에 가두지는 않는다. 경험별 장소 ID, 추천 범위 안/밖/미확인 관계, 배편·숙박 필요 여부와 근거를 구조화한다. 값이 있어도 근거가 검수·유효성 검사를 통과하지 않으면 미확인이다. 상세 교통은 선택이며, 당일 일정 가능을 주장할 때만 이동·대기·체험 시간까지 확인한다. 먼 장소 여러 곳의 장점만 합쳐 하나의 도시처럼 추천하지 않는다. 초기 15~20곳은 도시 중심으로 자연 여행 거점 도시를 최소 4곳 포함한다. 핵심 경험이 거점에서 현실적인 당일 왕복과 체험 시간을 확보할 수 없으면 파일럿 전에 별도 지역 후보를 검토한다. 섬·국립공원 등 지역 단위를 쓰는 경우에도 국가 평균값으로 빈칸을 메우지 않는다.

“세계 인기 100위”라고 표시하려면 공통 기준·연도·출처가 필요하다. 초기에는 **주요 여행 도시 100곳**으로 부르고, 지역 편중·휴식/자연형 후보 부족·비슷한 대도시 중복을 점검한다. 정확한 100곳 목록 작성과 사실 수집은 별도 데이터 작업이다.

### 4.2 도시별 최소 자료

- 장소·랜드마크: 실제 장소 ID와 추천 범위의 관계.
- 경험: 그 장소에서 무엇을 할 수 있는지.
- 중요한 제약: 계절 제한·장기 폐쇄·예약 필수·배편 또는 숙박 필요 등 추천 선택을 바꾸는 조건. ‘지금 갈 수 있다’는 당일 영업·예약 재고 보장이 아니다.
- 버스 요금·배차·정류장별 시간은 필수 제작 범위에서 제외한다. 관련 상세 질문에 쓸 자료가 있으면 별도 보관하며, 첫 추천 입력에 자동 포함하지 않는다. 비용을 저장할 때는 기준 시점·포함 범위를 명시한다.
- 출처: 주장별 근거 ID, 공식 링크, 확인일, 적용 지역/시기, 검수 상태.
- 재확인 초기 기준: 가격·운영·예약 최대 3개월, 교통·접근·계절 제약 최대 6개월, 위치·상설 경험 최대 12개월. 출처의 유효기간이 더 짧거나 변경을 발견하면 먼저 재검수한다.
- 추천용 짧은 요약과 상세용 근거 자료. 요약의 주장은 원자료로 추적할 수 있어야 한다.

“사람들이 친절하다”, “혼자 가기 좋다”, “안전하다” 같은 넓은 인상 점수는 검증된 사실로 쓰지 않는다. 혼자 참가할 수 있는 체험, 대중교통 접근, 구체적 유의사항처럼 사용자가 판단할 수 있는 정보로 바꾼다. 새 사람을 만나는 결과를 보장하지 않는다.

장소·경험의 유효 근거가 부족한 도시는 추천 대상에서 보류한다. 선택 정보인 상세 교통이 비었다는 이유만으로 보류하지 않는다. LLM 초안은 검수 전까지 사실이 아니다. 기존 나라의 축·관심 태그를 도시 사실로 자동 복사하지 않는다.
재확인 기한이 지난 주장은 추천 근거에서 보류한다. 도시 전체를 자동 제외하지 않으며, 그 주장에 의존하는 조건은 충족 미확인으로 내린다.

### 4.3 100곳을 LLM에 전달하는 방법

초기 기본안은 필수 조건·제외를 적용한 도시들의 **검수된 짧은 요약**을 한 번의 추천 요청에 전달하는 것이다. 상세 설명은 선택한 도시의 근거 자료만 전달한다.

100개 도시의 모든 문서를 매번 보내지 않는다. 압축 요약에 후보 선택을 좌우하는 조건이 빠지지 않는지 검수한다. 토큰·지연 측정 결과 감당하기 어렵거나 후보 누락이 생길 때 검색/후보 축소 단계를 추가한다. 지금 벡터 DB나 다단계 에이전트를 미리 만들지 않는다.

## 5. 추천 탭과 상세 화면

### 5.1 첫 진입

1. 현재 취향·여행 조건·제외와 일치하는 저장된 추천이 있으면 즉시 보여준다.
2. 없으면 해당 스냅샷으로 추천을 요청한다.
3. 날짜·예산이 없으면 “취향에 맞는 여행지”로 제시한다. 실제 일정·가격까지 검증한 여행안처럼 표현하지 않는다.
4. 후보가 비슷하거나 취향 정보가 부족하면 선택 입력을 하나 제안한다. 답변을 첫 추천의 필수 관문으로 만들지 않는다.

사용자 취향이 전혀 없으면 “아직 취향을 모르는 상태의 탐색 제안”으로 구분한다. 개인화했다고 꾸미지 않는다.

카드는 도시·나라, 이 사용자에게 맞는 이유, 가능한 경험 2~3개, 중요한 유의점, 상세/저장/제외 행동을 담는다. 보정하지 않은 “매칭 97%”나 LLM의 자체 확신 점수는 표시하지 않는다. 다양성 때문에 부적합한 후보를 섞지 않으며, 비슷한 후보만 남았다면 그대로 설명한다.

### 5.2 반응과 재추천

사용자가 이유를 누르거나 문장으로 쓴다. 제외·기억할 내용이 먼저 저장되고 화면에 표시된다. 이후 새 추천을 요청한다. 재추천 실패가 사용자의 저장된 선택을 되돌리지는 않는다.

기본안은 제외한 카드 자리를 대체하고 나머지 유효한 카드는 유지하는 것이다. 예산·동행·핵심 목적 변경처럼 전체 적합성이 바뀌면 전체를 다시 고른다. 별도의 “다른 후보 보기”는 현재 결과를 이번 요청에서 피하도록 하며 영구 제외를 만들지 않는다.

### 5.3 도시 상세와 질문

상세 기본 정보는 DB로 바로 표시하고, 사용자에게 맞는 설명은 생성 결과를 재사용한다. 첫 방문 때 생성이 필요하면 기본 정보를 읽는 동안 표시를 준비한다.

- 무엇을 할 수 있는지, 왜 이 사용자에게 맞는지, 맞지 않을 수 있는 점을 설명한다.
- “미식이 좋아요”에서 끝내지 않고 DB에 있는 구체적 경험을 연결한다.
- DB에 없는 답은 확인되지 않았다고 말한다. 최신 운영시간·가격·입국 요건 등을 모델 기억으로 채우지 않는다.
- 최신 확인은 검수된 공식 링크로 안내한다. 없는 링크를 생성하지 않는다.
- 도시를 제외해도 사용자가 직접 검색·상세 열람하는 것은 허용한다. 제외 상태를 보여주며, 열람만으로 해제하지 않는다.

## 6. 피드백·기억·제외 정책

### 6.1 해석 예시

- “이번엔 너무 비싸요” → 해당 후보를 이번 여행에서 제외하고 비용 문제를 기록한다. 금액을 모르면 예산 숫자를 지어내거나 모든 고물가 도시를 일괄 제외하지 않는다.
- “이번에는 자연을 보고 싶어요” → 이번 여행의 목적. 평소 도시 선호 유지.
- “나는 원래 붐비는 곳을 싫어해요” → 평소 혼잡 회피 선호. 사람 만나기 선호와 별개.
- “도쿄 다시 추천하지 마” → 도쿄를 계속 제외. 일본 전체·다른 대도시로 확대하지 않는다.
- “일본은 추천하지 마” → 일본에 속한 도시를 제외.
- “도쿄는 별로예요” → 도쿄의 부정 반응. 이유를 추측하지 않고 아래 기간 정책 적용.
- “친구랑 여행할 거예요” → 이번 동행. 밤 문화 선호 추가 없음.
- “음식은 좋았지만 줄 서는 건 싫었어요” → 음식에 대한 긍정과 대기 회피를 따로 저장.

범위가 모호해서 이후 추천이 크게 달라지면 “이번 여행에만 적용할까요?”처럼 한 가지만 확인한다. 모든 대화에 확인 팝업을 띄우지 않는다.

### 6.2 사용자 확정 정책

- **방문 도시도 기본 추천한다.** “새로운 곳만 보기”를 선택하면 방문이 확인된 도시를 제외한다. 도시를 모르는 국가 기록은 해당 국가 전체 제외로 바꾸지 않으며, 미확인 도시를 확실한 첫 방문이라고 설명하지 않는다.
- **이유·기간 없는 도시 부정 반응은 계속 제외한다.** “도쿄는 별로예요” 뒤에는 “도쿄를 추천에서 제외했어요 · 되돌리기”를 표시한다. 해제 전까지 유지하며, 취향 항목은 변경하지 않는다. 명시적으로 “이번에는”이라고 말하면 이번 여행에만 적용한다.
- 카드의 이유 없는 주 행동은 “추천에서 계속 제외”로 표시한다. “이번 여행에서 제외”와 “다른 후보 보기”는 메뉴에서 제공한다. 제외 저장 뒤 내용과 되돌리기를 보여준다.
- **명시적인 평소 취향은 자동 저장한다.** 예: “붐비는 곳을 피하는 취향으로 기억했어요 · 되돌리기”. 저장한 내용과 범위를 사용자에게 보여준다. 질문·가정·인용·모호한 말은 명시적인 취향 진술로 취급하지 않는다.

### 6.3 공통으로 지킬 규칙

제외는 대상 ID, 도시/나라 범위, 이번 여행/계속 적용, 이유 원문, 시점, 해제 상태를 저장한다. 앱 실행 세션과 여행 범위를 혼동하지 않는다.

- 제외 목록에서 확인·해제 가능하다. 해제는 부정 이유를 반대 취향으로 바꾸지 않는다.
- 나라 제외를 해제해도 별도로 설정한 도시 제외는 유지한다.
- 제외를 LLM 입력 전 후보 목록에서 적용하고, 출력 검증에서도 다시 확인한다.
- 필수 조건이나 제외를 만족하는 후보가 없으면 이를 알리고 사용자가 조건을 바꾸게 한다. AI가 임의로 해제하지 않는다.
- 평소 취향 수정은 사용자가 원문과 적용 내용을 확인·삭제할 수 있어야 한다.
- 명시적인 정정은 이전의 같은 범위 선호를 대체한다. 서로 다른 상황의 선호는 함께 보존한다.
- 삭제·철회한 증거는 추천 입력에서 빠지고 해당 추천 캐시가 무효화된다. 단순 요약 문장 속에 다시 살아남지 않게 한다.

## 7. LLM과 앱의 책임 경계

논리적인 요청 종류는 추천, 피드백 해석, 도시 설명/질문 세 가지다. 별도 에이전트나 서비스 세 개를 만들라는 뜻은 아니다.

**추천 입력:** 활성 사용자 증거, 이번 조건, 후보 ID와 도시 요약, 검수한 근거, 요청 버전.
**추천 출력:** 선택한 도시 ID, 근거 ID와 연결된 추천 이유·경험·유의점. 허용 후보 밖의 도시는 만들지 않는다.
**피드백 출력:** 대상, 요청 행동, 범위, 원문 근거, 확인이 필요한 모호함.
**상세 출력:** 주어진 자료가 지지하는 설명과 근거, 확인되지 않은 부분.

LLM이 DB를 직접 수정하지 않는다. 앱이 허용된 행동·대상·범위를 검증한 뒤 저장한다. 명시 버튼은 모델 해석 없이 처리하고, 자유문장만 해석을 요청한다. 사용자 문장과 DB 자료를 시스템 지시로 실행하지 않는다.

다음은 코드로 보장한다.

- 허용 ID, 중복, 현재 제외 목록, 자료 검수 상태.
- 근거 ID의 존재·검수 상태·기한·해당 도시 연결, 장소 ID·범위·주요 이동 제약.
- 답변 종류는 LLM이 제안하고 표시 여부는 서버·앱 검증 후 결정한다. 사실 문장마다 근거 ID가 필요하며 조언에 포함된 사실 전제도 예외가 아니다. ID 검사는 의미 적합성 보장이 아니다. [설명 계약](explanations.md)의 우회 사례를 별도 평가한다.
- 사용자가 확정한 필수 조건 중 DB로 판정 가능한 조건.
- 응답이 현재 취향·조건 버전에 대한 것인지. 요청 중 조건이 바뀌면 늦게 도착한 응답을 폐기한다.

대략적 비용·기후 자료만으로 실시간 총예산·날씨 적합성을 보장하지 않는다. 필수 조건의 충족 여부를 알 수 없으면 “충족 확인”으로 표시하지 않는다. 검증이 꼭 필요한 조건이라면 추천을 조건부로 표시하거나 확인 전 보류한다.

## 8. 저장·재사용·실패 처리

### 8.1 필요한 기록

기존 여행 기록·북마크를 재사용하고 다음 의미를 구분한다.

- 사용자 증거와 활성 상태.
- 이번 여행 ID와 조건.
- 도시 DB 및 근거 버전.
- 범위가 있는 제외.
- 추천 결과: 순서·설명·근거와 생성 당시 입력 버전.
- 실제 노출과 반응: 어떤 추천의 어느 카드를 보았고 어떻게 반응했는지.

원문 전체 대화를 매번 보내는 방식 대신, 활성 증거와 현재 질문에 필요한 문맥을 보낸다. 부정확한 요약으로 원문을 대체하지 않는다. 실험 로그는 앱 노출 스키마에 억지로 끼우지 않고 별도 파일로 남긴다.

### 8.2 다시 생성하는 기준

취향·이번 조건·제외·도시 자료·프롬프트/모델 버전이 관련 결과를 바꿀 때 무효화한다. 탭을 열 때마다 호출하지 않는다. 같은 유효 결과를 재사용하고, 상세도 도시·사용자 버전별로 재사용한다.

새로 제외한 도시는 네트워크 상태와 관계없이 화면에서 즉시 제거한다. 입력 저장에 실패했다면 “기억했어요”라고 표시하지 않는다.

### 8.3 실패와 비용

- 생성 실패 시 최신 조건을 여전히 만족하는 기존 결과만 보여준다. 없으면 재시도 상태를 표시한다.
- LLM 출력 검증 실패를 그대로 노출하지 않는다. 초기 기본안은 자동 재시도 최대 1회, 이후 수동 재시도다.
- 사용 가능한 후보가 1~2곳이면 그 수만 반환할 수 있다.
- 사용자별 호출 제한과 전체 지출 상한을 둔다. 제한 도달 시 기존 결과·검수된 상세 자료는 계속 볼 수 있다.
- 모델은 실험으로 고른다. 단가뿐 아니라 실제 입력/출력 토큰, 재시도, 지연과 상세 질문 빈도를 포함해 비용을 측정한다.
- 출시 비용 상한의 금액은 아직 미정이다. 유료 API를 호출하거나 서버를 운영하기 전에 정한다.

## 9. 온보딩과 공유 취향

사진 등록은 방문 기록을 채울 뿐이므로 직접 선호를 받을 기회를 반드시 제공한다. 다만 모든 사용자에게 모든 항목을 하나씩 질문하지 않는다.

초기 제안은 “좋아하는 경험 복수 선택 + 피하고 싶은 것 선택/자유 입력”이다. 선택하지 않은 항목은 싫어함으로 간주하지 않는다. 계획성 등 직접 정보가 없는 특성은 미상으로 남기고 추천에 필요할 때 묻는다. 문항을 건너뛸 수 있게 하고, 건너뛰면 해당 선호를 추정해 채우지 않는다.

공유 지문은 **직접 증거에서 만든 읽기 쉬운 요약**이다. 내부 추천 입력을 다섯 축으로 제한하지 않는다. “미식과 자연을 좋아하고, 예약은 적게”처럼 사용자에게 확인 가능한 내용으로 만든다. 새 공유 카드 형태·문항 문구는 별도 화면 설계에서 정한다. 기존 레이더 수치의 의미를 몰래 바꾸지 않는다.

## 10. 서버와 향후 집계

### 10.1 검증 단계

개발 PC에서 사례와 자료를 읽는 스크립트로 비교한다. 앱·서버 구현은 필요 없다. 합성 사례로 시작하고 실제 사용자 자료는 동의와 최소 전송 원칙을 적용한다. PC 실험이어도 외부 모델 API에 보낸 데이터는 외부 전송이다.

### 10.2 앱에 도입할 때

키 보호·요청 검증·호출/비용 제한을 담당하는 작은 서버 경유가 필요하다. 키를 앱에 넣지 않는다. 원본 사진이나 전체 위치 이력은 전송하지 않고, 사용자가 확인한 추천 관련 사실만 보낸다.

도시 자료의 운영 배포·갱신·캐시 방식과 서버 DB 필요 여부는 채택 후 구현 전에 정한다. MySQL 등 특정 제품은 미정이며 Firebase (Auth·Firestore·Storage)는 루트 README의 제외 범위를 따른다. LLM 호출 서버 도입은 사용자 기록의 클라우드 저장·동기화를 요구하지 않는다.

이 서버 도입과 **전체 사용자의 행동을 모으는 집계 서버**는 별도 결정이다. LLM 사용만으로 모든 사용자의 데이터가 자동 학습되거나 모델이 실시간 개선되는 것은 아니다. 외부 전송 안내, 제공자 보관 설정, 앱/서버의 보관·삭제 정책은 실제 제공자와 운영 구조가 정해진 뒤 출시 전에 확정한다.

### 10.3 데이터가 쌓인 뒤

먼저 “이 사용자의 다음 추천이 기억을 반영하는 것”으로 개인화한다. 다른 사용자 집계는 별도로 검증한다.

- 여행지 사실: 검수 자료와 실제 경험 보고를 함께 점검하되 인기·저장 수로 사실을 바꾸지 않는다.
- 적합성: 특정 선호·조건의 사람들이 어떤 경험을 좋게 평가했는지 비교한다.
- 노출 편향: 보여주지 않은 후보를 싫어했다고 간주하지 않는다. 노출 위치·모델/프롬프트/자료 버전·조건·반응을 연결한다.
- 클릭·저장은 여행 후 만족과 구분한다. 불명확한 부정 반응을 특성 전체의 음성 표본으로 쓰지 않는다.
- 집계 결과는 검수·평가·되돌리기가 가능한 버전으로 반영한다. 반응 한 번마다 공용 도시 설명이나 모델을 자동 변경하지 않는다.

집계 통계를 LLM 입력에 추가하거나 별도 순위 모델을 시험할 수 있지만, 어느 방식이 이기는지는 데이터가 생긴 뒤 판단한다. 지금 협업 필터링·미세조정·자동 가중치 학습을 구현하지 않는다.

## 11. 비교 실험과 도입 판단

### 11.1 서로 다른 질문을 분리한다

**선택 능력 실험:** 같은 사용자 사실, 같은 도시 후보와 검수 자료, 같은 필수 조건으로 단순 규칙·고품질 LLM·저가 LLM을 비교한다. 후보 선택을 위한 자료는 모두에게 같아야 한다.

**기존 앱 대비 실험:** 현재 모델, 알려진 추론 오류를 고친 모델, 새 도시 추천을 비교한다. 국가와 도시의 단위 차이·추가 질문의 정보량 차이를 명시한다. 이 결과만으로 LLM 자체의 우월성을 주장하지 않는다. 필요한 경우 공통 국가 후보 실험을 따로 둔다.

고품질 모델은 실험 기준이지 출시 기본 모델의 확정이 아니다. 단순 규칙은 비교 기준으로만 만들고 별도의 정교한 매칭 프로젝트로 키우지 않는다.

### 11.2 평가 방법

- 사용자에게 설명을 숨기고 동일 형식의 후보 이름·자료부터 보여준다. 겹치는 후보는 한 번만 평가한다.
- 설명은 그 뒤에 공개해 근거 정확성·사용자에 대한 단정·도움이 되는 정도를 별도로 평가한다.
- 추천 적합성은 해당 사용자가 판단한다. 자료 위반·제외 위반은 가능하면 독립 검수자가 판단하고, 확보 전에는 자체 검수로 기록하며 그 한계를 결과에 명시한다.
- 자료 작성자는 우선 자체 검수자로 기록한다. 아직 독립 검수자·평가 참여자는 확보되지 않았으며, 확보 전에는 독립 검수로 보고하지 않는다. 결과에는 자체/독립 검수 종류, 검수자, 자료 버전과 검수일을 남긴다.
- 방문하지 않은 곳을 오답으로 보지 않는다. 과거 평가 실험에서는 평가한 여행끼리 비교하고 가린 평가·이유·파생 프로필을 입력에서 제거한다.
- 같은 입력 반복, 후보 순서 변경, 핵심 조건 변경을 각각 시험한다. 순위가 고정돼 있다는 것만으로 좋은 추천이라고 판단하지 않는다.
- 프롬프트 개발 사례와 최종 평가 사례를 분리한다. 작은 파일럿은 오류 발견용이며 경쟁 우위 증명이 아니다.
- 비용·지연·검증 탈락·재시도·사용자 수정 횟수도 측정한다. 탈락 응답을 조용히 제외하고 품질을 계산하지 않는다.

도입 조건은 후보 선택의 개선, 근거 정확성, 아래 필수 시나리오 통과, 감당할 비용/지연이다. 통계·품질·비용의 수치 기준은 파일럿으로 측정 가능성을 확인한 뒤 **최종 평가 결과를 보기 전에** 정한다. 설명만 좋아졌다면 추천 선택까지 교체할 근거는 부족하다.

## 12. 구현 전에 통과시킬 시나리오

1. 즉흥 선호자가 일본·미국·캐나다 사진을 추가해도 계획 선호가 생기지 않는다.
2. 도쿄를 좋아했다는 답만으로 미식·사교 선호를 만들지 않는다.
3. 혼자 새 사람을 만나려는 사람과 친구와 시간을 보내려는 사람 모두에 대해, 자료에 근거한 서로 다른 경험을 제안할 수 있다.
4. 도시·자연 모두 좋아함과 둘 다 모름의 입력이 구분된다.
5. 도쿄 계속 제외는 재시작·재추천 후에도 지켜지고, 오사카까지 확대되지 않는다.
6. 이번 여행 제외는 재시작 후 유지되고 새 여행에서 해제된다. 계속 제외는 유지된다.
7. 예산 관련 부정 반응이 도시·자연 선호를 바꾸지 않는다.
8. 질문·열람·북마크만으로 새 평소 취향이 생기지 않는다.
9. 입력 변경 중 도착한 오래된 추천은 현재 추천을 덮어쓰지 않는다.
10. 자료에 없는 명소·가격·운영시간·링크를 사실로 보여주지 않는다.
11. 유효 후보가 부족하거나 비용 한도에 도달해도 제외를 풀거나 사실을 만들어내지 않는다.
12. 기억을 삭제·되돌리면 다음 입력과 공유 요약에서 빠지고, 과거 요약에서 복원되지 않는다.
13. 나라만 기록된 방문 이력으로 그 나라의 도시 전체를 방문 처리하지 않는다.
14. 검수 자료가 없거나 확인되지 않은 필수 조건을 충족했다고 표시하지 않는다.
15. 근거 없는 ‘조용한 동네라 쉬기 좋을 것’ 같은 사실 전제를 제안으로 분류해 통과시키지 않는다. 무관한 유효 ID를 붙인 문장도 오류로 평가한다. 생성 오류와 사용자 노출 오류를 분리한다.
16. 범위 밖·미확인 장소, 배편·숙박 필요 여부가 미확인인 경험을 범위 안·이동 제약 없음으로 합치지 않는다. 범위 안인 장소도 당일 완주 가능을 보장하지 않는다.

## 13. 현행 구현에서 옮기는 순서

현행 구현에는 5축 국가 추천과 로컬 피드백/노출 기록이 있다. B1에서 국가 방문·비교·저장만으로 취향이나 확신을 움직이던 경로를 제거했다. 이 문서의 도시·LLM 구조는 아직 구현하지 않았다. 기존 구현·자료의 비교 기준은 실험 시 Git 커밋과 앱 번들 자료 해시로 고정한다.

1. 확정된 정책에 따라 자료 형식·후보 목록·사용자 사례·검증 시나리오를 작성한다. 사용자 답변은 [TODO의 결정 기록](../TODO.md#확정한-결정과-남은-확인)을 따른다.
2. 15~20곳으로 자료 형식을 검수하고 PC 비교 도구로 파일럿을 실행한다. 첫 외부 LLM 파일럿의 총지출 상한은 US$10이다.
3. 개발에 쓰지 않은 사례의 선택·오류·비용으로 확대/재시험/보류를 판정한다. 확대 승인 후 목표 100곳으로 자료를 늘리고 최종 비교를 실행한다.
4. 채택 결정 후 도시 데이터·직접 선호·여행 조건·제외를 저장하는 구조와 이관을 구현한다.
5. 서버 경유와 추천/상세/피드백 UI를 연결한다. 공유 지문은 새 증거 구조에 맞춘다.
6. 집계는 이후 별도 판단한다.

이관 시 원본 퀴즈 답과 명시적 태그는 의미가 명확한 항목만 옮긴다. 국가 평균이 섞인 파생 5축 값은 새 선호의 근거로 쓰지 않는다. 기존 나라 제외를 도시 하나로 축소하지 않으며, 방문 도시를 모르면 모름으로 남긴다. 기존 기록과 제외를 보존하는 이관 검증이 필요하다.

현행 오류 수정 B1을 먼저 완료하고 출시 여부는 도시·LLM 평가 뒤에 판단하는 순서로 확정했다. 실제 출시 시점과 공개 범위는 평가 결과로 정한다.

## 14. 아직 정하지 않은 것

- 첫 공개 도시 목록과 개별 자료의 검수 결과. D2 조사 후보는 확정했으며 첫 공개 목록과 구분한다. 도시 중심·자연 거점 최소 4곳·자체 검수 우선·정보별 3·6·12개월 재확인은 확정했다. 전체 100곳을 첫 공개 범위로 확정할지는 품질 확인 후 결정.
- 온보딩 문항과 공유 지문의 최종 화면.
- 최종 평가 기준값, 모델·제공자, 출시 사용자별/전체 비용 상한. 첫 외부 LLM 파일럿 상한 US$10은 확정했다.
- 출시 시점, 도시 자료의 운영 배포·갱신·캐시 방식, 서버 DB 필요 여부와 제품 선택, 서버 전송·보관·삭제의 운영 세부. Firebase 제외는 현재 확정 범위다.
