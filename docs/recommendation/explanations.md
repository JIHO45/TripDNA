# 도시 추천과 설명의 근거

상태: 새 구조의 설명 계약. 기준: [핵심 설계](architecture.md) 5·7절.
고정된 best/fresh/underrated 슬롯·탐험 반경 공식·매칭 백분율은 새 추천에 사용하지 않는다.

## 카드

기본안은 최대 3개 도시다. 도시 이름을 중심으로 나라, 사용자에게 맞는 경험, 유의점을 보여준다.
적합한 후보가 적으면 카드 수를 줄인다. “새로운 도전” 자리를 채우려고 부적합한 곳을 끼우지 않는다.

추천 이유는 **사용자 근거 + 도시 근거**를 연결한다.
예: 사용자가 “미술관을 좋아한다”고 직접 답했고, 검수 DB에 특정 미술관 경험과 방문 조건이 있을 때 그 둘을 설명한다.
방문·북마크만으로 “미술관을 좋아하시니까”라고 말하지 않는다.

## 설명에서 구분할 것

- DB 사실: 무엇이 어디에 있고 어떤 조건에서 가능한지.
- 사용자 사실: 사용자가 직접 알려준 선호와 이번 조건.
- 적합성 판단: 그 두 사실을 연결한 추천의 이유. 미래 만족을 보장하지 않는다.
- 미확인: 자료가 없거나 최신 확인이 필요한 정보.

근거 ID의 존재만으로 모든 문장이 검증된 것은 아니다. 문장이 출처의 범위를 넘지 않는지 평가한다.
모델 내부 추론 과정을 노출할 필요는 없지만, 사용자가 판단할 추천 이유와 출처는 제공한다.

## 금지할 설명

- 집계가 없는데 “당신 같은 사람들이 좋아했어요”.
- 검수된 인기 자료가 없는데 “숨은 보석”, “세계 인기 100위”.
- “매칭 97%”, “AI 확신 90%”처럼 보정되지 않은 숫자.
- 현재 가격 없이 “항공·숙박 포함 총예산 충족”.
- 타인의 성격·국민성을 도시의 사실로 단정하기.
- 제외·비용·거리 이유를 무관한 경험 취향으로 해석하기.

## 상세 질문

사실 설명은 검수 DB에 근거한다. 일반 조언은 DB·사용자 사실과 모순되지 않게 제안하되, 조언 속 사실 전제에도 근거를 요구한다. ‘한 구역에 집중하기’ 같은 구성 조언은 가능하지만, 검증되지 않은 이동·운영시간으로 하루 일정의 실행 가능성을 보장하지 않는다. 자동 일정 생성기는 추가하지 않는다.
요금·시간표·운영 여부가 미확인이면 숫자를 모델 기억으로 채우지 않고 ‘확인된 정보 없음’과 준비된 공식 링크를 제공한다. 예약 가격·재고는 검증된 공식/제휴 예약 페이지에서 최종 확인하도록 연결한다. 링크가 없으면 URL도 만들지 않는다. 자동 웹 검색은 첫 버전에 넣지 않으며 도입 시 별도 결정한다.
열람과 질문 자체로 평소 취향을 갱신하지 않는다. 반복 상세 열람은 유효한 설명 캐시를 재사용한다.

제휴 링크는 추천 선택이 끝난 뒤 연결한다. 수수료·제휴 공급 여부를 추천 입력에 넣지 않는다.
설명과 유의점을 광고 뒤로 숨기지 않는다. 제휴 정책의 상위 기준은 루트 README다.

## 답변 분류와 표시 책임 — 2026-10-05 합의

E2 출력 계약은 문장 또는 하나의 주장 단위로 `kind`(`fact`/`advice`/`unverified`), `text`, `evidence_ids`, 관련 `user_evidence_ids`, `place_ids`를 받는 방향으로 작성한다. 이는 목표 계약이며 실행 검증기는 아직 없다. 사실과 조언이 섞이면 분리하며 조언의 사실 전제도 근거와 연결한다. 모델이 반환한 종류나 배지 문구를 그대로 신뢰하지 않는다.

서버·앱은 ID·자료 버전·검수·만료·제외·장소 범위를 검증한다. 검사 실패 사실을 `advice`로 바꿔 통과시키지 않는다. `unverified`에는 추측한 값 대신 확인되지 않은 항목을 표시한다. 구조 검사가 통과해도 문장과 근거의 의미 일치는 보장되지 않으며 사람 평가가 필요하다.

화면에서 사실 근거·개인화 조언·최신 확인 필요를 구분한다는 원칙은 채택한다. ‘도시 자료 기반 / 취향에 따른 제안 / 최신 확인 필요’는 **표시 문구 후보**이며 최종 문구·배치·아이콘은 U3에서 검토한다. 근거 표시를 ‘사실 검증 완료’ 배지로 쓰지 않는다. 근거에서는 출처·확인일을 확인할 수 있어야 한다. 문장별 혼합 답변을 하나의 검증된 답변처럼 표시하지 않는다.
