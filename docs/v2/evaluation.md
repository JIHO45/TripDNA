# 평가 계획과 도입 기준

상태: 2026-10-07 v2, 다음 비교는 **실행 전**이다. 이전: [비교 실험](../evaluation/offline-evaluation.md), [목록 대 프로필](../evaluation/profile-exploration.md), [지침 비교](../evaluation/guideline-comparison.md).
과거 계획·결과를 소급 변경하지 않는다. 새 비교는 기존 실행 번호와 섞지 않고 별도 계획 고정본·결과 파일로 남긴다.

## 다음 비교

> 2026-10-07 변경: 방식 구성은 [실행 5 계획](run5-plan.md)에서 네 방식(검색 없는 Haiku, Haiku + 검색, Haiku + 검색 + 제약 입력, Sonnet + 검색)으로 바꿨다. 아래 세 방식은 변경 전 기록이며 나머지 원칙은 그대로 적용한다.

동일 사례로 다음 세 방식을 비교한다.

- A: 현재 기준선 Haiku 4.5, 목록만, 추론 꺼짐.
- B: 상위 모델, 목록만. 모델 ID·추론 설정은 실행 전에 고정한다.
- C: A와 같은 모델·기본 생성 설정·목록에 실제 웹 검색과 근거 인용을 추가한다.

모델 변경과 검색 추가는 서로 다른 비교다. B에서 모델과 추론 설정을 함께 바꾸면 묶음 효과로 기록하며 각각의 인과 효과로 주장하지 않는다. 필요할 때만 별도 실험을 추가한다.
공통 지침은 같은 사용자 조건·출력 구조를 사용한다. C에 필요한 검색·인용 지침은 방식 차이로 명시한다. A/B는 검색 없이 답하며 근거 없는 출처 생성을 요구하지 않는다. 공통으로 확인되지 않은 핵심 조건의 충족을 단정하지 않게 한다. C의 근거 정책은 [출처 계약](../README.md#sources)을 따른다.

후보와 사용자 원문·언어·과제·출력 길이 한도를 같게 둔다. 인용 메타데이터는 답변 본문 길이와 별도 기록한다. 모든 방식에 같은 코드 검사를 적용하고 원본 출력과 검사 후 출력을 모두 보존한다. 기존 결과를 A 대신 재사용하지 않고 같은 실행에서 기준선을 다시 측정한다.

## 사례와 실행 전 고정

기존 실패 사례는 개선 진단용이다. 별도로 새 사례를 만들고 프롬프트 개발에 쓰지 않은 확인용 묶음을 고정한다. 확인용 결과를 보고 프롬프트를 고쳤다면 새 버전·새 확인 사례로 평가한다.
나라·도시가 지정된 조건 질문과 도시 언급 없는 열린 추천을 둘 다 포함한다. 지정 도시 상세 답변의 성공을 열린 추천 선택 품질로 일반화하지 않는다.

첫 호출 전에 다음을 별도 실행 계획에 확정한다.

- 사례별 원문·필수/선호 조건·추천과 상세 과제·기대 판단·공식 대조 자료. 평가용 정답·출처는 모델 입력에 넣지 않는다.
- 후보·입력·지침의 버전/해시, 정확한 모델 ID·추론/캐시·출력 제한, 검색 제공자·검색 횟수/시간 한도·날짜/도메인 설정.
- 사례 수·반복 수·호출 상한·방식별 실행 순서 교차 배치, 검수자와 검수 시간 상한. 반복을 독립 사용자 표본으로 세지 않는다.
- 품질·확인 불가·답변 범위의 허용 기준, 추천/상세별 지연 및 비용 상한, 혼합·동률·기술 실패의 판정 규칙.
- 검색·추론·초안 작성·실패까지 포함한 과금 항목과 최대 지출 추정, 잔여 예산, 외부 호출 없는 도구 검사 결과.

기본안은 자동 재시도 없이 실패를 기록하는 것이다. 다른 설정이 필요하면 첫 호출 전에 고정한다. 실행 도중 유리한 응답만 재생성하거나 불리한 사례를 빼지 않는다. 검색 기능이 실제로 동작했는지 검색 기록으로 확인하며, 연결되지 않았으면 C를 실행한 것으로 세지 않는다.

## 예산

기존에 정한 **첫 외부 파일럿 총 US$10 상한**은 탐색 실험·검색 비용과 공유한다. 새 문서나 실행마다 추가 US$10으로 초기화하지 않는다. 이전 지출과 남은 한도는 호출 전에 실제 기록에서 확인하며 현재 잔액은 이 문서에서 추정하지 않는다.
모델·검색 단가와 제공자 보관 설정을 실행 시점 공식 자료로 확인한다. 상한이 부족하면 사례/호출 계획을 호출 전에 줄이거나 별도 예산 결정을 받는다. 미완료 반복·미검수는 미판정으로 남긴다. 이번 문서 개편은 유료 API 실행이나 예산 증액을 포함하지 않는다.

## 판정과 기록

응답마다 조건 준수, 사실 정확성, 필요한 안전·계절 유의점 누락, 질문에 직접 답한 범위, 내부 용어 노출을 분리한다. C는 주장별 출처가 실제로 해당 내용을 뒷받침하는지 추가 검수한다. 인용 수가 많다는 이유로 품질을 높게 주지 않는다.

- 사실: 맞음 / 틀림 / 확인 불가. 제공 자료 밖이라는 이유만으로 틀림이 아니며, 출처가 있다는 이유만으로 맞음도 아니다.
- 제약: 충족 / 위반 / 판단 불가. 사용자 조건을 어긴 추천을 유의점으로 정당화하지 않는다.
- 답변: 직접 답변 / 부분 답변 / 답변 불능. 적절히 모름을 밝히는 것은 오류와 구분하되 사용성에 반영한다. 안전 등 보장할 수 없는 질문에 한계를 설명한 것은 정상 답변일 수 있다.
- 출처: 실제 열람 여부, 주장과의 의미 일치, 지역·시기·단위의 적합성, 날짜 확인 여부. 결론을 좌우하는 사실은 공식 출처로 대조한다.

실패·파싱 오류·잘림·검증 탈락·재시도 비용까지 포함한다. 확인 불가를 정상으로 세지 않는다. 문장별 진단과 응답별 오류율을 섞지 않는다. 각 비율의 분자·분모·미검수 수를 함께 기록하며 분모 0은 미산출이다.
생성 오류, 코드가 차단한 오류, 통과한 오류, 정상 답변을 잘못 차단한 오탐을 각각 기록한다. 검색 지연은 요청 시작부터 검증된 최종 결과까지, 최초 표시 시간과 구분해 측정한다. 평균과 표본 수·범위를 제시하고 충분한 표본이 있을 때 분위수를 계산한다.

모델 사용량·검색 횟수·실제 청구 또는 추정 여부·전체 비용·사람 검수 시간을 남긴다. 검색어·검색 시각·반환/열람 URL·근거 발췌와 도구 버전을 허용되는 보관 범위에서 남긴다. 검색 결과 원문을 보존하지 못한 부분과 재현 한계를 표시한다. 보관 경계는 [저장 계약](../README.md#storage)을 따른다.

AI 검수와 사람 자체 검수·독립 검수를 구분한다. 검수자 의견 불일치는 해결 전 미판정이다. 공식 대조가 없는 잠정 판정을 확정 사실로 바꾸지 않는다.

## 결과에 따른 다음 결정

사전 품질 기준을 통과한 방식 중 비용·지연과 답변 범위를 비교한다. 혼합 결과면 일괄 승자를 만들지 않는다. 세 방식 모두 부족하면 오류 원인을 보고 필요한 변경만 새 실험으로 고정한다.
검색이 충분히 정확하고 비용·지연도 허용되면 전체 프로필 없이 진행할 수 있다. 정확성은 충분하나 속도·비용이 부족할 때 검색 범위 축소·재사용·사전 제약 저장을 비교한다. 이 결과는 다음 구현 후보 선정이지 출시 승인이나 실제 사용자 선호 개선의 증명이 아니다.

## 확대와 최종 도입

합성 사례 다음에는 동의받은 실제 사용자로 후보 선택의 적합성을 평가한다. 설명과 모델 이름을 숨기고 동일 형식의 후보를 먼저 평가하며, 설명은 나중에 별도로 검수한다. 같은 후보는 중복 평가시키지 않는다. 단순 관심사 규칙과 LLM 비교는 후보·사용자 사실·사용 가능한 정보를 맞춘다. 검색 접근권 등이 다르면 시스템 전체 비교로 명시한다.
기존 국가 앱과 도시 추천은 입력량·추천 단위 차이를 기록하는 별도 비교다. 기존 앱은 Git 커밋과 번들 해시를 고정한다. 미방문은 오답이 아니며, 과거 평가를 가릴 때 파생 태그·순위·비교 관계도 정답을 누설하지 않도록 제거한다.

기존에 합의한 확대 관문의 보호 조건은 유지한다. 확대는 후보 범위 검증 확대이며 전체 프로필 제작 재개를 자동 의미하지 않는다.

- 개발에 사용하지 않은 **최소 8명**, 사용자별 실행 전 고정한 대표 사례 1개. 반복·추가 사례로 투표권을 늘리지 않는다.
- 사전 고정한 전체 참여자의 과반이 설명을 숨긴 비교에서 단순 규칙보다 LLM 후보를 선호해야 확대 신호로 본다. 동률·실행 실패·미응답은 분모에 포함한다. 유효 응답자가 8명 미만이면 재시험한다. 철회에 따른 표본 변경은 기록하고 재시험한다.
- 실제 제시된 제외 위반·확인된 틀린 사실·미확인 변동/안전 정보 및 필수 조건 충족에 대한 근거 없는 단정은 0건이어야 한다. 사실 판정 미완료는 보류다. 차단된 오류도 보고·수정하고 실패 비용을 포함한다. 지출은 위 예산 계약을 따른다.
- 검수 종류와 확보 인원을 기록한다. 기준 미달이면 재시험/보류이며 유리한 모델·사례를 사후 선택해 통과했다고 하지 않는다.

이 관문은 운영 판단이며 통계적 우월성 증명이 아니다. 확대 전 최종 표본·품질·비용·지연 기준을 결과를 보기 전에 별도 고정한다. 최종 결과 뒤 출시 모델·후보 범위·운영 한도·공개 시점을 결정한다. 설명만 좋아졌다면 선택 모델 교체 근거는 부족하다.

## 구현 회귀 시나리오

정책 원문을 복제하는 체크리스트가 아니라 실제 입력과 관찰할 실패를 묶는다. PC 출력 검사와 앱 저장·재시작 검사를 구분해 실행한다.

1. 즉흥 선호자가 일본·미국·캐나다 사진 등록 → 계획 선호가 새로 생기는지.
2. 이유 없는 도쿄 긍정 → 미식·사교 선호를 만들어내는지.
3. 혼자 새 사람 만나기 / 친구와 시간 보내기 → 서로 다른 요구를 구분하는지.
4. 도시·자연 모두 좋아함 / 둘 다 모름 → 같은 입력으로 압축되는지.
5. 도쿄 계속 제외 후 재시작·재추천 → 도쿄 노출 또는 오사카까지 제외되는지.
6. 이번 여행 제외 후 재시작·새 여행 → 범위별 지속성이 맞는지.
7. 예산 불만 → 무관한 도시·자연 선호가 바뀌는지.
8. 질문·열람·북마크 → 평소 취향이 자동 생성되는지.
9. 요청 중 조건 변경 → 늦은 응답이 현재 결과를 덮어쓰는지.
10. 근거 없는 명소·가격·운영·URL → 사실처럼 표시되는지.
11. 후보 부족·비용 한도 → 제외를 풀거나 사실을 만들어내는지.
12. 기억 삭제·되돌리기 → 다음 입력·공유·과거 요약에서 복원되는지.
13. 나라만 확인된 방문 → 모든 소속 도시를 방문 처리하는지.
14. 핵심 조건의 근거 없음 → 충족 배지가 표시되는지.
15. 조언으로 포장한 사실·무관한 유효 출처 연결 → 의미 불일치가 통과하는지.
16. 범위 밖/미확인 장소·배편/숙박 미상 → 범위 안·이동 불필요·당일 가능으로 둔갑하는지.

시간 합산·안전 누락·검색 실패와 날짜 미확인·오래된 출처도 다음 비교에 포함한다. 세부 재현 입력과 기대값은 실행 계획에서 고정하며 여기서 성공 결과를 미리 쓰지 않는다.
