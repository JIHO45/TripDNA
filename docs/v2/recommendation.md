# 추천 구조 — 문서 체계 v2

상태: 2026-10-07 결정과 검증 방향. 앱 적용 전 설계다.
이전: [설계 원문](../recommendation/architecture.md). 변경 이유의 실험 기록은 [실행 1~2](../evaluation/profile-exploration.md)와 [지침 비교](../evaluation/guideline-comparison.md)에 있다. 이번 결정은 제한된 실험을 근거로 다음 검증 순서를 고른 것이며 모든 모델에서 프로필이 불필요하다는 결론이 아니다.

## 이번 결정

- 전체 도시 프로필 제작·사람 전수 검수·자료 확대는 보류한다. 도시 목록을 기본 입력으로 놓고 모델 변경과 검색 추가의 효과부터 비교한다.
- 기존 “자동 웹 검색을 넣지 않는다”는 제한을 **비교 실험에 한해 해제**한다. 검색의 앱 도입·출시 기본 모델은 평가 후 결정한다.
- 검색으로 도시별 제약을 미리 생성·저장하는 구조도 지금 채택하지 않는다. 검색의 품질은 충분하지만 비용·지연이 문제라는 측정 결과가 나왔을 때 검토한다.
- 새 매칭 공식·벡터 DB·다단계 에이전트를 먼저 만들지 않는다.

여기서 프로필은 **공용 도시 정보 묶음**이다. 사용자의 직접 선호·기억을 없애는 결정이 아니다.

## 추천 단위와 입력

도시를 중심으로 추천하고 나라는 위치·묶음 정보로 둔다. 나라를 먼저 고르는 필수 단계는 없다. 사용자가 특정 나라·도시를 조건으로 정한 경우에만 그 범위를 적용한다. 후보의 식별은 [후보 계약](../README.md#candidates), 조건의 의미와 우선순위는 [사용자 기억](../README.md#memory)을 따른다.

입력은 활성 사용자 증거, 이번 조건, 방문 정보, 제외, 허용 후보와 입력 버전이다. 정보가 부족하면 탐색 제안임을 구분하고 날짜·예산 등 추가 답변을 첫 추천의 필수 관문으로 만들지 않는다.

## 처리 흐름과 책임

1. 현재 입력과 유효한 저장 결과가 일치하면 재사용한다.
2. 코드가 명확한 제외·허용 ID와 판정 가능한 필수 조건으로 후보를 걸러낸다. 자연어의 모호함을 임의의 강한 필터로 바꾸지 않는다.
3. 모델이 후보 선택·추천 이유·자유문장 피드백 해석을 담당한다. 실험별 자료 접근 권한은 [평가 계획](../README.md#evaluation)을 따른다.
4. 코드가 허용 ID·중복·제외·출력 형식·입력 버전과 확인 가능한 조건을 검사한다. 필요한 값이 검증되면 시간·비용 합산은 코드로 계산한다. 미확인 값을 계산해 확인된 사실로 바꾸지 않는다.
5. 표시 직전 앱이 최신 입력·제외를 다시 확인한다. 출처와 표현의 허용 범위는 [근거 계약](../README.md#sources)을 따른다.

링크나 ID가 존재하는 검사는 문장과 근거의 의미 일치를 보장하지 않는다. 내부 ID·프로필 용어 노출도 출력 검사 대상으로 두되 문자열 검사로 모든 의미 오류를 잡는다고 주장하지 않는다.
모델이 DB를 직접 수정하지 않는다. 명시 버튼은 코드로 처리하고 자유문장 해석만 모델에 맡긴다. 사용자 문장·검색 페이지·자료를 시스템 지시로 실행하지 않는다.

## 재생성·실패

취향·조건·제외·후보·자료 또는 출처 유효성·모델·프롬프트 변경이 결과에 영향을 주면 관련 결과를 무효화한다. 탭 재진입마다 새 호출하지 않는다. 검색 기반 결과의 유효기간은 정보별 변동성을 고려해 채택 전에 정하며 아직 정하지 않은 영구 재사용 기간을 가정하지 않는다.

제외는 저장 성공 후 즉시 화면에 반영한다. 기본안은 그 자리만 대체하고 다른 유효 카드는 유지하는 것이다. 핵심 목적·조건이 바뀌면 전체를 재평가한다. 생성 실패가 저장된 제외를 취소하지 않는다.

- 조건이 바뀐 뒤 도착한 이전 응답은 폐기한다.
- 실패·오프라인·호출 한도에서는 현재 조건을 여전히 만족하는 유효 결과만 재사용한다. 없으면 실패와 재시도 경로를 표시한다.
- 후보가 적으면 그 수만 반환한다. 적합한 후보가 없으면 조건 변경을 요청하며 제외를 임의로 푸는 대체 추천을 하지 않는다.
- 앱 채택 시 출력 검증 실패의 자동 재시도는 최대 1회를 기본안으로 두고 이후 수동 재시도로 전환한다. 실험의 재시도 정책은 [평가](../README.md#evaluation)에서 별도로 고정한다.

## 2026-10-07 추가 결정: 구독, 자료 배포, 저장

[실행 5 부분 결과](../../data/exploration/runs5/result-partial.md)의 비용 측정 뒤에 사용자가 정했다. 실험이 끝나기 전의 결정이며, 모델·검색 구성의 채택은 여전히 평가 뒤에 한다.

**LLM 기능은 유료 구독자에게만 제공한다.**

- LLM을 쓰는 추천과 질문 답변이 대상이다. 계기는 검색을 쓰는 호출의 원가다(Haiku 기준 추천 약 US$0.085, 상세 약 US$0.039, 검색 없는 호출은 약 US$0.002).
- 무료 사용자에게는 LLM을 쓰지 않고 기존 추천만 제공한다(2026-10-07 사용자 결정). 검색 없는 LLM 추천을 무료로 주는 안은 택하지 않았다. 그 구성은 실행 5의 함정 사례 9건 중 4건에서 조건을 어겼다.
- 가격, 상품 형태(월 구독, 기간제 이용권 등), 사용량 한도는 미정이다. 구독을 뺐던 이전 판단의 근거는 [v1 제품 기록](../v1/project.md)에 있다.
- 로그인을 필수로 만들지 않는 원칙은 유지한다.

**도시 자료는 앱 번들로 배포한다.**

- 후보 목록(약 100곳)과 채택되는 도시 자료를 앱 번들에 넣고 앱 업데이트로 갱신한다. 서버에서 내려받는 구조와 서버 DB는 두지 않는다.
- 번들 자료는 앱 업데이트 사이에 바뀌지 않는다. 가격·운영 시간·시즌 일정처럼 자주 바뀌는 사실은 번들에 넣지 않고, 필요하면 검색으로 확인한다.
- 전체 도시 프로필 제작 보류는 그대로다. 번들에 무엇을 넣을지(목록만, 목록과 제약 몇 줄 등)는 평가 뒤에 정한다.

**외부 DB를 지금 두지 않는다.**

- 사용자 기록은 기기에만 둔다. LLM을 부를 때 필요한 내용을 기기에서 꺼내 함께 보낸다.
- 검색으로 확인한 사실을 여러 사용자가 재사용하는 공용 저장소도 지금 만들지 않는다. 원가를 낮추는 수단으로 나중에 검토할 수 있다.
- LLM 호출 서버는 여전히 필요하다. API 키를 앱에 넣을 수 없고 구독 여부를 확인해야 하기 때문이다.
- **풀어야 할 점:** 구독자별 사용량 한도를 두려면 서버가 구독자별 사용 횟수를 기억해야 한다. 이것은 작은 저장이지만 저장이다. 한도를 어떻게 구현할지와 그 저장을 허용할지는 미정이다.

**서버와 서버 저장에는 Firebase를 쓴다.**

- LLM 호출 중계는 Cloud Functions, 서버 저장은 Firestore로 한다. 사용자가 2026-10-07에 정했다. 나중에 사용자 평가를 모을 자리까지 같은 곳에 두기 위해서다.
- Firebase는 2026-09-10에 로컬 저장으로 바꾸며 뺐고 이후 제품 범위에서 제외해 왔다. 기록된 이유는 “당시 로컬 저장 선택”이며, 같은 날 구독을 빼고 목표를 출시·유입으로 바꿨다. 구독과 사용자 평가 수집이 다시 계획에 들어오면서 그 전제가 달라졌다.
- 이 결정은 제품 선택이다. 위의 “외부 DB를 지금 두지 않는다”는 그대로다. 사용자 기록은 기기에, 도시 자료는 앱 번들에 둔다. Firestore에 처음 들어갈 수 있는 것은 구독자별 사용 횟수뿐이고, 사용자 평가의 수집은 출시 후 별도 결정이다.
- 로그인 화면 없는 사용자 식별에는 Firebase 익명 로그인을, 정식 앱에서 온 요청인지 확인하는 데는 App Check를 쓴다.
- 구독 확인은 앱이 보낸 구매 정보의 서명과 만료일을 Cloud Functions에서 애플 공식 라이브러리로 검증한다. 구독 관리 서비스는 붙이지 않고 시작하며, 환불·가족 공유 등 예외 처리가 커지면 다시 본다.
- 예전 Firestore 컬렉션과 규칙을 되살리지 않는다. 필요한 구조는 새로 정한다.
- 알려진 한계: Firestore는 여러 조건으로 묶어 세는 집계 질의에 약하다. 칸별 평가 수는 저장 시점에 따로 세어 두거나 밖으로 내보내 계산해야 한다. 요금은 읽기·쓰기 횟수에 따라 붙고, Cloud Functions에서 외부 API를 부르려면 종량 요금제가 필요하다. 현재 요금과 한도는 확인하지 않았다.

## 여행지 값의 갱신 (출시 후)

처음에는 고정된 자료로 시작하고, 사용자 평가가 쌓이면 검증을 거쳐 고친다. 출시 전에는 구현하지 않는다. 숫자 기준과 주기는 미정이며 아래 원칙만 고정한다.

- **대상은 적합성이다.** 어떤 취향·조건의 사용자에게 그 여행지의 어떤 경험이 맞았는지를 갱신한다. 사실(계절, 운영, 이동)은 인기나 평가 수로 바꾸지 않는다. 사실과 어긋나는 보고가 몰리면 다시 확인할 신호로 쓴다.
- **기준은 전체 사용자 수가 아니라 칸별 근거의 양이다.** 도시 × 경험 × 사용자 조건의 한 칸에 평가가 충분히 쌓였을 때 그 칸만 갱신 후보가 된다.
- **근거는 다녀온 뒤의 평가와 그 이유다.** 방문 사실, 클릭, 저장은 쓰지 않는다. 보여주지 않은 후보를 싫어한 것으로 세지 않는다.
- **방문자의 취향 평균을 여행지의 특성으로 되먹이지 않는다.** “누가 갔나”가 아니라 “간 사람이 무엇을 좋게 평가했나”를 쓴다.
- **묶어서 검증한 뒤 반영한다.** 평가 한 건마다 자동으로 바꾸지 않는다. 떼어 둔 평가로 새 값이 이전 값보다 실제 만족을 잘 맞히는지 확인하고, 사람이 확인한 버전으로 반영하며 되돌릴 수 있게 한다.
- **반영 방식은 미정이다.** 집계 통계를 LLM 입력에 넣는 방법과 별도 순위 모델을 데이터가 생긴 뒤 비교한다.

이 갱신에는 사용자 평가를 모으는 서버 저장이 필요하다. 도입은 별도 결정이며, 수집 목적·항목·보관 기간·동의·철회·삭제를 정하기 전에는 기록을 서버로 보내지 않는다. 지금 할 일은 나중에 칸별로 셀 수 있는 형태로 기기에 기록을 남기는 것뿐이다([계측](../README.md#metrics)).

## 채택 전에 남은 결정

출시 모델·검색 제공자와 호출 시점, 첫 공개 후보 범위, 비용·지연 허용치, 결과 유효기간은 미정이다. 도시 자료의 배포 방식은 위에서 앱 번들로 정했다. 첫 추천에 검색을 붙일지 상세에서만 쓸지도 측정 후 정한다. 프로필·검색·상위 모델 어느 것도 아직 출시 품질을 입증하지 않았다.
